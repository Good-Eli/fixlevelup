# Техническое задание
## Сервис выездного ремонта бытовой техники

**Версия:** 1.0  
**Дата:** 19 ноября 2026 года  
**Статус:** базовое функциональное ТЗ для проектирования и разработки  
**Назначение:** единый исходный документ для разработки сайта, Telegram-бота, Telegram Mini App мастеров и CRM менеджера.

---

## Паспорт проекта и принятые решения

Проект представляет собой цифровую систему одной ремонтной мастерской, обслуживающей один город. Компания выполняет выездной ремонт стиральных и посудомоечных машин, холодильников и телевизоров. В штате ориентировочно 5–10 мастеров. Мастера являются сотрудниками компании, работают по назначаемому графику и не являются независимыми исполнителями маркетплейса.

| Вопрос | Зафиксированное решение |
|---|---|
| География | Один город; точное название и зона обслуживания задаются в настройках |
| Исполнители | 5–10 штатных мастеров |
| Ценообразование | Единый корпоративный прайс; скидки и надбавки контролируются менеджером/администратором |
| Выбор работ | Мастер выбирает только утверждённые позиции каталога; свободно назначать цену за работу нельзя |
| Оплата | Клиент оплачивает непосредственно мастеру; онлайн-эквайринг в первой версии не нужен |
| Чеки | Генерация чеков не входит в объём разработки; налоговые/фискальные обязанности компании определяются отдельно и не отменяются этим решением |
| Клиентский канал без звонка | Telegram; клиент должен самостоятельно открыть бота и запустить его |
| Клиентский личный кабинет | Не разрабатывать в первой версии |
| Интерфейс мастера | Telegram Mini App + уведомления Telegram |
| Интерфейс менеджера | Веб-панель CRM |
| Основная база | Единая база данных для сайта, CRM, бота и Mini App |

### Что не задано и не должно быть придумано разработчиком

До запуска владелец проекта должен заполнить: название мастерской, город, адрес/зону выезда, телефон, домен, реквизиты оператора персональных данных, рабочие часы, фактический прайс, стоимость выезда и диагностики, временные границы вечернего/ночного тарифа, величины надбавок, правила экспресс-вызова, список мастеров, перечень районов, гарантийные условия, ссылку на профиль Авито и тексты юридических документов.

Все перечисленные параметры должны быть изменяемыми из административной части или через конфигурацию без правки исходного кода. В коде запрещено зашивать фиктивные цены, адреса, расписания и контактные данные.

# 1. Назначение и цели системы

## 1.1. Назначение

Создать единую систему обработки заявок на выездной ремонт бытовой техники. Система должна принимать заявки с публичного сайта, передавать их менеджеру, помогать назначать подходящего штатного мастера, предоставлять мастеру инструменты для выполнения заказа и фиксировать состав работ, итоговую сумму и факт оплаты.

## 1.2. Бизнес-цели

1. Упростить обращение клиента: звонок или самостоятельное оформление заявки без телефонного разговора.
2. Сократить время между поступлением заявки и назначением мастера.
3. Исключить потерю заявок и разрозненные записи в мессенджерах/таблицах.
4. Обеспечить единый контролируемый прайс и прозрачное формирование суммы заказа.
5. Видеть загрузку и производительность каждого мастера.
6. Собирать историю обращений и ремонтов клиента.
7. Использовать реальные отзывы Авито как внешний источник доверия, не имитируя отзывы на собственном сайте.

## 1.3. Критерии успеха

После внедрения менеджер в одном интерфейсе видит все заявки и график мастеров; мастер получает назначенные заявки в Telegram и закрывает их отчётом; клиент может оформить заказ с телефона без звонка; стоимость ремонта рассчитывается по утверждённым позициям прайса; руководитель видит основные показатели по заявкам и мастерам.

## 1.4. Объём первой версии

В первой рабочей версии реализуются:

- адаптивный одностраничный сайт;
- две клиентские формы: обратный звонок и полноценная заявка без звонка;
- клиентский Telegram-бот для привязки заявки, сообщений и подтверждения сметы;
- CRM менеджера с заявками, календарём и карточками мастеров;
- Telegram Mini App мастера;
- справочники услуг, неисправностей, цен, запчастей, надбавок и скидок;
- диспетчеризация с окончательным назначением менеджером;
- фиксация отчёта мастера и прямой оплаты клиентом мастеру;
- базовая статистика и аудит действий.

## 1.5. Вне объёма первой версии

Не разрабатывать без отдельного согласования: клиентский личный кабинет с паролем; мобильные приложения для iOS/Android; онлайн-оплату; бухгалтерию и расчёт зарплаты; складской учёт; интеграцию с кассой/ОФД; автоматическое GPS-слежение; полноценный маршрутный оптимизатор; мультигородскую структуру; маркетплейс независимых мастеров; автоматическую выгрузку отзывов из Авито; автоматическую закупку запчастей.

# 2. Архитектура решения

## 2.1. Общий принцип

Использовать архитектуру **модульного монолита**: единое серверное приложение и одна основная база данных, разделённые на логические модули. Не создавать микросервисы и сложную распределённую инфраструктуру без реальной необходимости. Для масштаба 5–10 мастеров модульного монолита достаточно.

Состав системы:

1. **Публичный сайт** — доступен без регистрации.
2. **CRM менеджера** — защищённая веб-панель.
3. **Telegram Bot** — сообщения клиентам и сотрудникам, связывание Telegram-аккаунтов, уведомления.
4. **Telegram Mini App мастера** — расписание, заказы, отчёты.
5. **Backend API** — единая бизнес-логика, права, расчёт цен, статусы и интеграции.
6. **PostgreSQL** — единое хранилище структурированных данных.
7. **Хранилище файлов** — фотографии техники и вложения, закрытые от публичного доступа.

## 2.2. Рекомендуемый технологический стек

| Слой | Рекомендуемая технология | Примечание |
|---|---|---|
| Публичный сайт и CRM | Next.js, React, TypeScript | Общая кодовая база, разные защищённые маршруты и layouts |
| Telegram Mini App | React, TypeScript | Может собираться как отдельный frontend-пакет в том же репозитории |
| Backend | NestJS, TypeScript | Модульный REST API, интеграция Telegram Webhook |
| База данных | PostgreSQL | Основная и единственная транзакционная БД |
| ORM и миграции | Prisma или эквивалент | Миграции обязательны, ручная правка схемы production запрещена |
| Файлы | S3-совместимое объектное хранилище | Приватный bucket, временные ссылки на просмотр |
| Очередь уведомлений | Таблица outbox в PostgreSQL на старте | Redis/отдельная очередь добавлять только при обоснованной нагрузке |
| Развёртывание | Docker Compose или эквивалент | Отдельные среды development/staging/production |

Допускается эквивалентный стек, если исполнитель заранее описал преимущества, не усложняет поддержку и сохраняет все архитектурные требования. Версии библиотек фиксируются lock-файлом; использовать поддерживаемые стабильные релизы на дату начала разработки.

## 2.3. Логические backend-модули

- `Auth` — вход, сессии, привязка Telegram, права.
- `Customers` — клиенты, контакты и адреса.
- `Requests` — заявки, карточки, статусы и история.
- `Catalog` — типы техники, неисправности, бренды и модели.
- `Pricing` — прайс, версии цен, скидки, надбавки и расчёты.
- `Scheduling` — смены, доступность, отпуска, блокировки и временные интервалы.
- `Dispatch` — подбор и назначение мастера.
- `WorkOrders` — диагностика, фактические работы, запчасти и завершение.
- `Payments` — регистрация факта прямой оплаты, без приёма денег системой.
- `Notifications` — Telegram-сообщения, повторы, журнал доставки.
- `Content` — контакты, FAQ, прайс публичной части, ссылки и отзывы Авито.
- `Analytics` — отчёты и агрегаты.
- `Audit` — неизменяемый журнал значимых действий.

## 2.4. Обязательные архитектурные правила

- Все интерфейсы обращаются к одной бизнес-логике и одной БД.
- Клиентская часть не рассчитывает окончательную цену самостоятельно: сервер возвращает расчёт.
- Сумма и позиции сохраняются в заказе как snapshot на момент согласования.
- Статусы меняются только через серверные команды с проверкой прав и допустимого перехода.
- Повторный запрос на создание заявки/оплаты/назначения не должен создавать дубликат: использовать idempotency key или иной механизм идемпотентности.
- Важные операции выполняются в транзакциях.
- События для уведомлений записываются в outbox в той же транзакции, что и бизнес-изменение; отправка выполняется фоновым обработчиком с повторными попытками.
- Физическое удаление заявок и финансовых записей обычным пользователям запрещено; применяется архивирование/soft delete, а финансовые события сохраняются.

# 3. Роли и права доступа

## 3.1. Роли

| Роль | Доступ |
|---|---|
| Неавторизованный посетитель | Публичный сайт, отправка форм, просмотр опубликованных цен и отзывов |
| Клиент с Telegram | Свои заявки, сообщения, согласование предложенной сметы и доступные действия по своей заявке |
| Мастер | Только назначенные ему заявки, собственный график/доступность, отчёты по своим заказам |
| Менеджер | Все заявки, клиенты, назначения, расписание, цены в пределах прав, отчёты и закрытие заказов |
| Администратор | Полные настройки, пользователи, роли, справочники, прайс, тарифные правила, аудит |

## 3.2. Матрица ключевых прав

| Действие | Мастер | Менеджер | Администратор |
|---|---:|---:|---:|
| Просмотр всех заявок | Нет | Да | Да |
| Просмотр назначенных ему заявок | Да | Да | Да |
| Назначение/переназначение мастера | Нет | Да | Да |
| Изменение рабочего графика другого мастера | Нет | Да | Да |
| Управление своей доступностью | Да | Да | Да |

Права проверяются на backend для каждого запроса. Скрытие кнопок на frontend не является механизмом защиты.

## 3.3. Учётные записи сотрудников

- Мастер создаётся администратором или менеджером с соответствующим правом.
- Самостоятельная открытая регистрация мастеров запрещена.
- Telegram ID связывается с заранее созданной учётной записью сотрудника.
- При увольнении сотрудник блокируется; история его заказов остаётся.
- Поддержать временное отключение сотрудника, отпуск и увольнение.

# 4. Публичный сайт

## 4.1. Общие требования

Сайт — одностраничный, mobile-first, быстрый и ориентированный на конверсию в заявку. Основной язык — русский. Не перегружать анимациями, pop-up и длинными текстами. Основные действия — позвонить или оформить ремонт без звонка.

Сайт должен корректно работать на смартфонах, планшетах и desktop. Все CTA-кнопки должны вести к телефону, форме или соответствующему разделу. Номер телефона должен быть кликабельным (`tel:`).

## 4.2. Структура главной страницы

1. **Первый экран:** название, краткое обещание, город/зона работы, телефон, кнопки «Позвонить» и «Оформить ремонт без звонка».
2. **Что ремонтируем:** стиральные машины, посудомоечные машины, холодильники, телевизоры. У каждой категории — короткое описание и переход к типовым неисправностям.
3. **Типовые неисправности и цены:** ориентировочные цены/диапазоны, пометка о необходимости диагностики и возможной стоимости запчастей.
4. **Как проходит ремонт:** заявка → согласование времени → выезд → диагностика → согласование сметы → ремонт → оплата.
5. **Почему обращаются:** только подтверждаемые факты — гарантия, опыт, квалификация, запчасти, прозрачный прайс. Не публиковать неподтверждённые обещания.
6. **Отзывы Авито:** несколько реальных выдержек с источником, датой/именем в разрешённом объёме и ссылкой на оригинальный профиль/отзыв. Кнопки «Все отзывы на Авито» и «Оставить отзыв на Авито».
7. **Зона выезда:** город, районы или проверка адреса по справочнику зон. Не заявлять обслуживание территории, куда мастера фактически не выезжают.
8. **FAQ:** диагностика, выезд, запчасти, гарантия, вечерние/ночные вызовы, порядок согласования цены.
9. **Контакты:** телефон, Telegram, график приёма заявок, юридические сведения оператора, ссылки на политику и согласие.
10. **Повторный CTA:** форма/кнопка вызова мастера.

## 4.3. Отзывы Авито

В первой версии отзывы размещаются вручную из подтверждённого профиля. Каждая запись содержит текст выдержки, дату, отображаемое имя (если допустимо), рейтинг (если он есть в источнике), URL оригинала и флаг публикации. Изменение/удаление отзыва на сайте доступно менеджеру/администратору.

Не создавать собственную форму публикации отзывов на сайте и не генерировать фиктивные отзывы. Автоматическую синхронизацию через API Авито не включать без проверки фактического доступа и разрешённых способов использования данных.

## 4.4. SEO и аналитика

- Человекочитаемые title/description, корректные H1-H3.
- Локальное SEO с городом и категориями услуг.
- Open Graph для ссылок.
- Sitemap.xml, robots.txt, canonical.
- Разметка LocalBusiness/Service только на основании реальных данных.
- Подключение счётчика аналитики возможно после проверки правовых оснований и настройки согласия на cookies, если применимо.
- В аналитике запрещено передавать телефоны, адреса, текст неисправности и другие персональные данные.

# 5. Приём заявок от клиента

## 5.1. Два сценария

Клиент выбирает один из двух сценариев:

**А. «Перезвоните мне»** — короткая форма, чтобы менеджер связался по телефону.  
**Б. «Оформить без звонка»** — подробная заявка с выбором техники, неисправности, адреса, времени и Telegram-подтверждением.

Эти сценарии должны быть одинаково заметны. Подробную форму не открывать сразу целиком: использовать пошаговые экраны/секции с индикатором прогресса.

## 5.2. Форма «Перезвоните мне»

Поля:

- имя — обязательное;
- телефон — обязательный, с маской и нормализацией;
- удобный интервал для звонка — необязательный, из настраиваемого списка;
- комментарий — необязательный;
- обязательный checkbox согласия на обработку персональных данных со ссылкой на документ.

После отправки создаётся заявка типа `CALLBACK`. Клиент видит подтверждение и номер обращения. Менеджер получает уведомление. Заявка попадает в очередь «Нужно перезвонить».

Для callback-заявки не требовать выбор техники, адреса и времени выезда. Менеджер может конвертировать обращение в полноценный заказ без повторного ввода клиента.

## 5.3. Подробная форма «Оформить без звонка»

Форма должна включать следующие шаги.

### Шаг 1. Техника

Обязательный выбор одной категории:
- стиральная машина;
- посудомоечная машина;
- холодильник;
- телевизор.

Дополнительно: бренд, модель, приблизительный возраст техники — необязательно. Справочник брендов расширяемый.

### Шаг 2. Неисправность

Показывать список симптомов, зависящий от выбранной категории. Примеры должны редактироваться через CRM. Обязателен вариант «Другая неисправность».

Также поля:
- описание своими словами;
- код ошибки (если известен);
- фото/видео техники, шильдика или ошибки — необязательно.

Вложения проходят проверку MIME-типа, размера и количества; ограничения задаются настройками. Файлы хранятся приватно.

### Шаг 3. Адрес

Обязательные поля: улица, дом, населённый пункт/город (город может быть предзаполнен и скрыт, если у проекта один город). Квартира, подъезд, этаж, домофон, комментарий по доступу — по правилам мастерской; рекомендуется оставить необязательными, если они не нужны для определения зоны.

Система определяет район/зону обслуживания по адресу или предлагает клиенту выбрать район из справочника. Если адрес за пределами зоны, заявка не должна отображаться как гарантированно доступная: показать честное сообщение и предложить оставить запрос на ручную проверку.

### Шаг 4. Дата и время

Клиент выбирает предпочтительную дату и временное окно. Доступные окна формируются с учётом графиков мастеров, специализации, района, уже назначенных заказов, длительности работ и буфера на дорогу.

**Выбранное время является предпочтением, а не окончательным подтверждением.** После назначения мастера менеджер подтверждает интервал клиенту. Интерфейс должен прямо объяснять это.

Если свободных окон нет, клиент может оставить предпочтительное время для ручного согласования. Нельзя показывать гарантированную доступность, если она не подтверждена алгоритмом.

### Шаг 5. Срочность

Два режима:

- **Обычный вызов** — ближайшее подходящее окно.
- **Экспресс-вызов** — приоритетная обработка и попытка назначить ближайшего свободного подходящего мастера за дополнительную плату.

Экспресс не означает гарантированное прибытие за конкретное число минут, пока компания не утвердила и не обеспечивает такой SLA. Если настройка целевого времени включена, показывать её только при наличии реальной доступности.

### Шаг 6. Контакты и подтверждение

Поля: имя, телефон для связи, способ связи. Для подробной формы без звонка способ связи по умолчанию — Telegram. Клиент должен подключить бота и нажать Start, после чего подтвердить привязку заявки.

Система не должна пытаться отправить Telegram-сообщение до того, как клиент сам открыл бота и запустил диалог. При незавершённой привязке заявка сохраняется со статусом `WAITING_TELEGRAM_LINK` и не переводится в обычную диспетчерскую очередь. На экране показывается кнопка повторного подключения и понятный резервный путь: изменить способ связи на «Перезвоните мне».

Телефон сохраняется как контакт для выездного обслуживания, но при выборе режима «без звонка» сотрудникам запрещено звонить клиенту, кроме случая, когда клиент отдельно изменил согласие/режим связи. В карточке заявки контактный режим должен быть заметен.

### Шаг 7. Проверка и отправка

Перед отправкой показать сводку: техника, симптомы, адрес, выбранное окно, режим срочности, ориентировочная стоимость/правило её определения, способ связи. Клиент подтверждает согласие на обработку персональных данных и отправляет заявку.

После сохранения показать номер заявки, статус и краткое объяснение следующих шагов.

## 5.4. Telegram-привязка клиента

Использовать Telegram deep link с одноразовым непредсказуемым токеном. Токен хранить в БД в хэшированном виде, ограничить срок действия и использовать только один раз. Токен не должен содержать телефон, адрес, ФИО или другие открытые персональные данные.

Последовательность:
1. Backend создаёт заявку/черновик и временный токен привязки.
2. Сайт открывает ссылку `t.me/<bot>?start=<token>`.
3. Клиент нажимает Start; бот получает параметр.
4. Backend проверяет токен, срок действия и статус.
5. Telegram ID привязывается к клиенту и заявке.
6. Клиент получает подтверждение привязки.
7. Заявка становится доступной менеджеру в рабочей очереди.

Одна Telegram-учётная запись может быть привязана к нескольким заказам одного клиента. Нельзя позволять клиенту по одному токену получить доступ к чужим заявкам.

## 5.5. Предварительная стоимость для клиента

Сайт показывает ориентировочную цену или диапазон по выбранной типовой неисправности. Источник диапазона — настроенный прайс/таблица соответствий симптомов и работ. Если диапазон неизвестен, показывать «Стоимость определяется после диагностики», а не подставлять условную сумму.

Отдельно отображать, если применимо:
- стоимость выезда;
- стоимость диагностики;
- ориентир по работам;
- информация о возможных запчастях;
- возможную надбавку за выбранное время/экспресс.

Текст обязательно поясняет, что итоговая стоимость зависит от фактической неисправности, необходимых работ и запчастей и будет согласована до ремонта. Публичная оценка не является финальным счётом.

# 6. Прайс и расчёт стоимости

## 6.1. Единый прайс

Базовый прайс общий для всех мастеров. Мастер не может иметь персональные цены. Цена позиции задаётся администратором; менеджер может управлять прайсом только при наличии отдельного разрешения.

Каталог разделяется минимум на:
1. услуги/работы;
2. диагностику и выезд;
3. запчасти/материалы;
4. тарифные надбавки;
5. скидки и специальные корректировки.

Для каждой работы хранить: код, название, категорию техники, описание, базовую цену, длительность для планирования, доступность для выбора мастером, доступность для публикации на сайте, дату начала действия цены, дату окончания (если применимо).

## 6.2. Версионирование прайса

Изменение цены создаёт новую версию/новую запись действия цены. Нельзя задним числом менять сохранённую стоимость старого заказа. В заказе сохраняются название позиции, код, количество, цена единицы и итог на момент согласования.

## 6.3. Выбор работ мастером

После диагностики мастер выбирает фактически выполненные работы только из активного утверждённого каталога. Сумма рассчитывается backend по цене позиции. Мастер не может редактировать поле цены, удалять обязательные тарифные строки или добавлять произвольную платную работу с произвольной стоимостью.

Если нужной работы нет в каталоге, мастер отправляет запрос «Нужна новая позиция/нестандартная работа» с описанием. Менеджер или администратор принимает решение и добавляет разрешённую строку/цену. До утверждения такой позиции она не включается в согласованную сумму.

## 6.4. Запчасти

Рекомендуемый порядок первой версии: отдельный каталог запчастей/материалов с наименованием и утверждённой ценой. Мастер выбирает фактически использованные позиции из каталога. Если нужной позиции нет, он отправляет её на согласование менеджеру; свободное изменение суммы запчасти мастером запрещено.

Если владелец решит пока не вести каталог запчастей, допускается временный режим «запчасть на согласование менеджеру», где мастер указывает только название/количество, а цену назначает менеджер. В любом случае итоговая цена клиенту не должна строиться на произвольной сумме, введённой мастером.

## 6.5. Скидки и надбавки

Система должна поддерживать:
- скидку в процентах;
- скидку фиксированной суммой;
- надбавку в процентах;
- надбавку фиксированной суммой;
- вечернюю надбавку;
- ночную надбавку;
- экспресс-надбавку.

Для каждого правила хранить: активность, период действия, способ расчёта, базу применения (работы, работы+запчасти, весь заказ или конкретные категории), минимальные/максимальные ограничения, совместимость с другими правилами и приоритет.

В первой версии временные надбавки должны быть взаимоисключающими друг с другом: если интервал попадает в ночной тариф, вечерний одновременно не добавляется. Экспресс-надбавка может суммироваться с одной временной надбавкой. Менеджерские корректировки применяются отдельно и фиксируются с причиной.

Менеджер может предоставить скидку или добавить надбавку в установленных администратором пределах. Превышение лимита требует подтверждения администратора. Мастер не применяет скидки/надбавки самостоятельно.

## 6.6. Формула

Итог рассчитывается на сервере по детализации:

`ИТОГО = выезд + диагностика + работы + запчасти + временная надбавка + экспресс-надбавка + утверждённые надбавки – утверждённые скидки`.

База применения каждой процентной надбавки/скидки определяется её настройкой. Система обязана показывать детализацию, а не только итог. Сумма не может стать отрицательной. Правила округления фиксируются единообразно; хранить деньги в целых копейках (integer), а не floating point.

## 6.7. Согласование сметы

После диагностики мастер формирует набор работ/запчастей из каталога. Backend рассчитывает смету. Менеджер проверяет её и отправляет клиенту через Telegram либо отмечает устное согласование по телефону, если клиент изначально выбрал звонок.

Для Telegram-клиента сообщение содержит понятную детализацию и кнопки «Согласен» / «Не согласен» / «Нужен вопрос». Нажатие фиксируется как отдельное событие с временем и версией сметы. До согласия ремонт не переводится в статус выполнения, кроме явно разрешённых диагностических действий.

При изменении состава/цены после согласования требуется новая версия сметы и повторное согласование. Старые версии сохраняются.

# 7. Расписание и диспетчеризация

## 7.1. График сотрудников

Для каждого мастера хранить:
- активность/неактивность;
- рабочие дни и интервалы смен;
- исключения: отпуск, болезнь, выходной, обучение, личная занятость;
- готовность к вечерним и ночным выездам;
- категории техники и дополнительные навыки;
- обслуживаемые районы;
- временной буфер на дорогу и подготовку;
- максимальное количество одновременно активных заказов (по умолчанию один выездной заказ в конкретный интервал).

Плановый график задаёт менеджер. Мастер в Mini App может сообщить о фактической недоступности или запросить изменение. Изменение утверждается менеджером, если это влияет на общую диспетчеризацию.

## 7.2. Расчёт доступных окон

При выдаче доступных временных интервалов учитывать:
1. рабочий график мастера;
2. подтверждённую специализацию на категории техники;
3. зону обслуживания;
4. уже назначенные визиты;
5. длительность визита по выбранной неисправности/типу работ;
6. буфер на дорогу и завершение предыдущего заказа;
7. отпуск и блокировки;
8. настройку экспресс-доступности.

Если система не располагает точной длительностью диагностики/ремонта, использовать настраиваемую оценку по категории и оставить окончательное подтверждение за менеджером.

## 7.3. Роль менеджера

Менеджер видит календарь по мастерам и список заявок. Для каждой новой заявки система показывает подходящих мастеров, причины соответствия/несоответствия и занятость. Менеджер вручную назначает мастера и подтверждает время.

Автоматическое назначение без подтверждения менеджера в первой версии запрещено. Автоматическая рекомендация допускается.

## 7.4. Назначение

При назначении backend повторно проверяет доступность в транзакции, чтобы два менеджера не назначили одного мастера на пересекающиеся интервалы. После назначения:
- создаётся запись assignment/appointment;
- клиенту отправляется подтверждение времени по выбранному каналу;
- мастеру отправляется уведомление;
- заявка меняет статус;
- все события записываются в историю.

Мастер должен подтвердить получение назначения. Если он не подтвердил в установленный интервал, CRM выделяет заказ как требующий внимания. Время ожидания настраивается; автоматическое снятие заказа — только по отдельной настройке.

## 7.5. Экспресс-диспетчеризация

Экспресс-заявка выделяется визуально. Система сначала ищет подходящих мастеров, готовых к экспресс-выезду и свободных в допустимом интервале. Менеджер видит ближайшие реалистичные варианты. Если подходящих мастеров нет, система предлагает клиенту обычное время или ручное согласование; не подтверждает несуществующую доступность.

# 8. Telegram Bot и Mini App

## 8.1. Клиентский бот

Назначение бота — связать клиента с заявкой и передавать важные сообщения. Полный интерфейс заказа остаётся на сайте.

Минимальные функции:
- `/start` — приветствие и обработка параметра привязки;
- `/help` — краткая справка и контакт мастерской;
- подтверждение привязки заявки;
- уведомление о принятии заявки в работу;
- подтверждение назначенного окна;
- отправка сметы;
- согласие/отказ/вопрос по смете;
- уведомление о переносе, завершении и гарантийной информации;
- кнопка «Связаться с менеджером».

Не отправлять клиенту рекламные сообщения без отдельного согласия. Не использовать бота как массовую рекламную рассылку.

## 8.2. Mini App мастера

Mini App открывается из Telegram-бота. Интерфейс mobile-first, крупные элементы управления, минимум ввода текста. Язык — русский.

### Главное меню

1. Сегодня.
2. Мои заказы.
3. Расписание.
4. Доступность.
5. История.
6. Профиль/специализация (только просмотр; изменения ограничены).

### Экран «Сегодня»

Показывает число назначенных заказов, ближайший визит, незавершённые отчёты и предупреждения. Для каждого заказа — номер, тип техники, временное окно, район и текущий статус.

### Экран заявки

Показывает номер, тип и бренд техники, описание неисправности, адрес, контактный способ, вложения, выбранное клиентом время, режим срочности, комментарии менеджера. Полный адрес и телефон доступны только назначенному мастеру и только в период, необходимый для выполнения заказа.

Действия:
- подтвердить получение;
- отметить «Выехал»;
- отметить «Прибыл»;
- начать диагностику;
- сформировать смету;
- отметить ожидание запчастей (с комментарием);
- начать ремонт после согласования;
- завершить ремонт и заполнить отчёт.

Если мастер не может выполнить заказ, он выбирает причину отказа/невозможности: занят, не подходит специализация, нет возможности добраться, личная причина, другое. После отказа заказ возвращается менеджеру; причина сохраняется.

### Экран доступности

Мастер видит свой график и может:
- указать фактическую доступность на ближайшие дни в пределах разрешённого горизонта;
- временно отметить «Недоступен»;
- запросить отпуск/выходной;
- подтвердить готовность к вечерним/ночным вызовам.

Плановый график редактирует менеджер. Мастер не может самостоятельно сделать себя доступным вне утверждённой смены, если это не разрешено настройкой.

### Формирование отчёта о ремонте

Обязательные поля:
- результат диагностики/фактическая неисправность;
- список реально выполненных работ из каталога;
- количество каждой работы;
- использованные запчасти из каталога;
- комментарий о результате;
- дата/время завершения;
- необязательные фотографии результата.

Поля суммы вычисляются сервером и доступны мастеру только для просмотра. Возможность добавить платную работу — только через поиск/выбор активной позиции каталога.

### Оплата напрямую мастеру

После ремонта мастер указывает:
- получил ли оплату;
- сумму, фактически полученную от клиента;
- способ: наличные / перевод / другой способ, если включён администратором;
- комментарий при неполной оплате или расхождении.

Система не принимает деньги и не проводит эквайринг. Статусы: `UNPAID`, `PARTIALLY_PAID`, `PAID`. Мастер не может изменить общую цену заказа, он фиксирует факт передачи денег. Менеджер видит расхождение между итогом сметы и полученной суммой.

### Завершение

После отправки отчёта заявка получает статус «Мастер сообщил о завершении». Менеджер проверяет работы, итог и оплату и закрывает заявку. До закрытия мастер может исправить отчёт, но каждое изменение журналируется. После закрытия изменения выполняются менеджером с указанием причины.

## 8.3. Безопасность Mini App

Не доверять `initDataUnsafe` и идентификаторам, переданным frontend. Backend должен валидировать исходный `Telegram.WebApp.initData` по официальному алгоритму Telegram, проверять подпись и свежесть `auth_date`, затем сопоставлять Telegram ID с активным сотрудником. Доступ предоставляется только заранее созданным сотрудникам. Сам факт открытия Mini App не даёт права на просмотр заявок.

# 9. CRM менеджера

## 9.1. Главная панель

Показывать:
- новые заявки;
- заявки, требующие звонка;
- заявки без назначенного мастера;
- назначения без подтверждения мастера;
- визиты сегодня;
- заказы в диагностике/ожидании согласования;
- отчёты мастера, ожидающие проверки;
- просроченные/проблемные заявки;
- число свободных мастеров.

Показатели должны рассчитываться из данных, а не задаваться вручную.

## 9.2. Реестр заявок

Таблица с фильтрами:
- период;
- статус;
- тип техники;
- срочность;
- мастер;
- район;
- источник;
- канал связи;
- оплата;
- наличие просрочки/проблемы.

Поиск по номеру заявки, телефону, имени клиента. Телефон отображать только пользователям с соответствующими правами.

## 9.3. Карточка заявки

Блоки карточки:
1. Номер, текущий статус, дата создания и источник.
2. Клиент и выбранный канал связи.
3. Техника, бренд, модель, неисправность и вложения.
4. Адрес и зона.
5. Предпочтительное и подтверждённое время.
6. Срочность и надбавки.
7. Назначенный мастер и его подтверждение.
8. История диагностики.
9. Сметы и история версий.
10. Выполненные работы и запчасти.
11. Итог и статус оплаты.
12. Внутренние комментарии.
13. Хронология действий и уведомлений.

Внутренние комментарии не должны уходить клиенту или мастеру автоматически.

## 9.4. Календарь

Виды: день/неделя, фильтр по мастеру, статусы визитов, цветовая индикация экспресс-заказов и конфликтов. Перетаскивание визита допускается только при повторной проверке доступности и подтверждении изменений. Перенос времени автоматически создаёт событие истории и уведомляет клиента и мастера.

## 9.5. Управление мастерами

Карточка мастера содержит ФИО, телефон/контакты, Telegram ID/статус связи, активность, специализации, районы, рабочий график, готовность к ночным/экспресс-выездам, текущую загрузку, статистику, историю заказов. Менеджер может назначать смены и блокировки в рамках прав.

## 9.6. Прайс и справочники

CRM должна позволять уполномоченным пользователям управлять:
- категориями техники;
- неисправностями/симптомами;
- брендами;
- работами и ценами;
- запчастями и ценами;
- временем выполнения для планирования;
- публичными диапазонами цен;
- стоимостью выезда и диагностики;
- вечерними/ночными тарифами;
- экспресс-надбавкой;
- скидками и ограничениями;
- районами обслуживания;
- FAQ и контактами сайта;
- ссылками и публикациями отзывов Авито.

Все изменения цен и важных справочников записывать в аудит.

## 9.7. Отчёты

Первая версия должна показывать за выбранный период:
- количество заявок;
- количество закрытых и отменённых;
- конверсию заявка → назначение → ремонт;
- средний чек;
- сумму заказов, отмеченных как оплаченные;
- сумму неоплаченных/частично оплаченных заказов;
- число ремонтов по мастерам;
- средний чек по мастерам;
- распределение по категориям техники;
- причины отмен и отказов;
- источники заявок.

Показатель «выручка» в панели следует подписать как «сумма оплат, отмеченных в системе», пока финансовая интеграция/бухгалтерская сверка не подключена. Не выдавать отметку мастера за независимое банковское подтверждение.

# 10. Статусы и жизненный цикл заявки

## 10.1. Основные статусы

| Код | Отображаемое название | Смысл |
|---|---|---|
| `NEW` | Новая | Заявка создана |
| `WAITING_TELEGRAM_LINK` | Ожидает подключения Telegram | Клиент выбрал связь без звонка, но ещё не запустил бота |
| `CALLBACK_REQUIRED` | Нужно перезвонить | Короткая заявка на звонок |
| `MANAGER_REVIEW` | На обработке менеджера | Проверка данных/адреса/времени |
| `WAITING_ASSIGNMENT` | Ожидает назначения | Готова к диспетчеризации |
| `ASSIGNED` | Назначен мастер | Менеджер назначил мастера |
| `TECHNICIAN_ACCEPTED` | Мастер подтвердил | Мастер принял назначение |
| `ON_THE_WAY` | Мастер выехал | Начал поездку |
| `ARRIVED` | Мастер на месте | Прибыл по адресу |
| `DIAGNOSTICS` | Диагностика | Проверка техники |
| `WAITING_ESTIMATE_APPROVAL` | Смета на согласовании | Клиенту отправлена смета |
| `IN_PROGRESS` | Ремонт выполняется | Клиент согласовал работы |
| `WAITING_PARTS` | Ожидание запчастей | Ремонт приостановлен |
| `TECHNICIAN_COMPLETED` | Отчёт мастера отправлен | Ожидает проверки менеджером |
| `CLOSED` | Закрыта | Менеджер завершил заказ |
| `CANCELLED` | Отменена | Отмена с обязательной причиной |
| `REVISIT_REQUIRED` | Требуется повторный выезд | Отдельный связанный процесс/заказ |

Статус оплаты хранится отдельно от статуса заказа. Не объединять «закрыта» и «оплачена» в один статус.

## 10.2. Допустимые переходы

- `NEW` → `MANAGER_REVIEW` или `CALLBACK_REQUIRED`.
- `WAITING_TELEGRAM_LINK` → `NEW`/`MANAGER_REVIEW` только после успешной привязки.
- `CALLBACK_REQUIRED` → `MANAGER_REVIEW` или `CANCELLED`.
- `MANAGER_REVIEW` → `WAITING_ASSIGNMENT`, `WAITING_TELEGRAM_LINK` или `CANCELLED`.
- `WAITING_ASSIGNMENT` → `ASSIGNED` или `CANCELLED`.
- `ASSIGNED` → `TECHNICIAN_ACCEPTED`, `WAITING_ASSIGNMENT` при переназначении или `CANCELLED`.
- `TECHNICIAN_ACCEPTED` → `ON_THE_WAY`, `DIAGNOSTICS` (если мастер уже на месте), `WAITING_ASSIGNMENT` при обоснованном отказе.
- `ON_THE_WAY` → `ARRIVED` или отмена/перенос с причиной.
- `ARRIVED` → `DIAGNOSTICS`.
- `DIAGNOSTICS` → `WAITING_ESTIMATE_APPROVAL`, `WAITING_PARTS` или `CANCELLED`.
- `WAITING_ESTIMATE_APPROVAL` → `IN_PROGRESS`, `WAITING_PARTS` или `CANCELLED`.
- `IN_PROGRESS` → `WAITING_PARTS` или `TECHNICIAN_COMPLETED`.
- `WAITING_PARTS` → `DIAGNOSTICS`/`IN_PROGRESS` после поступления запчастей и согласования нового визита.
- `TECHNICIAN_COMPLETED` → `CLOSED` или обратно в работу с обязательной причиной.
- `CLOSED` не переоткрывается мастером; менеджер/администратор может создать связанный повторный заказ.

Backend должен отклонять любые переходы, не перечисленные в state machine, и записывать инициатора, время, старый статус, новый статус и комментарий.

## 10.3. Отмена и неявка

Причина отмены обязательна. Различать отмену клиентом, компанией, невозможность доступа, отсутствие клиента и невозможность выполнения мастером. При необходимости предусмотреть плату за ложный вызов отдельной настраиваемой услугой, но не включать её автоматически без решения владельца.

# 11. Уведомления

## 11.1. Клиент

Через Telegram отправлять:
- заявка получена;
- назначено время и мастер (без лишних персональных данных мастера, если не разрешено);

Уведомлять о:
- новой callback-заявке;
- новой полноценной заявке;
- экспресс-заявке;

# 13. API и интеграции

## 13.1. Общие требования API

- REST API с версионированием `/api/v1`.
- OpenAPI/Swagger спецификация обязательна.
- Единый формат ошибок и валидация DTO.
- Проверка прав и входных данных на сервере.
- Пагинация, фильтры и сортировки для списков.
- Rate limiting для публичных и чувствительных endpoint.
- Idempotency для создания заявок, подтверждения смет и регистрации платежных отметок.

## 13.2. Основные группы endpoint

| Группа | Примеры операций |
|---|---|
| Public | получить категории/неисправности/публичный прайс; проверить доступные интервалы; создать callback; создать заявку |
| Telegram | webhook updates; начать привязку; подтвердить Telegram ID; принять callback-кнопку по смете |
| Auth | вход менеджера; выход; обновление сессии; профиль; проверка ролей |
| Requests | список/карточка; смена статуса; комментарии; события; отмена/перенос |
| Scheduling | график мастера; исключения; доступные интервалы; назначение/переназначение |
| Technician | мои заявки; принять; выехать; прибыл; диагностика; отправить смету/отчёт; отметить оплату |
| Pricing | каталог; создание версии цены; правила надбавок; расчёт сметы; согласование |
| Analytics | агрегированные показатели и отчёты |
| Content | редактирование контактов, FAQ и отзывов |

Frontend не должен иметь прямого доступа к PostgreSQL. Все изменения идут через backend.

## 13.3. Интеграция Telegram

- Использовать официальный Telegram Bot API через webhook с проверкой подлинности webhook-запроса.
- Секрет бота хранить только в секретах окружения/secret manager.
- Не записывать токен в логи и исходный код.
- Проверять `initData` Mini App на backend по алгоритму Telegram и контролировать `auth_date`.
- Обрабатывать повторные updates идемпотентно.
- Для привязки клиента использовать deep linking с ограниченным одноразовым токеном.

## 13.4. Авито

В первой версии только ссылки на профиль/отзывы и вручную поддерживаемый список публикаций. API-интеграцию вынести в отдельное исследование после проверки доступа, разрешений и условий Авито.

# 14. Нефункциональные требования

## 14.1. Производительность

- Публичная главная страница должна быстро открываться на мобильном интернете.

- Ошибка Telegram не должна терять заявку.
- При временной недоступности backend незавершённая форма должна показывать понятную ошибку и не сообщать о принятии, пока сервер не подтвердил запись.
- Все финансовые и статусные операции транзакционные.
- Резервное копирование БД ежедневно; рекомендуемое хранение ежедневных копий — не менее 30 дней, если владелец не утвердит иной срок.
- Регулярно проверять восстановление из резервной копии.

## 14.3. Безопасность

- HTTPS/TLS для всех внешних соединений.
- Пароли веб-пользователей хэшировать современным алгоритмом (Argon2id или эквивалент).
- Сессии защищать HttpOnly, Secure, SameSite cookies; защита от CSRF там, где применимо.
- Поддержать ограничение попыток входа и rate limiting.
- Роли проверяются на backend.
- Мастер видит только назначенные ему заказы.
- Клиент видит только свои заявки по привязанному Telegram ID и/или одноразовому безопасному токену.
- Секреты и ключи не хранить в Git.
- Персональные данные не включать в application logs, ошибки аналитики и URL.
- Файлы проверять по MIME и размеру; ограничить расширения и права доступа.
- Критичные действия писать в audit log.

## 14.4. Интерфейс и доступность

- Адаптивность начиная с узкого мобильного экрана.
- Контрастные состояния кнопок, видимый focus, подписи полей и понятные ошибки.
- Формы должны сохранять уже введённые данные при переходе между шагами.
- Не полагаться только на цвет при отображении статусов.
- В Mini App предусмотреть состояние загрузки, пустые состояния, сетевую ошибку и повтор действия.

## 14.5. Мониторинг

- Централизованные технические логи без персональных данных.
- Мониторинг доступности сайта/API/БД.
- Отдельные метрики очереди Telegram-уведомлений и ошибок webhook.
- Уведомление администратора при длительной ошибке отправки или отказе резервного копирования.

# 15. Персональные данные и правовые требования

Система обрабатывает имя, телефон, адрес выезда, Telegram ID, сведения о заказе и переписку по ремонту. До запуска владелец должен определить оператора персональных данных, цели, правовые основания и сроки хранения, подготовить политику обработки, формы согласия и процессы обработки запросов субъектов данных.

Если оператор собирает персональные данные граждан РФ в рамках действия 152-ФЗ, архитектура должна учитывать требование части 5 статьи 18 о первичной записи, систематизации, накоплении, хранении, уточнении и извлечении таких данных с использованием баз данных на территории РФ, с учётом предусмотренных законом исключений. Размещение основной БД и основного хранилища в РФ следует считать базовым требованием до отдельного юридического заключения.

Telegram является внешним сервисом. До запуска необходимо отдельно проверить правомерность передачи Telegram идентификатора, сообщений и иных данных, а также применимые требования к трансграничной передаче. С технической стороны минимизировать данные в сообщениях: не отправлять адрес и телефон в обычном уведомлении, если они могут быть показаны авторизованному сотруднику в Mini App через backend.

В формах:
- согласие на обработку персональных данных — отдельный обязательный checkbox, если это требуемое правовое основание;
- согласие на рекламу/маркетинг — отдельное необязательное согласие, не объединять с обработкой заявки;
- ссылки на политику и сведения об операторе должны быть доступны рядом с формой;
- фиксировать дату/время, версию текста согласия и источник.

**Важно:** техническое ТЗ не заменяет юридическое заключение. Перед публикацией сайта необходимо проверить актуальные требования 152-ФЗ, уведомления Роскомнадзора, локализацию, трансграничную передачу, договоры с хостингом и правила расчётов/чеков для выбранной организационно-правовой модели. Отсутствие функции печати чека в программе не означает, что у компании отсутствует обязанность его выдавать.

# 16. Приёмочное тестирование

Система считается готовой к запуску после прохождения следующих сценариев на staging-среде.

| № | Сценарий | Ожидаемый результат |
|---:|---|---|
| 1 | Клиент отправляет callback-форму | Создана заявка `CALLBACK_REQUIRED`, менеджер получил уведомление |
| 2 | Клиент оформляет подробную заявку и подключает Telegram | Telegram привязан, заявка доступна менеджеру |
| 3 | Клиент выбрал «без звонка», но не запустил бота | Заявка остаётся `WAITING_TELEGRAM_LINK`; бот не пытается написать первым |
| 4 | Клиент прикладывает фото | Файл проходит проверку и доступен только уполномоченным пользователям |
| 5 | Клиент указывает адрес вне зоны | Система показывает честное предупреждение и отправляет запрос на ручную проверку |
| 6 | Клиент выбирает занятое окно | Система не подтверждает недоступный интервал |
| 7 | Менеджер назначает мастера | Проверяется специализация, график и отсутствие пересечения; создаётся appointment |
| 8 | Два менеджера одновременно назначают мастера на одно время | Только одна конфликтующая операция может завершиться успешно |
| 9 | Мастер открывает Mini App | Backend валидирует Telegram initData и права сотрудника |
| 10 | Неавторизованный Telegram-пользователь открывает Mini App | Доступ к заявкам запрещён |
| 11 | Мастер выбирает выполненную работу | Цена подставляется из каталога; редактирование цены мастером невозможно |
| 12 | Мастер пытается ввести произвольную платную работу | Система не включает её в итог; создаётся запрос на согласование |
| 13 | Менеджер применяет скидку в пределах прав | Скидка отражается в детализации и аудите |
| 14 | Менеджер превышает лимит скидки | Операция требует полномочий администратора или отклоняется |
| 15 | Клиент не согласен со сметой | Ремонт не переходит в `IN_PROGRESS`; решение записано |
| 16 | Смета изменена после согласования | Создана новая версия; требуется повторное согласие |
| 17 | Мастер отправляет отчёт | Заявка становится `TECHNICIAN_COMPLETED`, менеджер получает уведомление |
| 18 | Мастер отмечает оплату | Фиксируются сумма, способ и статус; итоговая цена заказа не меняется |
| 19 | Сумма оплаты отличается от итога | CRM показывает расхождение и не скрывает его |
| 20 | Менеджер закрывает заказ | Заказ получает `CLOSED`, история и финансовые значения сохранены |
| 21 | Telegram API временно недоступен | Заявка сохраняется; уведомление остаётся в очереди на повтор |
| 22 | Прайс изменён после закрытия заказа | Историческая сумма закрытого заказа не меняется |
| 23 | Менеджер переносит визит | Проверяется новая доступность, сохраняется история, клиент и мастер уведомляются |
| 24 | Сотрудник деактивирован | Доступ закрыт, история ранее выполненных заказов сохранена |
| 25 | Пользователь без прав пытается открыть чужую заявку | Backend возвращает отказ; данные не раскрываются |

Дополнительно обязательны unit-тесты расчёта цен, интеграционные тесты переходов статусов, проверка прав, тестирование мобильной верстки, базовый security review и тест восстановления БД из резервной копии.

# 19. Инструкции для AI-разработчика в DSH

Этот раздел предназначен для передачи вместе с ТЗ агенту, который будет разрабатывать проект.

1. Сначала изучи ТЗ целиком. Не начинай с генерации всех файлов сайта и бота одновременно.
2. Составь технический план, структуру репозитория, схему БД, модель прав, state machine и список API. Покажи выявленные противоречия до реализации.
3. Сохраняй принятые бизнес-решения. Не заменяй Telegram Mini App личным кабинетом, не добавляй клиентскую регистрацию, онлайн-эквайринг или микросервисы без отдельного запроса.
4. Не придумывай город, цены, надбавки, расписание, юридические сведения и отзывы. Создай пустые/демонстрационные конфигурации, явно помеченные как тестовые.
5. Реализуй сначала backend-контракты и модель данных, затем CRM, публичный сайт, Telegram и Mini App. Интерфейсы должны использовать одну бизнес-логику.
6. Для каждой завершённой функции добавляй тесты: права, валидация, расчёт стоимости, переходы статусов, конкурентное назначение и обработка повторных Telegram updates.
7. Не доверяй данным, пришедшим из браузера или Mini App. Все цены, статусы, права, доступность и итоговые суммы проверяются сервером.
8. Не позволяй мастеру вводить произвольную стоимость работы. Оплата фиксируется отдельно от цены заказа.
9. Делай небольшие законченные этапы. После каждого этапа запускай тесты, линтер, typecheck и проверку сборки; не продолжай при критических ошибках.
10. Не переписывай рабочие модули целиком ради косметических улучшений. Сначала изучай существующую структуру, сохраняй обратную совместимость и делай минимальные осмысленные изменения.
11. Перед изменением схемы БД создавай миграцию. Не удаляй данные и не выполняй destructive migration без резервной копии и явного согласования.
12. Веди `README.md`, `CHANGELOG.md` и файл решений `docs/DECISIONS.md`. Фиксируй команды запуска и проверки.
13. В конце каждого этапа предоставляй: что реализовано, какие файлы изменены, какие тесты пройдены, какие ограничения остались и как проверить результат вручную.
14. Не заявляй, что функция готова, если она только нарисована в интерфейсе или использует временные mock-данные. Все интерактивные элементы должны быть подключены к реальному backend либо явно помечены как прототип.
15. Не помещай реальные персональные данные в тестовые фикстуры и логи. Используй вымышленные данные.

3. Telegram Bot Features / Deep Linking: https://core.telegram.org/bots/features. Использовать deep link с параметром для безопасной привязки пользователя к заявке.
