# P03-04D synthetic copy-only restore drill

This is a local, explicitly opted-in drill, not a backup schedule, disaster recovery procedure, production cutover, or evidence of production storage erasure. All inputs must be synthetic. No HTTP/bootstrap, automatic enablement, or live policy is provided.

Prerequisites: running pinned local PostgreSQL 18.7 and Garage 2.5.0, the separate [ledger and floor services](<../file-ledger/README.md>), ignored local fixture credentials, and frozen workspace dependencies. From the repository root:

```powershell
$env:FIXLEVELUP_BOOTSTRAP_ISOLATED_DB_TESTS='1'
$env:FIXLEVELUP_STORAGE_S3_TESTS='1'
$env:FIXLEVELUP_FILE_RESTORE_TESTS='1'
corepack pnpm exec vitest run apps/api/tests/file-restore.test.ts
```

The fixture creates its own source and destination PostgreSQL databases and two fresh private Garage buckets with distinct credentials, using the pinned local service containers. It does not modify the working database, old buckets, old roles, images, networks, or volumes. Access to the new source is revoked only for that fixture database. Databases, buckets, keys, dumps, copies of the dumps in the PostgreSQL container, and the ignored synthetic artifacts are intentionally retained. No deletion, drop, restore into an existing database, or trigger disablement is attempted. Docker administrators can see key-import arguments; do not print diagnostics, archives, connection settings, or key material. Artifacts are not encrypted and must contain no real data.

1. Before new authority changes, take a custom PostgreSQL dump omitting the runtime epoch row and export the bounded, verified exact registry objects. Sign the bound dump hash, schema revision, complete inventory, original and destination identities, and old ledger head. No ordinary application process can open the destination yet.
2. Record later holds, withdrawal and an unresolved deletion decision. Fence the source runtime, stop its broker and file storage adapter, demonstrate refusal of an old read ticket, and drain exact pending decisions using the ledger-only reconciler. Revoke database CONNECT from the source application role, end the fixture pool, prove reconnection fails and no application writer remains, then fence old ledger writer authority. Only the trusted fixture migrator remains; the drill assumes control of that operator and of every old executor. A remotely sent PUT remains debt, not cancelled by local shutdown.
3. Sign a fresh challenge-bound current authority record. It binds the authoritative overlay dump and exact source rows (current legal documents, versions, sessions, consent, intent cancellation, holds/decision and associated history). A new empty database receives old pre-data schema, old non-overlay data, exact current overlay data, and old post-data constraints/guards; initialize `RESTORE_CLOSED` while runtime `CONNECT` is withheld. Existing immutable registry targets are never rewritten.
4. Verify the real independently pinned ledger lineage and full current authority against restored rows. Match every old inventory key one-to-one; suppress all tombstoned objects before PUT, preserve unresolved charges, and use exclusive fresh bucket credentials plus an exact conditional new-key PUT and full digest-checked readback for survivors. Check a separate signed approval, check fresh current authority and ledger again, CAS the new epoch active, then allow runtime `CONNECT` only after the confirmed response. The only installed aliases are scoped to the exact copied registry tuple. The restore receipt is required by target retention and DELETE wiring, and source credentials/coordinates are rejected even if they are valid. Skipped historical tombstones get no physical-delete alias.
5. Demonstrate actual F metadata and bounded streaming of exact unaffected bytes, durable post-backup hold protection with real retention planning, refusal of old withdrawn proof and tombstoned descendants, and unchanged unresolved debt. Release one hold through the new authorized primary, append at the new ledger writer epoch, and confirm two exact Garage deletions exclusively against the new copies; the matching original objects still pass their digest checks. An established old ledger principal cannot append even when it supplies the new epoch and a fresh event ID. The restore fixture seeds a synthetic published tuple; actual engine correctness belongs to the separate C engine suite, and signed replay/rollback/fork/floor-loss checks belong to the separate durable ledger suite.

The reopened ACTIVE epoch 2+ is a read/delete-only profile for copied objects, not new raw or sanitized writes. A valid new no-byte reservation is allowed; new/existing raw B commands and unprocessed/published C commands return `NOT_CONFIGURED` without invoking the body factory or iterator, raw GET, worker, evidence writes or sanitized PUT. The real restore regression verifies the exact DB digest and both bucket lists remain unchanged, and still exercises copied READY streaming and hold release/copied DELETE under current authority. See [current integration evidence](<../../docs/P03-04CDE-CONTRACT.md#6-current-status-and-evidence>).

Ignored host directory `backups/p0304-file-restore-*` contains the signed manifest, old and current dumps, object artifacts, filtered TOC, and aggregate evidence only after success. A failed run does not reuse these resources; inspect the fixed stage and use a new run if authorized. Do not grant destination `CONNECT` on an uncertain activation response. No production retention, authentication handoff, RPO/RTO, cloud storage or multi-writer guarantee is implied.
