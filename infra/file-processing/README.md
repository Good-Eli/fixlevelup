# Local synthetic file-engine fixture

This is test infrastructure, not API/bootstrap wiring. It accepts only synthetic bytes. No public route, repository credential or Docker socket is mounted in either worker. The [OCI/native security report](<OCI-REMEDIATION.md>) records the scoped Astra PASS for the exact audited scanner/decoder offline entrypoints only. This is not zero-CVE, production or distribution approval and does not cover arbitrary Node or the separate FreshClam network updater. A successful antivirus result is not an OCI gate.

## Reproduce the isolated run

- Use the exact workspace toolchain, Node `24.22.3` / pnpm `12.21.0`; `corepack pnpm install --frozen-lockfile --ignore-scripts --strict-peer-dependencies`. For dependency evidence run the [existing gate](<../ci/DEPENDENCIES.md>) with a new exclusive output under `node_modules/.cache/p0304cde/`. No advisories or license review exceptions are defined here.
- Pull only the approved upstream ClamAV `1.4.7_base@sha256:21622d96b8a7080af7974d99ca60a9e061eff5ff831ed6986d00953fc19ff67f`, platform `linux/amd64` manifest `c2cc3f37cb7c93833441e0c439461649f8ea3c7d16eb94cd7296f123286504c5`. Use upstream `freshclam` directly (not `/init`) in a new named container, with the [one-shot config](<freshclam.conf>) mounted readonly and a new empty cache directory mounted as `/defs`; non-root `65534:65534`, cap-drop ALL, no-new-privileges, read-only root, restricted tmpfs/CPU/memory/pids, no port/socket or repository mount. Its only intended destinations are official signature mirror `database.clamav.net` and version lookup `current.cvd.clamav.net`; restrict egress in the environment before real deployment (a local Docker bridge alone is **not** an enforceable DNS/domain firewall). No update process is run in a scanner container.
- Copy only `main.cvd`, `daily.cvd`, `bytecode.cvd` into a new directory inside the ignored cache; keep the update directory separate. Verify each with upstream `sigtool --info`, including `Verification OK.`, retain hashes and the daily version/build date, then never mutate the snapshot; mount it readonly. The launcher checks the signed-file set's canonical digest (`sha256` of sorted `filename + TAB + decimal length + TAB + lowercase hex SHA-256 + LF`), platform image pin and exact observed `clamscan --version` daily epoch. Hashes are checked before and after scan. The fixture assumes its trusted host cache is not concurrently modified by another privileged process; RO bind mounts protect against the worker, not a privileged host writer.
- Build the [current scanner recipe](<ClamAV-libcrypto.Dockerfile>) with `docker build --platform linux/amd64 --load -f infra/file-processing/ClamAV-libcrypto.Dockerfile <new-input-only-directory>`. The directory contains the signed [exact Alpine APK](https://dl-cdn.alpinelinux.org/alpine/v3.24/main/x86_64/libxml2-2.13.9-r3.apk), the official OpenSSL 3.5.9 release tarball (verify its detached signature against the canonical fingerprint), the five upstream patch downloads and the [pinned digest manifest](<openssl-inputs.sha256>). Configure/build/test runs offline after Alpine compiler/tool setup; the historical [XML-only recipe](<ClamAV-libxml2.Dockerfile>) is not the current engine. The [decoder recipe](<Dockerfile>) is built from the repo root with `docker build --platform linux/amd64 --load -f infra/file-processing/Dockerfile .`. It compiles three modules offline after the pinned frozen install and uses a separate scratch runtime containing only Node, Sharp, the decoder code and their dynamic libraries.
- Store the exact tested scanner index/platform and decoder index separately from mutable tags. The [launcher](<docker-test-launcher.mjs>) and application epoch allow only the reviewed scanner image identity; a rebuild producing a new OCI identity needs an explicit pin update, independent inspection and fresh preflight rather than automatic trust. Set `FIXLEVELUP_FILE_PROCESSING_FIXTURE` explicitly to an ignored, local-only descriptor JSON for real opt-ins. Required descriptor keys are `snapshotDir`, `epoch` (`engineVersion`, hex `engineImageSha256`, hex `defsSha256`, ISO `defsBuiltAt`), `decoderImage` (`sha256:` OCI index ID), `scanner` and `decoder`. Both limits require explicit `cpuMilli`, `memoryMiB`, `pids`, `tmpfsMiB`, `wallMs`; scanner additionally requires `maxFileBytes`, `maxScanBytes`, `maxFiles`, `maxRecursion`, `dailyRevision`. No production thresholds are assigned. Example synthetic engine bounds observed successful: scanner `1000,1200,32,32,45000`, scanner bytes `1048576,8388608`, limits `64,8`; decoder `1000,512,32,32,10000`. Actual scan setup/compile costs ~18–30 s/container; two independent scans require a longer coordinator deadline than a single scanner wall deadline.
- Run `node infra/file-processing/preflight.mjs <descriptor>` from repo root. This re-encodes synthetic JPEG, PNG and WebP samples with EXIF via the real native decoder, proves metadata was removed and requires a full, separate pinned ClamAV invocation for original and transformed bytes. It runs the well-known harmless EICAR test separately; no malware material is stored or processed.

E exercises an already verified, read-only offline snapshot. FreshClam above is separate provisioning evidence; it is not part of processing, READY, or the E runtime. The updater does not inherit scanner security or isolation approval. The audited decoder OCI index and amd64 manifest are both checked before any container starts; the later scanner-epoch constant change in the host source does not affect the decoder, which does not consume that export.

The fixture creates a fresh named container per call, using fixed argv, no TTY or interactive shell, local engine only, no app credentials, no logging driver, `--network none`, non-root UID/GID, cap drop, no-new-privileges, read-only FS and bounded memory/swap, CPU, pids and tmpfs. Decoder sees no definitions, no scanner output and no app authority. Linux cgroups provide resource ceilings. Each Docker metadata/create/inspect/kill call has a 2.5 s control ceiling and at most 250 ms CLI exit grace; attached byte IO uses the absolute per-worker wall starting before create. Abort, timeout or output overflow stop the local CLI; this alone does not prove sandbox exit. Cleanup attempts a single bounded kill and a bounded exit inspection, in sequence. Unknown settlement produces a fixed error and does not free the slot. In a real deployment this needs an independent watchdog and controlled/attested engine; loss of the local host process/daemon is not equivalent to verified sandbox termination. Local proof containers and evidence are intentionally retained; no resource or data deletion is performed by these fixtures.

ClamAV's own time-limit help explicitly permits skipped/assumed-clean input. `--max-scantime=0` disables that internal skip; the external watchdog is mandatory. Outer code refuses zero-byte input (pinned bare CLI returned `stdin: OK` for it), caps exact stdin before scanning, requires exact result bytes plus both EOFs and validated exit, and rejects indicated limits/errors. An oversize probe actually elicited `Heuristics.Limits.Exceeded.MaxFileSize` (not CLEAN). Named signatures and child stderr are never application outputs.
