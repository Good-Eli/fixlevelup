# FixLevelUp — постоянный протокол локальных коммитов

Протокол установлен владельцем в P01-01.8A и действует для всего репозитория.
Прямые последующие указания владельца имеют приоритет.

## Когда создавать коммит

- После каждого успешно завершённого и принятого пользователем подэтапа
  самостоятельно создавать один логический локальный коммит.
- Принятие подэтапа пользователем — достаточное разрешение на этот коммит;
  дополнительное подтверждение самого коммита не требуется.
- Собственный отчёт GPT о готовности не заменяет приёмку пользователя.
- Приёмка не разрешает автоматически начинать следующий подэтап.
- Не создавать фиктивные коммиты за прошлые подэтапы.

## Проверки до коммита

1. Убедиться, что работа завершена в согласованном scope и пользователь её принял.
2. Проверить фактические результаты тестов и сборок, предусмотренных подэтапом.
   Невыполненные или неуспешные проверки не объявлять успешными.
3. Проверить текущую ветку, `git status`, staged, unstaged и untracked файлы,
   `git diff`, `git diff --cached` и точный список будущего коммита.
4. Проверить отсутствие секретов, локальных данных, временных результатов,
   caches, generated artifacts и изменений вне согласованного scope.
5. Сравнить staged и рабочие версии изменённых файлов. В коммит должны попасть
   проверенные актуальные версии; прежний index не считать автоматически верным.
6. Проверить правила исключения и выполнить `git diff --check`, затем
   `git diff --cached --check` для подготовленного коммита.
7. Добавлять только согласованные файлы явными путями. Не использовать
   `git add .` или `git add -A`; не включать посторонние изменения пользователя.
8. Повторно проверить staged diff и список файлов непосредственно перед коммитом.

Если тесты не прошли, работа не завершена, обнаружены секреты, посторонние
изменения, неоднозначный состав или нарушение scope — коммит не создавать.
Сохранить рабочее состояние и доложить пользователю; ничего не удалять
и не исправлять вне согласованного scope.

## После коммита

- Проверить SHA, сообщение и полный состав созданного коммита.
- Повторно проверить `git status`, оба diff и чистоту рабочего дерева.
- Если остались чужие изменения или локальные файлы, сохранить их и явно
  отразить в отчёте; не добиваться чистоты удалением или сбросом данных.
- Сообщить SHA, состав, результаты проверок и ограничения.

## Постоянные запреты

Без отдельного прямого разрешения владельца запрещены push, изменение remote,
Git identity или Git settings, переключение веток, переписывание истории,
rebase, amend, force push и удаление локальных данных.
`git reset --hard` и `git clean` не использовать. Не выполнять массовое
восстановление файлов и не терять staged, unstaged или untracked изменения.
Не включать `.env`, секреты, локальные БД, дампы и build artifacts.

## Очистка Docker после проверок

Владелец поручил 22.11.2026: останавливать и удалять больше не нужные тестовые
контейнеры Docker. Перед удалением подтвердить их принадлежность проверкам,
сохранить необходимые результаты и убедиться, что контейнер не используется
активной задачей. Удалять адресно по проверенным именам/ID, без массового prune.
Не прерывать текущие проверки и рабочие сервисы. Это разрешение не включает
удаление томов с данными, образов или чужих контейнеров; `docker rm -v`,
`docker volume prune` и `docker system prune` без отдельного разрешения не применять.

## Как экономить бюджет владельца

Самостоятельные части задачи поручать субагентам, не дублируя уже проверенную
работу. Выбирать из доступных в текущей сессии моделей Codex с учётом расхода
лимита и сложности задачи. Использовать минимальный достаточный уровень
рассуждения. Внешние тарифы, включая PlusVibe, при выборе не учитывать.
В сессии указывать выбранную модель, уровень и причину выбора. Передавать только
необходимый контекст и запрашивать краткий результат.

## Обязательный блок в каждом ответе об актуализации

Владелец потребовал 21.11.2026: в **каждом** ответе на запрос актуализации
статуса (roadmap, subtasks, changelog, README, «актуализируй», «общий статус»)
обязательно выводить блок **«Прогресс по этапам»** — ASCII-диаграмму
с процентами по всем этапам P00…P15.

Формат сохраняется дословно: имя этапа, полоса из `█` и `░`, процент справа,
пояснение в скобках. Блок не сокращать до таблицы и не заменять текстом.
Он выводится даже когда запрос касается только одного файла или одного этапа.

## Адресное решение для начального baseline

В P01-01.8A владелец отдельно разрешил включить существующий актуальный
`apps/web/next-env.d.ts` и потребовал сохранить `.gitignore` без изменений.
Это исключение для данного baseline, а не общее разрешение коммитить generated
artifacts. Остальные generated outputs, зависимости и локальные credentials
в baseline не включаются. Документы R3.2 сохраняются в текущих рабочих версиях
как проектный snapshot, без обновления исторических записей о ходе реализации.
