# Доступ сотрудников FixLevelUp

**Область:** сотрудники одной компании. Один сотрудник имеет ровно одну текущую роль. Нет наследования, клиентских ролей, произвольных персональных grants и пользовательского SQL/API для изменения каталога. Отдельные исторически привязанные bootstrap-источники P03-02 и P03-05 — не персональный редактор grants. Страница CRM — `/crm/access`, запросы — в Nest на том же HTTPS origin. Публикация в production и реальная привязка Telegram не входят в этот контракт.

**Границы P02 (решение владельца 20.11.2026):** контракт описывает только staff-авторизацию; customer request grants в `P02` не входят — их модель, выдача и отзыв реализуются в `P05`/`P07-core` вместе с Q03/Q17 до первого защищённого клиентского действия. Telegram-вход мастера работает только по заранее существующей активной связи `staff_telegram_links`; потока первичной привязки Telegram к нужному сотруднику нет, поэтому реальный Telegram-вход не используется до его появления. Это ограничение объёма, а не security/production approval и не одобрение коммита.

## Кто и что может делать

Стартовые назначения создаёт миграция. Таблица — начальные **данные**, а не зашитое в guard разрешение по должности.

| Действия | Scope | TECHNICIAN | MANAGER | ADMIN |
|---|---|---|---|---|
| `staff.self.read`, `staff.self.update`, `staff.self.deactivate` | SELF | Свой профиль | Свой профиль | Свой профиль, кроме деактивации последнего ADMIN |
| `staff.read`, `staff.create`, `staff.update`, `staff.deactivate` | GLOBAL | Нет | Только сотрудники с **системной** ролью TECHNICIAN | Да, с ограничениями назначения, SELF и последнего ADMIN |
| `roles.read` | GLOBAL | Нет | Нет | Да |
| `roles.create`, `roles.update`, `roles.archive`, `roles.permissions.manage`, `staff.role.assign` | GLOBAL | Нет | Нет | Обязательные защищённые |

CUSTOM создаётся пустой. Ей и системным ролям можно явно включать обычные действия. `staff.create` — создание карточки, не логина или Telegram-связи. Без `staff.role.assign` начальная роль ограничена TECHNICIAN; нельзя создать оператора с более широкими общими правами, чем у создателя. Пользовательские и прочие неадминистративные роли с общим staff-действием также ограничены целями SYSTEM TECHNICIAN. Имя «Администратор» у пользовательской роли ничего не разрешает: идентичность определяется типом и внутренним кодом. Системный код, тип, имя и статус не меняются.

`SELF` привязан к `staffId` **проверенной сервером сессии**, не к полю из запроса. Для self-операций свой UUID вводить не нужно. Общая команда изменения сотрудника не заменяет SELF-команду. `GLOBAL` снимает географическую границу, но не отменяет право на действие, ограничение на тип цели или активность. В P02 `CITY` не выдавался. В [P03-02](P03-02-ACCESS.md) он относится только к пяти географическим операциям. Для доступа нужны явное право роли и отдельное административное назначение сотрудника в город ресурса; для управления мастерами их рабочие допуски не заменяют административное назначение. Нет неявного добавления прав: например, право менять роль не даёт список сотрудников. Состав сотрудников роли требует также `staff.read`; без него счётчики не выдаются.

## Хранение и атомарность

- `foundation.permissions` — каталог (код, модуль, описание, `protected`, `active`); runtime только читает его. Для допуска нужны активный код, известный серверный контракт и фактически включённый `role_permissions` с допустимым scope. Неизвестные коды закрыты.
- `roles` хранит UUID, стабильный уникальный код, сведения, тип/статус, версию, даты и автора. `role_permissions` уникален по роли и коду. Изменение набора — атомарный diff; выключение обновляет `enabled`, а не удаляет историю из аудита. Архивную роль не редактируют и не назначают.
- `staff_role_assignments` сохраняет ранее назначенные роли с датами и субъектами назначения/отзыва. Частичный уникальный индекс допускает не более одного текущего назначения; отложенная проверка запрещает сотрудника без допустимой роли при COMMIT. Назначение SELF, неактивному сотруднику, неактивной роли и архивирование роли активного сотрудника запрещены. Исторические записи и сотрудники не удаляются.
- `staff.role` сохраняет контракт **канальной аутентификации** P02. Он не является вторым источником полномочий. Системное назначение синхронизирует маркер канала; при назначении CUSTOM сохраняется прежний способ входа (TG остаётся TECHNICIAN, CRM остаётся MANAGER). Никому не создаются credentials/links автоматически. Назначение ADMIN требует существующего web credential.
- Имя в профиле (`display_name`, до 80 символов) редактируется отдельно от роли, состояния и credential. Версия карточки — монотонная сумма `profile_version` и `auth_version`. Правка имени не отзывает сессию; смена роли, деактивация и recovery делают прежний `auth_version` невалидным.

**Одна блокировка для административного инварианта.** В `READ COMMITTED` все RBAC-записи берут `pg_advisory_xact_lock(hashtextextended('fixlevelup:admin-invariant',0))` до строк субъекта, связи, сессии и цели. Защищённое чтение использует shared-вариант той же блокировки. Проверка точной сессии, текущих полномочий и объекта, ETag, изменение и аудит используют один `PoolClient`, до COMMIT. После ожидания последующий SQL видит уже зафиксированные назначения/деактивацию, а не устаревший снимок. Запись, зафиксированная до отзыва, остаётся; более поздняя не наследует старый доступ. Блокировки хранятся в PostgreSQL, не в памяти процесса. Это сознательный выбор в пользу доказуемого порядка, а не высокой параллельности административных записей.

Отдельный `COUNT` двух оставшихся администраторов в разных транзакциях не защищал P02-06. Теперь MANAGER в принципе не видит ADMIN как допустимую цель. Даже два уполномоченных ADMIN не могут совместно деактивировать/понизить последнего: под общей блокировкой должен остаться ACTIVE SYSTEM ADMIN с web credential и обязательными правами. PostgreSQL дополнительно защищает системные роли/защищённые связи, архивирование и текущее назначение. Runtime не может изменять каталог, удалять/обнулять таблицы или выполнять DDL. Добавленные trigger-функции — `SECURITY INVOKER` с фиксированным `search_path`, а не универсальный привилегированный сервис. Владелец БД/DDL остаётся доверенной стороной.

Права не кэшируются в сессии. Токен CRM не принимается как Telegram bearer и наоборот. Для TG повторно проверяются конкретная строка связи, активность и версия; старый `initData` в grace-окне не оживляет сессию старой версии. Действующие параметры P02: web idle 30 минут / absolute 12 часов, TG idle 2 часа / absolute 24 часа; grace 60 секунд не продлевает TTL.

## HTTP API

Все пути относительно `/api/v1`. Успех — `{data,meta:{requestId}}`; список в `data` — `{items,pageInfo:{hasMore,nextCursor}}`. Данные и ошибки — `no-store`. Ошибка — безопасный `application/problem+json`, без значений входных полей. Для cookie-мутаций нужны точный Origin, JSON и session-bound `X-CSRF-Token` из `/auth/me` (`X-Auth-Request: 1`) или `/auth/login`. TG-маршруты не используют cookie. Для изменения существующего объекта нужен **сильный** `If-Match` из карточки: `"staff-vN"` либо `"role-vN"`. Нет заголовка → 428, неверный формат → 400, устаревшая версия → 412. Невалидная сессия → 401, нет права → 403, недоступная чужая цель → 404, конфликт состояния/блокировки → 409. После конфликта UI перечитывает права/объект; автоматического повтора записи нет.

| Метод и путь | Проверка | Тело / результат |
|---|---|---|
| GET `/access` | Собственная CRM-сессия | Только `staffId`, `{id,code,type}` текущей роли и действующие коды permissions для UI |
| GET `/staff`, GET `/staff/{id}` | `staff.read` + цель | Список / карточка; никаких credentials и внешних идентификаторов |
| POST `/staff` | `staff.create` + контроль допустимой начальной роли | `{role:"TECHNICIAN"\|"MANAGER",displayName?}`; 201. Неидемпотентное создание, не повторять вслепую |
| PATCH `/staff/{id}` | `staff.update` + цель | `{displayName}`; только это поле |
| POST `/staff/{id}/deactivate` | `staff.deactivate` + цель | `{}`; статус и auth_version меняются вместе |
| PUT `/staff/{id}/role` | `staff.role.assign` | `{roleId}`; старое назначение закрывается, новое открывается |
| GET / PATCH `/staff/self`, POST `/staff/self/deactivate` | Соответствующее `staff.self.*` и владелец | Собственная карточка / `{displayName}` / `{}`; TG self: `/telegram/staff/self` |
| GET `/roles`, GET `/roles/{id}`, GET `/permissions` | `roles.read` | Роли с разрешениями и доступными счётчиками; каталог сгруппирован по `module` |
| GET `/roles/{id}/staff` | `roles.read` **и** `staff.read` | Только доступные текущие сотрудники роли |
| POST `/roles` | `roles.create` | `{name,description}`; 201, сервер формирует код/тип, набор прав пуст |
| PATCH `/roles/{id}` | `roles.update` | `{name?,description?}`, хотя бы одно поле, только active CUSTOM |
| PUT `/roles/{id}/permissions` | `roles.permissions.manage` | `{permissions:[{code,scope}]}` — весь желаемый набор. Повторы, неизвестные коды, неподдержанные scope и скрытое снятие защищённых прав запрещены |
| POST `/roles/{id}/archive` | `roles.archive` | `{}`; только CUSTOM без активных назначенных сотрудников |

В Mini App используются отдельные маршруты `/telegram/staff` (те же операции по тем же правам) и `/telegram/roles`, `/telegram/permissions` (только чтение). Сервер принимает здесь только Telegram bearer; `roles.read` и общие staff-права по умолчанию у мастера отсутствуют. Защищённые права никогда не выдаются роли TG-сотрудника.

ETag защищает **версию редактируемого объекта**, а не все связанные проекции: переименование роли не меняет версию карточки сотрудника; изменение числа назначенных сотрудников не является редактированием полей роли. Число в подтверждении — видимая область на момент чтения. Перед записью состав для запрета архива и права проверяются заново под блокировкой. Изменения возвращают новую версию. Участник с правом записи, но без независимого чтения получает подтверждение, а не обход запрета через write response. Нельзя назначать роли самому себе. Назначения/редактор не могут использоваться для нового общего права сверх полномочий субъекта. Обязательные защищённые permissions только у SYSTEM ADMIN — их нельзя снять, передать или заменить. При удалении у собственной системной роли обычного права восстановить его выдачей самому себе нельзя. Для проработки изменений административной матрицы используйте изолированную копию; операторское восстановление политики требует отдельного контролируемого решения, не открытого endpoint.

## P03-05: staff management в закрытом synthetic контуре

Владелец принял P03-05 22.11.2026 в synthetic scope после PASS Astra Gate 1/2. Отдельный полный аудит Astra P03-01…P03-05 — PASS ([отчёт](P03-AUDIT.md)); реальные grants и production не разрешены.

[Контракт P03-05](P03-05-CONTRACT.md) фиксирует точную матрицу 18 новых активных необязательных (`protected=false`) кодов с явными правилами делегирования и routes; наличие кода само по себе не даёт права. Допустимые CITY-коды: прежние пять geography, два callback (`read/manage`) и три content (`read/manage/publish`). Одновременно требуются действующее admin-city assignment и пересечение scope всех необходимых разрешений на одной цели, не объединение областей. TECHNICIAN/CUSTOM-TG — ноль effective P03 grants; CUSTOM-web с MANAGER marker следует manager-матрице по явным grants. SYSTEM ADMIN GLOBAL с matching read/manage — единственный путь к full company/legal; `settings.readiness.read` GLOBAL у A/M/CUSTOM-web не даёт глобальной территории и не раскрывает policy refs, документы или чужой primary.

При новом role grant, расширении scope, создании staff с ролью или назначении готовой роли субъект должен иметь собственный действующий GLOBAL **того же кода**; для нового административного города при `adminAssign` — GLOBAL каждого CITY-кода P03-05, территория которого действительно расширится. Проверки выполняются под общей RBAC-блокировкой; точно сохранённый grant не новая выдача, отзыв города не требует расширяющих grants. CITY и GLOBAL grants роли действуют на **всех текущих и будущих членов роли** в пределах scope/условий, не на одного выбранного сотрудника; интерфейс предупреждает до подтверждения.

Выбранный владельцем A — одноразовый личный источник 18 GLOBAL-кодов у исходного bootstrap-assignment, не гранты роли. Не выдаётся снова после login/recovery/reassign или replay миграции; отзыв источника не затрагивает независимо делегированный grant роли. Active source view/revoke требует SYSTEM ADMIN, `roles.permissions.manage` и свой GLOBAL точного кода; отзыв необратим. Management read/write/replay проверяют свежие DB-часы после последнего ожидания; запрос не получает старую квитанцию или конфликт до проверки authority по реальной исходной цели/типу. Только bootstrap mismatch — фиксированный 404 после проверки запрошенного кода. Staff aggregate `0` и первая команда staff geography с `geo-v0` не являются нулевой management receipt version.

## Переход с P02

Миграции 001–008 сохраняют историю. Перед 009 остановить писателей старой версии и сделать проверяемый backup; **не** развертывать старый и новый authz параллельно. Сначала репетиция и проверка доступа на изолированной копии. Таблицы сотрудников, web credentials, история web/TG сессий и Telegram-связей не пересоздаются. Неподдерживаемый логин или формат Argon2id блокирует перенос без вывода его значения: неспособный войти сотрудник не может считаться резервным ADMIN. Проверка формата не доказывает, что человек знает пароль. В одной транзакции создаются каталог/матрица и назначения, увеличивается `auth_version` у существующих сотрудников и отзываются прежние runtime-привилегии на `user_permissions`. Старый backend после cutover не может читать grants, новый никогда к ним не обращается.

| Исходные данные | Назначение при переходе |
|---|---|
| Пустая БД | Только каталог и три роли. Аккаунт и пароль не создаются. Первый оператор — отдельно через защищённый bootstrap |
| Непустая БД | Требуется достоверный singleton bootstrap marker → ACTIVE ADMIN с web credential. Если его нет, 009 останавливается, не выбирая администратора по имени/порядку строк |
| Сотрудник из проверенного marker | SYSTEM ADMIN с утверждённой матрицей |
| Старый TECHNICIAN | SYSTEM TECHNICIAN с явными SELF-полномочиями; TG link сохраняется |
| Остальные старые MANAGER/ADMIN | До четырёх общих CUSTOM-профилей по **фактическим** бессрочным действующим GLOBAL grants. `staff.read` → `staff.read`; `staff.manage` → `staff.create` и `staff.deactivate` в пределах системных мастеров. `staff.update`, назначения ролей и новые административные права не добавляются |

Неизвестные, отозванные, ещё не действующие и срочные grants не становятся постоянными: они остаются в исторической таблице у владельца схемы. До перехода сверить их с владельцем политики и запланировать явные назначения. После — повторный вход и проверка ролей/каналов, актуальных прав, audit и readiness. Если bootstrap root уже заменён/уволен — требуется отдельная доверенная сверка и план перехода; нельзя превращать проверку в автоматическое повышение любого старого ADMIN. Перекатывать один лишь старый бинарник назад нельзя: он ожидает запрещённые legacy grants.

## Аудит и развитие

Аудит событий создаётся в транзакции с записью. Для назначения — actor/target и прежняя/новая роль; для редактора — безопасный diff кодов и scope, версии; для архивирования — статус и версия. При правке свободного текста сохраняется факт изменения/версия, а не имя сотрудника или содержимое описания. Cutover фиксируется с системным актором. Bootstrap и recovery имеют собственные события P02. Успех без записи AuditLog невозможен. Обычные отклонённые запросы не создают per-request строк в бизнес-аудите: это не журнал всех попыток входа и не неограниченный канал записи от клиента.

Новый модуль добавляет **вместе** код с описанием в каталог миграцией, типизированный контракт и scope в [серверном словаре](../apps/api/src/authz/capability.ts), реальную серверную операцию и отрицательные/положительные тесты. Обновить readiness/constraint/ACL и UI-проекцию по необходимости. Новый каталог сам по себе не назначает разрешение. Для `CITY` уже действуют отдельное административное назначение сотрудника, проверка города объекта и серверная фильтрация списков ([география P03-02](P03-02-ACCESS.md), [дополнения P03-05](P03-05-CONTRACT.md)); одного `cityId` клиента недостаточно. При расширении матрицы нужны транзакционные тесты.

**Открытые gates:** ручная проверка bootstrap/recovery в настоящем TTY обязательна **до первого реального использования**; non-TTY и pseudo-TTY тесты её не заменяют. Списки рассчитаны на небольшую мастерскую P02 и сейчас возвращаются целиком; перед ростом численности нужны cursor pagination и нагрузочная проверка времени удержания policy lock. Нет инструмента первичного выпуска web credentials или установления Telegram-связи для новых сотрудников: без безопасного intended-employee proof реальный Telegram-вход не используется, а критерий приёмки `P02-05` ограничен обменом по заранее существующей активной связи. Customer request grants в `P02` не реализуются. Нет живого Telegram E2E, доверенного production reverse proxy/HTTPS и согласования обработки реальных ПД/152-ФЗ. Ни тестовые БД, ни browser fixtures не подтверждают эти условия. В рамках P03-02 действует отдельный [контракт территориальных прав](P03-02-ACCESS.md); он не закрывает перечисленные эксплуатационные условия.
