## 3. Снимки, криптография и внутренний доступ к ПД

- `requests.city_id/intake_city_version_id` NOT NULL и неизменяемы даже у callback. Исторические city/address/area/district/timezone/labels выбираются из справочников и хранят provenance каждой ревизии; свободный ввод не попадает в открытые snapshots. Текущие pointers имеют composite FK к **своему** request/revision/city, immutable history не переписывается. Snapshots контакта, адреса и appliance связаны с точными sources; `request_faults` (ревизия техники + fault ID/version + category match) — единственный набор выбранных симптомов. Переиспользуется [реальная typed схема справочников 019](P04-01-CONTRACT.md) и [точное чтение immutable revision](../apps/api/src/catalog/reads.ts#L115-L139); для нового выбора — active/current parents под P04 fence, не marketing/price data. CITY-only callback interval использует [типизированное разрешение P03](../apps/api/src/settings/configuration/references.ts#L410-L475) и exact timezone provenance; source и cancel reason — действующие типизированные COMPANY reference revisions, не разрешения. Срочность и предпочтение времени — только предпочтение, без цены, SLA или брони; неявный timezone/геокодер/ставка запрещены.
- Точный профиль обработки фиксируется отдельно от правил статуса и `row_version`: immutable `workflow_version` (`wf-r2-p05-v1` как первый технический идентификатор) и immutable `intake_policy_revision_id` с FK на reviewed metadata/hash режима (без ключей/реальных сроков в миграции), purpose/evidence/admission versions. Связи источников сохраняют exact revision. Внутренний набор поддерживаемых пакетов выбирается **по сохранённой паре**, не «last version». Неподдерживаемая версия → safe `503 REQUEST_RULES_UNAVAILABLE`, без нового эффекта; устаревший ETag для поддерживаемого пакета → `412`; historical package не подменяется новым. Помимо pinned business semantics обязательны актуальные authority, expiry/revocations и kill switch; прежняя версия не обходится в устаревший security путь. Штатная первая migration пустая в data части, версии и условия явно provisioned тестовым stand, не runtime seed. Сравнение historical vs current policy выполняется на двух явно версионированных тестовых пакетах, не выдуманной второй боевой политике.
- **Угрозы:** прочтение БД/дампов/реплик, утечка диагностик, перебор fingerprint по известному телефону и перестановка ciphertext; не обещаем защиту от полного захвата процесса с ключами. Имя, нормализованный телефон, точный адрес/доступ, описание/ошибка/комментарий и произвольный ввод — только versioned ciphertext. Node crypto AES‑256‑GCM с отдельным случайным DEK на payload, 96-bit nonce и полной меткой; wrapping под versioned KEK отдельным AEAD доменом, уникальность nonce под KEK обеспечивается случайным nonce с ограничением объёма на ключ и документированной границей ротации. AAD: environment/schema/purpose, UUID и immutable revision, role payload vs wrapping; никаких implicit fallback/mixed key purposes. Idempotency HMAC‑SHA‑256 имеет свой versioned key и domain prefix; CSRF/лимиты — иные ключи; квитанция из доверенной БД **не подписывается** и не credential, второй receipt HMAC не нужен. Exact HMAC сравнивается constant time по `key_id` сохранённой строки. New writes — активный key, reads/replay — исторический key по ID; missing key отказывает, не считается hash mismatch или запросом на новую вставку. KEK, HMAC и CSRF вне БД/Git, раздельные по средам; back up нужных ключей отдельно, rehearsal synthetic copy, rewrap не переписывает immutable факты (управляемое отдельное хранилище ключевой обёртки), проверяется возможность открыть прежние записи и невозможность кросс-средового восстановления. `retire` для HMAC не отменяет durable tombstone; для DEK уничтожение одной обёртки не удаляет копии из backup. Live key retirement/field erasure, hold и rescrub остаются P13P; encrypted payloads/key slots отдельно от постоянных provenance rows, которые не содержат raw ПД. Поисковый blind index — отдельный P06 scope с анализом equality leakage и отдельным ключом.
- **Кто видит plaintext:** обработчик F/manual intake знает только вход; `ConvertCallback` и `ChangeDetails` пишут новые полные поля разрешённого раздела, не читают прежние ПД. `ChangeContact` требует отдельное verified evidence для нового payload/actor/target; создаёт новый contact snapshot, не меняет существующее правовое основание заявки и не копирует прежний PHONE allow. `ReadyForDispatch` проверяет только basis, contact permission и address assessment metadata. Единственный ранний внутренний decrypt-usecase — `verifyAssessmentAddress` внутри `RecordCoverageAssessment`: он сравнивает с точным адресом, уже известным сотруднику по независимой разрешённой процедуре; plaintext не возвращается. До вызова: `requests.read ∩ requests.coverage.assess`, live actor/same city, actual basis, expected request version и current address snapshot под locks. Harness выдаёт одноразовое короткоживущее server-side evidence на `COVERAGE_REVIEW`, связанное с точным actor/request/address revision и **каноническим кандидатом адреса** из независимого источника; клиент не может менять кандидата сохраняя evidence. UUID evidence и флаг браузера сами по себе не авторизуют. При отсутствии разрешённой процедуры или адреса из независимого источника assessment недоступен, read API не вводится. Точный результат сравнения не раскрывается в ошибке/логе, нет отдельных подсказок по полям. Сверка, область/операция, успех записи имеют actor/request/snapshot/purpose/evidence IDs без raw values. После проверок authority и до decrypt: подтвердить committed minimal security audit attempt в отдельном коротком autocommit по доверенному append-only порту без FK/запросов к locked domain rows; business tx хранит только audit correlation и атомарный success event. Audit attempt не доказывает decipher/success, фиксирует допущенную попытку даже при последующем rollback; если нельзя подтвердить audit attempt/одноразовое потребление до доступа — не расшифровывать. Для той же purpose/evidence повтор не делает ещё одну сверку; для exact committed replay сверка не нужна. Ни в request/PG rows аудита, ни в errors, telemetry, URLs или outbox не попадают candidate/plaintext/filename/ciphertext/key material. Источник evidence — отдельный внутренний issuer **только T**, не HTTP, не role action и не generic fixture flag. Его вход — заранее подготовленный synthetic fact из независимого источника, а не мнение пользователя запроса. Непрозрачный handle связывает issuer, purpose, exact actor/request/address revision, immutable canonical candidate и expiry; публичный DTO не может заменить кандидата или передать свои source/authority fields. Одноразовость обеспечивает append-only запись `audit_attempt` с UNIQUE `(issuer, evidenceId, purpose)` **независимо от Idempotency-Key**: допуск только при подтверждённом новом commit этой записи, не при обнаружении старой. Потеря ACK попытки → no decrypt, неизвестный результат нельзя автоматически использовать повторно; при rollback доменной команды durable попытка остаётся, success event не возникает. Exact replay подтверждённого business commit возвращает только квитанцию, не decrypt. Ответ при отказе admitted comparison — один безопасный отказ без посимвольной/полевой диагностики, значений или возможности перебирать candidate одним handle. Тесты: cross-city/stale/scope отказ до audit/decrypt; чужое evidence, changed candidate и конкурентное повторное использование с разными keys; failure/unknown ACK audit attempt → ноль decrypt; успешное сравнение с последующим forced rollback → один факт попытки, ноль успешных effects; одинаковая ошибка и отсутствие ПД в logs/outbox/response.

## 4. F proof, consent, квитанция и телефон

### 4.1 Слоты, TTL и CSRF

Существующий P03 anchor: [миграция 013](../prisma/migrations/20261121000400_settings_legal_references/migration.sql#L311-L379), [порт issue/lock](../apps/api/src/settings/legal/legal-sessions.ts#L47-L93) и [точный proof/expiry](../apps/api/src/settings/legal/legal-sessions.ts#L119-L180). P05 сам выдаёт 256-bit случайный secret, хранится существующий SHA‑256, исходный token — только Secure/HttpOnly/SameSite=Strict `__Host-fixlevelup_f_<uuid>`, Path=/, без Domain; селектор — отдельный `X-Form-Session-Id` UUID, не в URL. Не принимать чужие/doubled cookie/header, F proof в body, CRM cookie или staff/TG bearer как F. Slot budget отдельно от CRM: максимум 4 живых F на browser group, не более 8 cookies этого префикса в запросе и 8 KiB Cookie до parse; отдельные bounded source/global/per-F rate limits. `POST /public/form-session/browser` с `{}` и обязательным same-origin marker (exact Origin, JSON, custom header, no CORS) проверяет существующую группу или при отсутствии выдаёт отдельную защищённую opaque `__Host-fixlevelup_fgroup` cookie, **не** F. Клиент сериализует первичный bootstrap вкладок по origin; сервер ещё не создаёт anchor, не привязывает старые формы к новой группе и не считает cookie идентичностью физического браузера. Issue с `{}` требует уже доказанную group cookie; под quota/group lock считает **все** живые связанные anchors по БД, не только присланные cookies; параллельные issue одного group сериализованы. Клиент может удалить cookies/сменить профиль, поэтому новый group также subject to source/global issuance cap; proof заявки не зависит от group cookie. Group и сопоставления живут не меньше своих anchors, имеют ограниченный expiry и не удаляются произвольно. Фиксированные caps — защита протокола, TTL остаются явно настроенными тестовыми значениями. `Max-Age`/`Expires` рассчитываются по DB TTL консервативно; окончательная власть только DB clock. При подтверждённом отзыве или предъявлении точной просроченной cookie — адресное `Max-Age=0` для неё одной; ни замещения формы, ни очистки CRM cookie. Логическое освобождение слота — по DB expiry/revocation без уничтожения истории. Отзыв F (отдельный endpoint) — только закрытие proof, не request transition, не правка согласия.

Issue и все мутации требуют точный настроенный Origin (отсутствующий также deny), same-origin без CORS, duplicate security headers запрещены. Однозначный CSRF proof формируется отдельным ключом на назначение `P05_F_MUTATE`, привязан к F selector/secret и отдельному сроку ≤ остатка anchor; выдаётся no-store лишь при issue либо специальном read-only bootstrap действующей исходной F с same-origin `Origin` и non-simple header, не продлевает anchor, body/storage не сохраняются. Reissue создаёт короткий proof текущей версии; прежний недействителен после revocation/expiry либо ключевой смены, в своём сроке не является одноразовым idempotency key. CSRF проверяется до разрешённого действия и повторно вместе с anchor у decision point если срок мог пройти. Только configured technical budgets, без живых default policy. Никакого PII на этапе формы/consents/advisory; если нераспознанный raw запрос содержит адрес, server отвергает его и не пишет/обрабатывает как проверку адреса. Proof: concurrent slots/quota и независимость вкладок, expiry freed slot без нового anchor из прежнего proof, raw header duplicates/bad UTF‑8/CSRF expiration/origin/crm cookie unchanged, clocks sampled после wait, отсутствие PII по synthetic sentinels.

### 4.3 Replay, partial и ошибки

Idempotency namespace — `(F anchor|staff actor, operation, canonical UUID key)`; HMAC по closed decoded normalized intent, exact target, expected version, evidence и полям обработки. Dispatcher исполняет тот же frozen payload, не пересобирает его из raw JSON. В F scope сериализует anchor; в staff create — dedicated xact key fence на namespace до request row, затем UNIQUE; actor+policy lock не заменяют exact target reauth. До claim/replay/conflict проверяем authority и live clocks; ничего о prior target до отдельного подтверждения его scope. У использованного anchor **любой другой ключ или другая submit-операция** получает `409 FORM_ALREADY_SUBMITTED` без номера/статуса/ETag, даже если body равен; прежний ключ/та же операция с иным body → safe `409 IDEMPOTENCY_KEY_REUSED`, точный replay → `200` та же историческая квитанция, новое создание → `201`, мутация → `200`. Чужая или неживая F не узнаёт, занят ли anchor. `version` в DTO — доменная `row_version`, не валидатор HTTP и не версия consent/workflow. Вместо тега только по версии используем **strong ETag выбранного представления** (ниже); HMAC команды включает точный исходный `If-Match`, если V требуется. Exact authorized replay идёт до проверки **текущего** тега, но не до актуальной reauth. Ошибка не отражает значения DTO.

**Точный wire V для P05.** `GET /public/request-session` и staff `GET /requests/{id}` после актуальной авторизации сериализуют только `{"data":…}` в канонические UTF‑8 bytes (фиксированные keys/order, identity encoding, без transform; `Cache-Control: no-store, no-transform`). Прежний [случайный trace ID в теле](../apps/api/src/auth/http.ts#L51-L58) **не используется для этих двух GET**: correlation ID в заголовке, не часть representation. Остальные маршруты P01–P04 и их envelopes неизменны. Strong `ETag: "p05-r1-<sha256hex>"` — hash канонического length-delimited tuple `(p05-r1, F|STAFF, request_id, exact response bytes)`. `row_version` входит через `data.version`, а разрешённая форма ответа — через exact bytes. Отключить auto/weak ETag и compression для этих двух GET на всех слоях тестового ingress. Не emit тег недоступной проекции. Этот hash не authority, не содержит открытых ПД, не дополнительная подпись квитанции. Для этих двух GET поддерживается один канонический `If-None-Match`: сначала scope и выбор разрешённой формы, затем `304` без тела, с ETag и no-store, строго при совпадении с этой формой; другой допустимый тег → `200` с текущей формой. Нет bypass авторизации по тэгу; дубли, список, `*` и weak tag не входят в этот контракт. Unsafe methods не используют conditional GET ответ.

Для существующей заявки каждая именованная I/V команда требует один strong `If-Match` **из своего canonical GET**, не из другой поверхности, не weak/multiple/wildcard и не из write receipt. Отсутствие→428, неверный синтаксис→400; mismatch→412 после текущего proof при fresh mutation. Текущее представление выбирается тем же кодом под anchor/legal/request locks, при одинаковых guards; с тегом сверяется и actual `row_version` locked row для CAS. Старая полная проекция после legal-only revoke не совпадёт с version-only даже без смены `row_version`; отмена/PHONE withdrawal всё ещё принимает **свежий** version-only ETag при той же независимой authority. Для exact replay исходный ETag входит в HMAC, но compare с новым фактом не нужен. Write receipts содержат историческую version и **не** возвращают GET ETag; для нового изменения сначала fresh GET. Тесты реального HTTP: два GET с разными trace headers и теми же exact bytes/tag; revoke legal без смены row_version → новый restricted body/tag, прежний `If-None-Match` не даёт 304, старый `If-Match` не даёт fresh write, новый restricted tag допускает закрывающее действие без нового GIVEN. Проверить так обе поверхности, denial до вычисления условного ответа, cross-target tags, exact replay со старой V при сохранившемся праве и без implicit reauth после withdrawal.

Receipt в одной транзакции, immutable, bounded: F submit/ChooseCallback `{publicNumber,status,version}`, обычный staff write `{id,publicNumber,status,version}`, cancel/withdraw обеих поверхностей `{applied,version}`. Номер, ID и доменная `version` из квитанции не authority; `ETag` для GET в write receipts не выдаётся. Независимый от receipt durable command identity хранит exact `(principal,operation,key)` с UNIQUE в append-only request event, `request_id`, resulting version и audited correlation, без raw body; HMAC только на стороне receipt/command evidence, не подпись DTO. Ровно одна пара command-event ↔ receipt обеспечивается real unique + deferred constraints обоих направлений, F submit дополнительно тем же consumed edge, audit/outbox связываются по exact row/event IDs и safe operation/correlation перед commit. При сомнительном исходе искать обе стороны, не считать отсутствие receipt отсутствием эффекта; при drift/incomplete linkage механическая readiness закрыта. Порядок проверки F: live scope/ownership → право на обычный результат по исходному неотозванному основанию → целостность найденной связи → key/body. Отзыв между запросами блокирует обычную квитанцию и не показывает конфликт существующего ключа или факт submit. Исходная F с действующим основанием, целым consumed edge и иным ключом видит только установленный `409`; неконсистентный edge/event/receipt/audit/outbox не считается ни успехом, ни свободным anchor. Valid replay проверяет совпадение aggregate/own historical event/version, receipt, submit edge и audit/outbox; to/version из immutable event, не current mutable row. Не требовать вечно актуального outbox `PENDING`, при будущей архивации до удаления создать permanent identity tombstone. Missing/conflicting/partial (включая edge/event без receipt) → safe `503` + redacted operational code, без success/предположения rollback/repair/второй записи. No auto retry при unknown COMMIT: отбросить соединение, клиент повторяет именно тот же key или authorized read-only reconcile. Обычный tx error до коммита откатывает домен+events+audit+outbox+receipt. Proof: fault после каждой записи, потеря ACK с обоими исходами, разные keys/конкурентный submit, inconsistent result, scope/revocation after wait, old MAC keys, архивный city/catalog exact replay и равенство минимального результата.

### 4.4 Явное и отзывное PHONE разрешение

Append-only `phone_permission_events`: `request_id`, `contact_revision_id`, фиксированная purpose `REQUEST_SERVICE_CALL`, `GIVEN|REVOKED`, exact `supersedes_given_id` (null только у GIVEN), DB timestamp, actor/provenance и versioned evidence. Composite FK same request/contact/purpose/GIVEN + one revoke per GIVEN; под request lock один effective latest CURRENT contact allow, не bool и не факт сохранённого номера. Issuance только при callback (F/staff), ручном полном PHONE intake и `ChooseCallback`; замена контакта не копирует allow, не даёт автоматического нового. Отзыв F через `POST /public/request-session/phone-permissions` (REVOKED only в этом route) своей текущей привязки, staff через `POST /requests/{id}/commands/withdraw-phone` с `requests.read + requests.contact.manage` и проверенным указанием клиента по текущей staff procedure, не по пожеланию сотрудника. I/V, закрытый DTO, contact/GIVEN выбираются из locked request; proof для staff привязан к exact current contact and permit generation. Операция не читает старые ПД. Поддерживается withdrawal даже после ready/terminal: статус не меняется, версия увеличивается, current eligibility/phone hint/token инвалидированы. Точная квитанция старого GIVEN или create остаётся доказательством history, не выдаёт активное PHONE право. Никакой actual call task или доставка в P05.

`ReadyForDispatch` и будущие потребители PHONE проверяют exact current allow, legal basis, contact и статус под тем же request lock. Для dispatch обязательна также актуальная coverage (§6); callback не требует адреса. `WAITING_ASSIGNMENT` сам по себе не авторизация звонка/выезда. Revoke wins → ready отказ без эффектов; ready wins → следующий успешный withdraw немедленно выключает eligibility без переписи status/history. При 412 клиент получает свежую V и явно повторяет действие; неуспешная попытка не есть отзыв.

Успешный ready оставляет одно durable информационное событие `REQUEST_READY_FOR_ASSIGNMENT` с IDs/версией, без телефона, proof/grant, задачи на звонок или отправки. После успешного withdraw событие и квитанция сохраняются как история; старое pending-событие не может быть превращено в PHONE-действие. Будущий consumer повторно проверяет live contact revision, exact unrevoked GIVEN/purpose, legal basis, actor/scope, status и subject version **при постановке задачи и непосредственно перед допуском исполнения**, под тем же request lock. При revoke, неверной версии или другом провале proof — только безопасный пропуск устаревшего действия, без звонка и fallback. Уже начатое внешнее действие отзывом задним числом не отменяется. В P05 нет live consumer. Тесты: оба порядка реальных PG commits, ready-first → событие/квитанция сохраняются, но read-only policy checker отвергает действие по этому же evidence после withdrawal; no call/send handler/task. Отдельно stale vs explicit retry, два отзыва, новый контакт, copied receipt и cancelled request not callable.

Для exact receipt replay текущее READY/offer/geo не валидируется как fresh write. Ветки с возможным fresh effect могут заранее взять fences; итог replay определяется отдельно, до применения fresh prerequisites. Нельзя брать GEO/offer/runtime в ветке несуществующей или отключённой тестовой композиции с incidental effect.

До staff by-request locks допустимо только неблокирующее чтение immutable target/session mapping; под locks перечитать совпадение и полномочия. Legal parent IDs разрешить по exact immutable keys после anchor, блокировать **сами parent rows**; [current doc/version/evidence](../apps/api/src/settings/legal/legal-consent.ts#L88-L128) проверять следующим RC statement, не брать joined revision из snapshot, полученного до ожидания. Publish legal идёт [doc→версия с reviewer FK](../apps/api/src/settings/legal/legal-documents.ts#L112-L141); P05 не берёт конфликтующие `FOR UPDATE` на staff/city раньше doc/reference. Старые пары FK приобретают обычный `KEY SHARE` на exact parents; no inversion через late `FOR UPDATE` либо обратный writer path. Runtime, intent и контроль для attachment нельзя открывать через порт, стартующий отдельную tx. Решение coverage/reference читается новым statement после fence; no shared→exclusive conversion или lock+basis в одном SQL. Повторный вызов переиспользованного порта лочит только уже удержанные parents, а не расширяет набор после позднего ресурса. HTTP/KMS/S3/человеческий review вне tx, локальные crypto keys загружены заранее; исключение — bounded security audit attempt из §3 без FK на held rows и на отдельном маленьком writer pool. PostgreSQL `clock_timestamp()` после всех waits и принудительных deferred checks, перед эффектом/решением и перед COMMIT/ответом; late refusal откатывает домен. Lock не останавливает время на сети; no stale RR/автоматического повторного write.

- **Issue/fresh submit:** [SINGLE_CITY resolver](../apps/api/src/settings/geography/city-context.ts#L32-L90) из post-fence snapshot; F issue сохраняет city+version, fresh submit требует оба текущих без fallback. Staff intake использует тот же current server context плюс exact `GLOBAL/CITY`. Historical read/replay авторизует persisted city и proof, а не новую активную географию. Не lock только старую row: новая ACTIVE или новая published area через общий X меняет множество. Runtime FK locks только на exact родителей, старые P03/Catalog guards остаются.
- **Advisory vs exact coverage:** район до consent — same-city active district, только `AREA_REVIEW_REQUIRED` и подсказки; даже FULL mapping не устанавливает `IN_ZONE`. При staff оценке по §3 под S GEO считывается ограниченная по объёму, но полная сортированная basis: текущий активный city/version/timezone, **все** действующие опубликованные зоны этого города `(areaId,areaVersionId)` (и при наличии района — его `row_version` и mappings текущих зон для этого района). Даже новая зона без mapping может влиять на оценку точного адреса. Пустой набор не даёт положительной оценки; превысив лимит — отказ, не усечённая basis. Immutable assessment фиксирует exact address revision, city, digest нормализованной basis, выбранную действующую same-city area+version, `IN_ZONE / OUTSIDE / REVIEW / EXCEPTION`, actor/reason/version. IN_ZONE или EXCEPTION требуют одну явно выбранную зону и независимое evidence; при overlap/вне зоны причина обязательна, нет автоматического исключения. Для OUTSIDE/REVIEW положительной authority нет. `ReadyForDispatch` под S GEO заново читает **всю** basis после wait и требует совпадение текущего адреса, активного city/version/timezone и набора зон с assessment; иначе `409 COVERAGE_ASSESSMENT_STALE`. Флаг готовности не заменяет этот live predicate будущего назначения; никакой гарантии слота. Смена адреса обнуляет current assessment, история сохраняется. Browser timezone/ENV не источник.
- **Инвентарь GEO writers на 021.** Обязательные точки переноса под X: [`cityCreate/AddVersion/Publish`](../apps/api/src/settings/geography/catalog-commands.ts#L757-L846), [`cityActivate/Deactivate/SetPrimary`](../apps/api/src/settings/geography/catalog-commands.ts#L849-L940) с переносом company settings, [`districtCreate/Update/Archive`](../apps/api/src/settings/geography/catalog-commands.ts#L978-L1066), [`areaCreate/Archive`](../apps/api/src/settings/geography/catalog-commands.ts#L1102-L1167), [`areaAddVersion/EditDraft/Publish`](../apps/api/src/settings/geography/catalog-commands.ts#L1203-L1322), [`areaCoverage`](../apps/api/src/settings/geography/catalog-commands.ts#L1357-L1425) и вложенный parent update из 011; company publisher и [`referenceCreate/Publish/Archive`](../apps/api/src/settings/configuration/references.ts#L171-L354), включая вызовы из [P03 management runner](../apps/api/src/settings/management/management-runner.ts#L87-L126). Включить в proof как application path каждый, кто меняет basis, так и прямые вызовы внутренних портов: `INSERT/UPDATE/DELETE` (и legacy запрещённые операции) через runtime на защищённых relations без X отказывают; guard не снимает прежний запрет `TRUNCATE`. Старый writer без prelock не может изменить guarded basis, старые операции, уже соблюдающие порядок, не превращают весь 021 binary в совместимый. Prepared/migration SQL и fixture DML используют тот же контракт либо закрытую DDL фазу без runtime, не исключение роли из guard. На каждом точном S0…S3 — реальные трассы совместимого B для writer-first и reader-first: primary/версия, новая опубликованная overlap-зона, rezone/archive/rename reference; оба порядка COMMIT и вариант rollback, без stale/mixed basis. На S0 используется изолированный reader probe с теми же fences без обращения к отсутствующим P05 relations; SQL guard и реальный P05 effect проверяются только на применимой расширенной схеме. §7 проверяет закрытый B, отказ несовместимого legacy writer и повторный запуск B на expanded schema, не только схему.
- **Доказательства перед первой DDL (план, а не результат этой задачи):** на пустой и наполненной изолированной 021 PostgreSQL 18.7 сверить legacy metadata; трассировать реальные compliant company/activate, unprotected-by-this-fence city publish/area/new overlap, RBAC and catalog vs reader, original legal/file prefix. Два backend + независимый observer `pg_blocking_pids`, exact lock mode/key, оба commit order/rollback и `lock_timeout`; показать текущий gap без нового guard, не выдавать это за проверку будущих FK. **После каждой relevant DDL:** реальный writer through app/guard vs reader (включая вновь опубликованную зону и прямое runtime DML без обязательного X → отказ), fresh after wait basis, scope/role revoke, original consent revocation/publication after wait, clock/lease/policy истечение после последнего lock/audit wait, attach/delete, blocked connection без частичного эффекта; 40P01 недопустим для ожидаемых нормальных пар. Bounded unexpected lock/serialization conflicts fail closed, без автоматического дубля. Нет заявления об отсутствии всяких deadlock вне зафиксированного графа.

### 5.2 READY — переиспользование P03 и безопасное прикрепление

На baseline **нет публичного upload/read/download HTTP**: [файловый контракт P03-04](P03-04CDE-CONTRACT.md#L3-L14) и [проектные маршруты, не реализация](API.md#L105-L122). Изолированный harness с живым F и exact current GIVEN вызывает настоящую цепочку:

| Шаг | Факт на main |
|---|---|
| 014 → `RESERVED` | [Миграция 014](../prisma/migrations/20261121000500_file_upload_reservations/migration.sql), [внутренний `reserveFileUpload`](../apps/api/src/files/reservations/index.ts#L24-L33): только no-byte reservation/точное основание и budget; `RESERVED→CANCELLED`, не state-машина публикации. |
| 015 → `QUARANTINED` | [Миграция 015](../prisma/migrations/20261122000100_file_upload_attempts/migration.sql), [реальный `uploadReservedFile`](../apps/api/src/files/upload-coordinator/index.ts#L64-L92): durable register/dispatch перед байтами, bounded private S3 PUT + exact full GET, одна immutable quarantine binding; `VERIFIED` attempt не READY. |
| 016 → READY | [Миграция 016](../prisma/migrations/20261122000200_file_processing_access/migration.sql), [`processQuarantine` и F-only metadata/access](../apps/api/src/files/file-lifecycle/index.ts#L1-L6), [verified publication join](../apps/api/src/files/file-lifecycle/publication.ts#L30-L46). Реальные закреплённые scanner/decoder, sanitized bytes доказаны; `{intentId,completed}` не access proof, READY идентифицируется точным `fileId = file_publications.id`. |
| 017 → hold/delete и restore fence | [Миграция 017](../prisma/migrations/20261122000300_file_privacy_deletion/migration.sql#L148-L188), [P03-04 access/retention/restore](P03-04CDE-CONTRACT.md#L88-L115): preexisting copy/ledger policies, no restore changes, READY не оживает из restore. |

Fresh attach — только F repair. В одном submit tx `request_files` имеет restrictive FK `(request_id,owner_session_id)` к committed submit-edge (сам edge включает city/request/customer), `(intent_id,owner_session_id)` к фактическому intent и `(intent_id,file_id)` к publication; минимум необходимый новый immutable unique tuple на старых таблицах, никаких изменений old ACL/SQL001…021. No duplicates `(request,file)`; один file/intent не участвует одновременно в разных заявках. Staff manual без F и без attachments. Узкий in-transaction admission переиспользует [проверку `authorizeMetadata`/`accessWindow`](../apps/api/src/files/file-access/registry.ts#L36-L95), точный [P03 authorization check](../apps/api/src/files/file-lifecycle/authorization.ts#L173-L227) и выдаёт только safe IDs/MIME/size для связи, не blob location/stream ticket. Не принимать prior HTTP/metadata read как доказательство. Внутри original ready window: `ACTIVE` exact namespace/epoch 1, intent `RESERVED`, privacy `OPEN`/access epoch 1, same owner, exact original GIVEN still current, verified raw/sanitized/READY revision, MIME allowed JPEG/PNG/WebP, configured count/byte budgets including complete attachment list; `now < min(F expiry, intent expiry, original upload-policy expiry, current access-policy expiry, publication+maxAccessAge)`. Finite DB clock после locks/append+deferred checks для всех attached files; fail closed на отсутствующий runtime/policy, stale READY, wrong doc/owner/binding, D-frozen, unproven bytes или mixed set. Отрицательные проверки side effects=0; exact old replay не повторяет admission, не дает доступ к файлу. P05 не даёт новой выдачи байт, не отнимает принятый P03 pre-submit authorization path и не расширяет его TTL/authority.

**Attach vs delete:** обе операции держат существующий префикс runtime→anchor→doc→intent→control. Проверка `NOT EXISTS request_files(intent_id)` в selection до LIMIT и повторно после lock в irreversible `decide` (возраст — действующая [DUE-проверка P03](../apps/api/src/files/file-privacy/retention.ts#L36-L45), [selection/decision](../apps/api/src/files/file-privacy/retention.ts#L72-L120)). DB backstop S3: attach под уже удерживаемым intent lock создаёт штатный lazy control через [существующий порт](../apps/api/src/files/file-lifecycle/authorization.ts#L98-L109), если его нет; требует `OPEN`. Добавляем real FK `(intent_id, open_state)` → `file_privacy_controls(intent_id, delete_state)` по новому непарциальному UNIQUE, `open_state` NOT NULL CHECK = `OPEN`, `ON UPDATE RESTRICT ON DELETE RESTRICT`. Не изменяем control epoch, hold или state ради attach. FK запрещает существование прикрепления при non-OPEN, включая попытку **`OPEN→PENDING_LEDGER`** в старом writer и прямой SQL; при delete winner точного FK-target больше нет. В отличие от триггера с запросом по старому MVCC snapshot, FK не основывает гарантию на app-side check. Runtime не может удалить/обновить link или смягчить CHECK. На точных pre-S3 профилях работает прежняя ветвь без запроса к отсутствующей таблице; S3/drift проверяется по точному профилю, отсутствие FK/данных схемы не разрешает legacy fallback. Hold/ledger/delete обычных unattached файлов неизменны; для attached старый aging не действует до отдельного P13P. В file-only restore действует отдельный source/target gate ниже; наличие FK не доказывает, что снимок содержит все уже принятые заявки. Полный P05 rescrub не входит. Rollback floor включает защиту deletion; штатные P05 releases не могут обходить relation guard.

**Какие пути удаления проверяются.** От aging решение идёт в [`readCommittedWork` и `authorizeLedger`](../apps/api/src/files/file-privacy/deletion.ts#L18-L72): `OPEN` не создаёт ни graph, ни ledger membership. [`claimExactItem`](../apps/api/src/files/file-privacy/delete-claim.ts#L44-L74) требует exact non-OPEN decision, `LEDGERED/VERIFY_PENDING` и совпадение ledger position, а [grant создаётся только после подтверждённого COMMIT](../apps/api/src/files/file-privacy/delete-claim.ts#L94-L102). [Broker](../apps/api/src/files/file-privacy/broker.ts#L172-L185) принимает только такой одноразовый grant для точного key/target/epoch; [drain FENCED](../apps/api/src/files/file-privacy/deletion.ts#L115-L149) не вызывает broker. Уже выданный grant соответствует non-OPEN intent — прикрепить его задним числом нельзя. Прямой вызов этих портов не обходит проверки; прямую DB-попытку изменить `OPEN` проверяем под runtime и old writer. Ручные действия S3-администратора, доступ к storage credentials, удаление самой среды и недоступность хранилища не предотвращаются FK; в проверяемом P05 нет таких путей/credentials у API, отключены внешние lifecycle rules тестового bucket. Сохранность не выводится ни из READY, ни из строки link.

Тесты: real Garage PUT/GET + утверждённые P03 scanner/decoder pipelines, no synthetic READY SQL. Отказы на PDF/non-READY, stale/missing access window при ещё живом F, отмену intent, чужого владельца, consent revoke→GIVEN₂, restored epoch. При attach-first: age-due retention и прямой `OPEN→PENDING_LEDGER` не дают decision/item; действующий reconcile/drain не создаёт ledger запись/claim/DELETE; доверенный **тестовый** observer читает exact raw и sanitized bytes того же isolated bucket, полным bounded GET сверяя исходную длину и SHA‑256 после попыток, независимо от ACL F-window. При delete-first: нет attachment ни на стадии committed decision, ни после ledger/broker; повтор/restore не оживляют authority. Положительное удаление unattached и legacy P03 full restore, negative expanded restore из §5.3 — отдельные реальные доказательства. Тестовый observer не даёт новых HTTP routes или байтовых полномочий приложению.

### 5.3 File-only restore: доказать отсутствие P05 после остановки источника

[Существующий inventory/overlay](../apps/api/src/files/file-restore/inventory.ts#L9-L34) переносит F/legal/files/audit/outbox, но не P05 request/customer/receipt. [P03 fixture](../apps/api/tests/file-restore.test.ts#L205-L231) уже останавливает file runtime, лишает `fixlevelup_runtime` CONNECT и подписывает текущие факты после drain; это не автоматический fence для P05, особенно для callback без файла. Проверка при создании базового dump/manifest — только предварительная; пустая целевая БД не доказывает актуальную полноту источника.

- Перед первым `currentAuthority` для любого поддерживаемого профиля доверенный оператор изолированного прогона блокирует новые P05 работы и подключения к **исходной** БД, включая API, worker, test harness, внутренний importer/issuer/DDL, отзывает effective `CONNECT` у всех application writer roles вместе с обходом через PUBLIC/наследование и дожидается завершения уже начатых транзакций/пулов; не заменяет drain вызовом file `FENCED`. Подтверждает конкретный source DB/кластер, старый file namespace/epoch/fence, отсутствие активных writer backends и prepared transactions, отключённые write capabilities/процессы и отсутствие нового допуска до завершения handoff. Прежний file-only `SOURCE_DRAIN` завершить по P03-протоколу до окончательной проверки отсутствия writers; после неё разрешены только доверенные read-only проверки источника. Весь handoff удерживает фактический отказ writer `CONNECT`, запрет выдачи новых source launch proofs и закрытие уже допущенных source consumers, не просто флаг в подписанном сообщении. Снимать их между проверками или перед открытием цели нельзя. Неопределённый исход закрытия источника → не открывать цель. Out-of-band owner DDL вне границы доверия; нет подключения к рабочей среде.
- **Только после этого** — свежая проверка на том же primary: точный schema profile, отсутствие всех P05 operational rows по закрытому перечню таблиц данного профиля (заявки/клиенты, снапшоты и encrypted payload, F extension/submit, PHONE/evidence, attachments, events и durable receipt/tombstones; полный перечень совпадает с reviewed DDL), включая any partially committed/inconsistent state. Не считать незнакомую/отсутствующую при expanded profile таблицу «пустой». Разрешимы известный unexpanded cap (P03/021 при подтверждённом отсутствии P05 schema) либо exact expanded profile с пустым P05 state; unknown/unavailable/незавершённый drain → `RESTORE_AUTHORITY`. Ни одна строка ПД не попадает в доказательство.
- В каждом restore под новым bridge оператор выдаёт версионированное текущее attestation в дополнение к [существующему signed nonce/manifest/overlay/inventory/head](../apps/api/src/files/file-restore/records.ts#L80-L92). Оно связывает hash authority record с exact source DB/cluster identity, destination/manifest digest, актуальным schema profile, old namespace/epoch и доказанным результатом `P05_EMPTY_AFTER_DRAIN` либо `P05_SCHEMA_ABSENT_AFTER_DRAIN` для exact прежней схемы. Признак выбирает только signer по проверенным текущим данным, не caller flag. Fence держится до handoff. В [начальном `currentAuthority`](../apps/api/src/files/file-restore/rescrub.ts#L69-L96) и [повторном после IO перед `ACTIVE` CAS](../apps/api/src/files/file-restore/rescrub.ts#L120-L143) проверяем вновь подписанный результат с новым nonce и свежей проверкой **источника**; стабильные поля должны совпасть. На цели при выключенном `CONNECT` проверяем отсутствие P05 state и точное равенство профилей: фактический source profile после drain = подписанный profile = профиль manifest = фактический target profile. Проверка повторяется внутри закрытой target-транзакции перед `ACTIVE`; два известных, но разных профиля не дают допуск. Старый формат снимка/overlay P03 остаётся доступен с новым актуальным доказательством отсутствующей P05-схемы, но старый authority record **сам по себе** не разрешает reopen; manifest о старой версии не заменяет проверку фактического профиля источника. Existing ledger, inventory и hold/cancellation checks не ослабляются. При любом отказе не переводить цель в `ACTIVE` и не разрешать runtime `CONNECT`.
- Три раздельные отрицательные трассы на реальных изолированных PG/restore: (1) после пустого по P05 base dump принять и подтвердить callback **без вложения**, затем осушить все source writers — отказ до `ACTIVE` и runtime `CONNECT`, хотя в dump заявки нет; (2) source и восстановленная цель имеют **два разных, по отдельности известных** schema profiles — отказ до открытия, не считать два валидных профиля взаимозаменяемыми; (3) остановить исполняемый handoff барьером **между последней source-проверкой и целевой активацией**; каждая перечисленная роль writer и повторный запуск прежнего API/worker/harness не получает source `CONNECT` или source admission. Если независимый наблюдатель фиксирует, что writer path всё-таки доступен либо fence потерян, handoff останавливается и target остаётся закрытым. Bounded pause, наблюдаемые ACL/PG sessions и ноль side effects, а не констатация флага. Положительные legacy P03 restore и точный пустой expanded profile проверяются отдельно. Полное восстановление P05/ПД остаётся за P13P.

### 5.4 No-call: точный источник и граница P07

`catalogVersionId` — **не** из P04: будущая exactly published [`channel_offer_catalog_versions.id`](DATABASE.md#L334-L343) P07-ADM и membership `(catalog_id,option_version_id,provider)` с purpose `REQUEST_CONFIRMATION`. P04 даёт отдельные revisions техники/симптомов. Единственный domain port `validateNewOffer(tx, selection)` получает exact provider/option/catalog/purpose, читает authoritative current pointer и B/technical/live/D matched scope в том же PG primary tx под version/readiness fence, с очередным post-wait/near-commit clock, возвращает только immutable allow basis tuple или closed reason. Writer того источника разделяет тот же fence; deadline/expiry rechecked до COMMIT. Не принимать ready/connection IDs или внешний вызов от клиента. Сохраняется только exact immutable provenance/IDs и начальный waiting code; новое A-off не переписывает прежний выбор и не ломает exact authorized replay. FK к реальным P07-ADM sources добавляет P07 до открытия; не создавать конкурирующий каталог в коммерческой схеме.

## 7. CITY/RBAC и реальный путь совместимости

- Сохраняем **каноническую** матрицу P02/P03/P04, не отдельную синтетическую CRM identity. `requests.read/create/review/coverage.assess/contact.manage/ready/cancel`: active ordinary codes, SYSTEM ADMIN web exact `GLOBAL` или `CITY` с действующим admin-city assignment, SYSTEM MANAGER/CUSTOM-web exact `CITY` и assignment, TECHNICIAN/TG/F/C/guest deny. На каждое действие нужен exact code плюс read той же цели, не union. City при create из trusted context, при by-id из persisted aggregate до receipt; wrong city/no target indistinguishable. Делегирование проверяет собственный exact GLOBAL и защищённый role policy, включая косвенное усиление через staff create/assign/admin-city assignment/role replacement, никто не получает прав по имени роли. Для synthetic-only test заполняются адресные grants в disposable PG явно проверенным оператором, под RBAC X и с тестовым expiry/identity; no grants on migration/bootstrap/startup, no real provisioning/rights. Новые codes не становятся штатным source authority при отсутствии expanded schema, неизвестном профиле, placeholder policy или test fixture. Existing read/use/write/replay reauth at final DB time.
- 021 [CHECK](../prisma/migrations/20261122000700_catalog_management/migration.sql#L34-L43) не допускает CITY новых codes; его изменение попадает в точный [P03 readiness hash](../apps/api/src/infrastructure/database/runtime-database.ts#L575-L626) и [P04 readiness](../apps/api/src/infrastructure/database/runtime-database.ts#L637-L723) вместе с guards/ACL. Старый [PUT роли](../apps/api/src/roles/roles.service.ts#L159-L182) не умеет сохранённые enabled P05 codes. **Не утверждать**, что 021 binary годится для expanded schema. Также с S1 SQL требует новых GEO fences; старый binary не подходит после даже первого expand без расширения RBAC. Именно это, а не «новый intake выключен», задаёт rollback floor. Выбран **bridge, а не общее ослабление fingerprint/constructor и не произвольный GUC**.
- **Bridge B — отдельно воспроизводимый закрытый артефакт P05-03 с подготовленными writers, защитой retention и точными profiles 021/S1/S2/S3.** На предыдущих срезах промежуточные B₁/B₂ проверяются с уже созданными profiles. B на 021 до любой новой DDL берёт требуемый X GEO, но не читает отсутствующие P05 relations/permissions; P03/P04 продолжают работать. B на S1/S2 распознаёт только reviewed intermediate shapes, на S3 — точный role catalog, guards и retention interlock. Known 021 fingerprints и действующие проверки не удаляются; expected hashes из reviewed DDL на чистой PG18, не runtime baseline из фактических данных. Для обычного B/R и изолированного T выбор профиля допустим только при **двух независимых проверках**:
  1. **История — вне runtime.** Доверенный release/test preflight с migrator credential на согласованном primary проверяет полный список `foundation._prisma_migrations` по закреплённому manifest артефакта: точные name/checksum, по одной завершённой записи на миграцию, без failed/pending/unknown записей и без исправления истории. Артефакт подтверждается по digest до запуска. Короткоживущий подписанный launch proof содержит `issuerGeneration, launchNonce, consumerKind, instanceId, channelId, artifactDigest, targetIdentity, database, databaseOid, runtimeRole, schema, profile, historyManifestDigest, physicalContractDigest, witness, expiresAt`. `targetIdentity` связывает proof с тем же настроенным endpoint соединения: в проверке это закрытый namespace с локальным PostgreSQL, для будущей рабочей среды нужна отдельно проверенная аутентичность транспорта/сервера. Witness не подменяет доверие серверу и не охраняет от DBA с правом произвольного DDL. `consumerKind` = API, WORKER либо изолированный test harness; `instanceId` и `channelId` назначает launcher отдельному дочернему процессу/каналу, не по self-report и не по повторно используемому PID. Подписывающий ключ и migrator credential только у внешнего оператора; приложению — pinned public key и ожидаемые facts через защищённую конфигурацию, не endpoint и не env «ready». S0 не требует новой таблицы/роли/функции в приложении: сравнивается неизменённая история 001…021.
  2. **Физический профиль — непривилегированный runtime.** До допуска проверяются подпись, exact identity/nonce/expiry/artifact/database/schema, точные catalog/table, constraints, triggers/functions/indexes/ACL по независимому build allowlist. Прежние P03/P04 predicates и [запрет SELECT history](../apps/api/src/infrastructure/database/runtime-database.ts#L347-L374) сохраняются. Preflight выполняет проверку истории на том же выделенном операторском соединении, на котором держит случайный advisory witness в отдельном namespace. Witness — session lock **только у внешнего launcher**, не у прикладных пулов и не на ключе GEO/CFG; после read-only проверки транзакция закрыта, witness живёт от preflight до остановки этого экземпляра. Runtime на проверяемых соединениях видит granted witness в `pg_catalog.pg_locks` (exact key/mode/backend PID/DB OID), а не просто имя БД. Это связывает обе проверки с одним primary и позволяет проверять последующие соединения, **но не расходует proof**. Потеря witness/соединения или неверный fingerprint до допуска — отказ, без DB-backed работы. Миграции/DDL выполняются при закрытом трафике под release lock, после них требуется новый handoff. Никаких GRANT на history, SECURITY DEFINER обхода и migrator creds в API/worker; runtime не утверждает, что непрерывно проверяет историю.

**Однократный admission у launcher (обязателен дополнительно к обеим проверкам).** В изолированном прогоне используется один приватный реестр launcher в отдельной одноразовой control DB того же PostgreSQL, с отдельными owner/launcher ролями и без доступа application/migrator credentials. Это операторская часть тестового контура, не application schema/API/runtime dependency и не миграция S0–S3. Реестр не входит в application backup/restore. Неизменяемый ключ `(issuerGeneration,launchNonce)` — PK, **без** consumer в ключе; в строке exact digest подписанного proof, consumer kind, instance, private channel, expiry. И выдача `ISSUED`, и погашение подтверждаются COMMIT с `synchronous_commit=on`; proof передают только после подтверждённой выдачи. У launcher узкие права, без DELETE/TRUNCATE, изменения binding или DDL; DB guard допускает только начальное `ISSUED` и переход `ISSUED→CONSUMED` с неизменяемым победителем. Текущий issuer generation задаётся доверенной конфигурацией, не сообщением child.

Для допуска launcher принимает успешный runtime handshake на живом witness **только по собственному приватному IPC-каналу конкретного child** (эксклюзивно наследуемый handle; PID, присланный channel ID или proof сами по себе не дают доступ). Затем в control DB: явная RC, exact row `FOR UPDATE`, **следующим statement после ожидания** один условный UPDATE `ISSUED → CONSUMED` с проверкой binding/digest и `clock_timestamp() < expires_at`. Победитель — ровно одна возвращённая строка и подтверждённый durable COMMIT; у второго `0 rows` или отказ. Immutable winner сохраняется; нельзя читать старый `CONSUMED` как повторное разрешение, переподписывать этот nonce или делегировать CAS локальному кэшу. После COMMIT launcher снова проверяет неистекший срок по часам БД и live witness/тот же IPC, затем посылает **один** сигнал именно победившему child. Child принимает сигнал один раз из своего канала, сверяет привязку, срок по часам БД и живой witness **непосредственно перед запуском**, затем подтверждает активацию. Проигравший параллельный CAS не закрывает действующую активацию того же владельца канала и не создаёт вторую; иному предъявителю сигнал не выдаётся. Launcher не открывает HTTP ingress до подтверждения этого child. Worker bootstrap и DB timers также запрещены до принятого сигнала и финальной проверки. До допуска child выполняет только ограниченные read-only проверки метаданных под runtime ролью, не бизнес-запросы.

Wrong consumer, отказ CAS, истечение срока, отсутствие реестра, потеря witness или ошибка runtime proof не допускают предъявителя. Повторное сообщение уже допущенного child не даёт второго сигнала и не отзывает его подтверждённый допуск. При неопределённом COMMIT launcher закрывает исходный ожидающий канал и останавливает child; не перечитывает `CONSUMED` ради повторной выдачи. Исчерпанный или закороченный канал **не восстанавливается**, даже если транзакция в действительности откатилась: новый IPC не принадлежит исходному подписанному binding. При неизвестной доставке уже отправленного сигнала закрыть ingress, остановить/дренировать потенциально допущенный экземпляр до replacement; не обещать откат уже состоявшихся эффектов. Duplicate/late completion не выдаёт разрешение после закрытия канала. Restart/rollback и отдельный worker всегда с новым nonce/proof/channel и пройденным preflight; один proof не допускает API и worker вместе. Журнал не откатывают, не клонируют и не подключают второй реестр к той же generation. Если реестр утрачен: сначала закрыть прежние процессы/каналы и отозвать доверие к прежней generation, затем новый authority bootstrap и preflight. Просроченные выдачи не переиспользуются. Операционный режим P05 проверяется только на собственной изолированной инфраструктуре.
- **Role writer в bridge:** recognized rule для новых codes (не unknown), exact target scope и existing checks сохраняются, new enable/expand/actual issuance P05 не открываются в обычном composition. Если expanded synthetic rollback fixture уже имеет P05 rows, B безопасно обрабатывает просмотр и явно сохранённые/отзываемые обученным caller строки по exact scopes; если пред-P05 клиент прислал неполную authority set, не удалять/понижать скрыто и не выдавать права; отказ до любого эффекта. У unaffected roles прежний PUT semantically identical на S0…S3. Без branch-wide изменений P03/P04 grants невалидные P05 grants не становятся authority.
