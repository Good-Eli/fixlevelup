### 2.2. Калибровка

За единицу принят **P02 = 1,0 балла** — самый «средний» по составу этап: схема,
API, права, тесты, без экзотики. Остальные оценены относительно него по объёму
подэтапов в [ROADMAP §3](ROADMAP.md#3-малые-подэтапы-с-приёмкой), числу миграций и
классу риска.

### 2.3. Оговорки, без которых цифры обманывают

- **Точно измерены только P01–P04.** Остальное — оценка. Погрешность по
  отдельному этапу — примерно плюс-минус половина, по сумме — заметно меньше.
- **Балл ≠ день.** Балл P03 (файловый контур с ledger и restore) тяжелее балла
  P06 (экран CRM), хотя формально это одна единица. Веса внутри оценки это
  сглаживают, но не выравнивают полностью.
- **P15 честно не оценивается**: там передача, обучение, поддержка и юридические
  документы, а не только код.
- **Трудоёмкость — это работа, а не календарь.** Половина времени уходит не на
  код: ревью, приёмки, миграционные доказательства, ожидание доступов.

### 2.4. Календарные сценарии

Наблюдаемый темп на P01–P04 — около 2 баллов за активный день при параллельных
исполнителях.

| Сценарий | Что предполагает | Оценка активной работы |
|---|---|---|
| **Оптимистичный** | только synthetic, тот же темп, без задержек на доступах | 13–14 дней (≈3 недели) |
| **Реалистичный** | с итерациями ревью и приёмками (+60% на переделки) | 21–25 дней (≈5 недель) |
| **Полный** | с реальными каналами, staging, нагрузкой, restore-учениями, юридикой и хостингом | 40–50 дней активной работы |

Разница между вторым и третьим сценарием — не в объёме кода, а в том, что часть
работ нельзя начать без доступов и решений владельца.

## 3. Этапы: что это и зачем

| Этап | Что это | Зачем в общей картине |
|---|---|---|
| **P00** Архитектура | Договорённости о том, как устроена система: модель данных, доступ, каналы, открытые вопросы. Только документы. | Чтобы каждый модуль не строился по-своему. |
| **P01** Foundation | Каркас: репозиторий, сборка, база, хранилище файлов, очередь событий, CI. | Фундамент, на котором стоят все приложения. |
| **P02** Сотрудники и доступ | Кто входит в систему, с какой ролью и что именно ему разрешено. | Без этого нельзя безопасно открыть кабинет и календарь. |
| **P03** Настройки и география | В каком городе работаем, какие районы обслуживаем, какие тексты и документы показываем, где лежат вложения. | Привязка цен, расписания и заявок к городу; безопасные файлы. |
| **P04** Каталог и цены | Что продаём и почём: техника, симптомы, работы, запчасти, правила наценок, расчёт стоимости. | Без каталога и цены заявку невозможно обсчитать. |
| **P05** Клиенты и заявки | Заявка появляется в системе и живёт по утверждённому сценарию: от «перезвоните» до готовой работы. | Точка, из которой живёт весь бизнес. |
| **P06** CRM | Менеджер видит все заявки, открывает карточку, читает историю, работает с дашбордом. | Рабочее место, без которого заявки не обрабатываются. |
| **P07** Каналы связи | Переписка с клиентом в Telegram, VK и MAX, шаблоны сообщений, очередь отправки, распределение уведомлений менеджерам. | Клиент пишет там, где ему удобно. |
| **P08** Сайт и формы | Публичный сайт и форма приёма заявки без звонка. | Клиент может прийти сам, в любое время. |
| **P09** Расписание и визиты | Смены, окна, расчёт слотов, назначение мастера, подтверждение, перенос и отмена. | Превращает заявку в конкретную запись с человеком и временем. |
| **P10** Mini App мастера | Экраны мастера в Telegram: «сегодня», заказы, действия, файлы. | Мастер работает с телефона, а не с бумаги. |
| **P11** Сметы | Расчёт стоимости по заявке, версии сметы, согласование с клиентом. | Деньги обсуждаются до работ, а не после. |
| **P12** Отчёты и платежи | Мастер сдаёт работу, фиксируются суммы, оплаты и возвраты. | Закрытие работ и учёт денег. |
| **P13** Закрытие и аналитика | Закрытие заявок, повторные выезды, KPI, удаление персональных данных по срокам. | Порядок в данных и цифры для решений. |
| **P14** Сквозная приёмка | 69 сценариев, безопасность, нагрузка, восстановление после сбоя. | Доказательство, что всё работает вместе, а не по частям. |
| **P15** Production | Реальный хостинг, домены, боты, передача проекта и инструкций. | Запуск и независимость от разработчика. |

## 5. Что не сделано и какие gates открыты

### 5.1. По принятым этапам

- **P01, F06 — PARTIAL.** До коммерческого распространения нужны: инспекция
  архива `@visx/vendor@4.0.0-alpha.0`, архивная проверка всех вариантов Lightning
  CSS, artifact-level SBOM/notices для Sharp/libvips, юридическая оценка
  распространения.
- **P02.** `CITY` выдаётся только для географических операций и только вместе с
  назначением сотрудника в город. Нет первичной привязки Telegram (реальный вход
  мастера не используется), нет инструмента выпуска веб-доступа новому
  сотруднику, списки без пагинации, cutover-миграция `009` необратима.
- **P03.** P03 сам по себе не добавляет файловый HTTP transport или публичный
  intake. P05 реализует клиентские form-session/submit paths только в
  изолированной T composition; release R их не публикует. Публичный выбор
  города и live `ADDRESS_COVERAGE` по-прежнему отсутствуют; PDF остаётся в карантине.
- **P04.** Реальный прайс не импортируется и не нормализуется; Q06/Q09/Q10
  открыты (валюта, налоги, округление, лимиты, тарифный момент).

### 5.2. Технические границы P05 и эксплуатационные / юридические gates

- **P05 synthetic implementation не является live activation.** Все P05 HTTP
  controllers и commands изолированы в test composition T; `AppModule` R их не
  подключает. Миграции 023/024 исполнялись только на disposable PostgreSQL. Нет
  реальных клиентов/персональных данных, реальных каналов и доставки менеджеру;
  P06/P07/P08/P13P/P14 сохраняют свои будущие scope.



- Ручная TTY-проверка bootstrap и восстановления доступа не выполнена.
- Живой Telegram E2E и первичная привязка сотрудника не проверены.
- Доверенный HTTPS reverse proxy не настроен.
- Согласование обработки реальных персональных данных не получено.
- Рабочая база не мигрировалась; production deployment не выполнялся.
- Ни один мессенджер не подключён к реальным аккаунтам; сайт не опубликован.
