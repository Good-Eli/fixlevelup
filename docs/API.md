# Предварительный контракт REST API

**Статус:** проект этапа 0, ревизия R3.2 от 19.11.2026 (owner decisions, география одной компании и уточнение tooling; историческая R3 ранее помечена R2.1); решения владельца и AS-MAX-01 зафиксированы в [DECISIONS §18/§20](DECISIONS.md), прочие технические детали — предложения. Это схема команд/DTO, не сгенерированный OpenAPI и не работающие endpoints. Приложение, миграции, регистрации ботов и отправка сообщений не выполняются; отдельный [Preflight P01](PREFLIGHT_P01.md) — документация будущего scope, не разрешение начать. Реальный OpenAPI 3.1, DTO, typed client и contract tests создаются после согласования соответствующего подэтапа. Источник — [ТЗ §13](../ТЗ.md); связаны [архитектура](ARCHITECTURE.md), [БД и state machine](DATABASE.md), [решения и доказательства доступа платформ](DECISIONS.md), [порядок реализации](ROADMAP.md).

R2 расширяет клиентский канал с Telegram до TG/VK/MAX с одной бизнес-логикой; Telegram Mini App и бот штатных сотрудников остаются отдельным staff-контуром. До утверждения R2 новые сценарии не считаются разрешением на реализацию. Существующие функциональные группы API и исходный TG-статус WAITING_TELEGRAM_LINK сохранены; WAITING_CHANNEL_LINK добавляется для VK/MAX, общий predicate `is_waiting_link` объединяет оба. Совместимость предполагается добавочной, с явным описанием legacy route aliases. Все3 способа равноправны, но публичный выбор ограничен admin A и фактическими B–D, клиентские операции — также E (§11.7). AS-MAX-01 принят для архитектуры и разработки общего core, admin UI, MAX adapter/binding и contract tests после отдельного разрешения на код. Регистрация/token не prerequisite P01 и других модулей; реальный MAX остаётся закрыт до registration/verification/moderation/credentials, technical readiness, live acceptance и нужной фазы E. Владелец подтверждённо самозанятый и резидент РФ; платформенное подключение отложено. Совместимость фактической конфигурации проверяется на позднем live этапе без повторного исследования/обсуждения юридических разрешений — [DECISIONS §20](DECISIONS.md#20-решения-владельца-r32). Сейчас работа только документационная.

## 1. Правила контракта

- Базовый путь `/api/v1`; HTTPS; JSON UTF-8, кроме загрузок/stream и provider webhook response protocols. Версия API независима от request ETag, версии плана визита и ревизии сметы.
- Frontend не обращается к PostgreSQL. REST-контроллеры, клиентские адаптеры TG/VK/MAX и staff Telegram handlers вызывают те же application commands. Цена, разрешённый переход и право доступа проверяются доменом; адаптер не содержит собственной логики статусов/сумм.
- UUID и публичный номер — строки. `amountMinor`, provider user/peer IDs и другие bigint — строки без арифметики JavaScript Number. `providerSubject` opaque string, уникальный вместе с `provider`; формат одного провайдера не навязывается остальным. Валюта явно в DTO; правила/валюта подтверждаются Q06. Количество — decimal string с whitelist единиц/точности.
- Instants — ISO 8601 с offset, нормализация UTC; локальная дата/время смены отдельными полями плюс IANA timezone и city version. Не принимать неоднозначное «2026-... 10:00» без зоны для визита. API возвращает plan `visitTimezone` snapshot, а до плана — request/F intake city snapshot; скрытой company ENV/browser timezone нет.
- DTO allowlist; неизвестные поля, недопустимая сортировка/enum, лишние `price`, `status`, `customerId`, provider identity в публичной форме отклоняются. Серверный total единственный нормативный.
- Список: `{items, pageInfo:{nextCursor,hasMore}}`; cursor opaque, стабильная сортировка `createdAt,id`; calendar queries — ограниченный `from/to`. Лимит/максимальный диапазон конфигурируются и документируются в OpenAPI. Фильтры/поиск валидируются; телефон не помещать в URL query для логируемого поиска — отдельный POST search.
- Обычный успех: `{data, meta:{requestId}}`; отсутствие содержимого — 204. Ошибка: `application/problem+json` с безопасными `type,title,status,code,requestId,errors[{field,code,message}]`; не возвращать stack, SQL, токены или echo PII. Чужой ресурс — согласованное 404 без раскрытия существования; недостаточная capability внутри доступной области — 403.
- `201` create, `200` read/command result, `202` durable async receipt (не признак завершения доставки/переноса/отмены), `204` logout; `400` syntax, `401` missing/expired auth, `403` permission, `404` unavailable resource, `409` business conflict, `412` stale If-Match, `413` upload size, `415` type, `422` semantic validation, `428` required version missing, `429` throttled, `503` unavailable. Webhook использует отдельный provider response protocol; UI ACK не является доменным успехом.
- DTO с ПД, F/auth/link/action responses и приватные projections возвращают `Cache-Control: no-store`; proxy/SSR не кеширует их публично. Токены и payload с ПД не включаются в query логируемых внутренних API. Provider deep link неизбежно несёт короткий opaque nonce, но не ПД и не credential доступа к заявке.

### Примеры кодов ошибок

`VALIDATION_FAILED`, `CONSENT_VERSION_STALE`, `CITY_CONTEXT_INVALID`, `CITY_CONTEXT_STALE`, `CITY_SCOPE_MISMATCH`, `CITY_CHANGE_REQUIRES_NEW_REQUEST`, `CITY_MEMBERSHIP_REQUIRED`, `SERVICE_AREA_REVIEW_REQUIRED`, `NO_SUITABLE_CAPACITY`, `SCHEDULE_CONFLICT`, `VERSION_CONFLICT`, `TRANSITION_NOT_ALLOWED`, `CHANNEL_LINK_REQUIRED`, `CHANNEL_OPTIONS_CHANGED`, `CHANNEL_OFFER_DISABLED`, `CHANNEL_NOT_READY`, `CHANNEL_PERMISSION_REQUIRED`, `CHANNEL_BLOCKED`, `CHANNEL_PREFERENCE_STALE`, `PHONE_PERMISSION_REQUIRED`, `LINK_EXPIRED`, `LINK_ALREADY_USED`, `LINK_CLAIM_REQUIRED`, `LINK_SESSION_MISMATCH`, `LINK_CONFIRMATION_REQUIRED`, `LINK_CANDIDATE_CHANGED`, `ACTION_EXPIRED`, `ACTION_STALE`, `APPOINTMENT_VERSION_STALE`, `APPOINTMENT_CONFIRMATION_REQUIRED`, `CANCELLATION_REVIEW_REQUIRED`, `QUOTE_VERSION_STALE`, `QUOTE_EXPIRED`, `QUOTE_NOT_APPROVED`, `PRICE_NOT_CONFIGURED`, `ADJUSTMENT_LIMIT_EXCEEDED`, `REPORT_QUOTE_MISMATCH`, `PAYMENT_REFERENCE_MISMATCH`, `CONTACT_MODE_FORBIDS_CALL`, `FILE_NOT_READY`, `IDEMPOTENCY_KEY_REUSED`, `EMPLOYEE_INACTIVE`, `CONFIGURATION_INCOMPLETE`.

## 2. Auth, идемпотентность и concurrency

Обозначения: **P** — публично; **F** — ограниченная web form/request-сессия; **C** — проверенный клиент через любой разрешённый клиентский канал; **T** — активный мастер; **M** — менеджер с capability; **A** — администратор; **W** — проверенный webhook конкретного `channel_connection`. Ни один endpoint не доверяет роль/ID из frontend.

- CRM: server session cookie `HttpOnly/Secure/SameSite`, CSRF token/header для mutating requests, Origin check и allowlist CORS. SSR не является источником permissions.
- Staff Mini App: raw signed Telegram `initData` только в POST body auth exchange; проверка подписи/свежести/active employee. Короткая отзываемая bearer session в памяти, не long-lived localStorage token. Выход/блокировка отзывает сессию. Это не клиентская авторизация VK/MAX.
- F: random opaque browser secret в защищённой cookie, hash на сервере; trusted server-side `intake_city_id/intake_city_version_id` фиксируется при создании F. Только собственная незавершённая форма/созданная заявка и её linking/upload/fallback; city из body/query не заменяет этот context. F не даёт список всех заказов клиента. CSRF применим и к F. Public номер не credential. GET собственной заявки возвращает ETag заявки для последующих **V** операций.
- C: не клиентский password-based web login. Client commands требуют проверенные `channel_account` и private `channel_endpoint`, действующий `request_channel_grant` и policy конкретного действия. `customer_channel_links` — проверенная M:N связь; совпавший account/телефон не объединяет разных customers и не выдаёт все их заявки. Короткий scoped web action при необходимости привязан к конкретным request/action/endpoint и отдельно согласован; общего кабинета он не создаёт.
- В таблицах **I**: `Idempotency-Key` обязателен для команды. Scope = authenticated principal либо F session + operation; для C также endpoint и request. Key не передаёт ПД. С тем же key и тем же canonical body возвращается прежний результат/ссылка на него; с другим body — 409. Проверка прав повторяется и для replay, чтобы не раскрыть ПД после отзыва доступа. Идущий запрос — documented pending/409 retry, не параллельный второй write.
- **V**: требуется `If-Match` с ETag доступного агрегата; отсутствие — 428, stale — 412. В F binding/preference/contact commands это ETag **заявки**, полученный из GET `/public/request-session`; GET link возвращает его в DTO и отдельный link ETag при необходимости. Команды appointment содержат `expectedPlanVersionId`, а связанные изменения заявки — `expectedRequestVersion`; quote/report commands содержат ожидаемую ревизию. Полный набор проверяется атомарно, не по последовательно устаревающим чтениям.
- Для C строки **I,V** обозначают обязательный эквивалент этих guards в adapter/application command: provider не обязан присылать наши HTTP Idempotency-Key/If-Match. Idempotency/action ID и expected versions восстанавливаются из серверного opaque action mapping; authenticated scoped web REST action обязан передать обычные headers. Открытого passwordless C REST login эти таблицы не создают.
- Идемпотентный повтор проверяется до конфликтующего stale-version отказа для собственного прежнего результата, но после Auth/актуального доступа. Provider update dedupe, одноразовый action token и идемпотентность доменной команды — разные уровни, ни один не заменяет остальные. Успешный QUESTION потребляет только свой action, не соседнее APPROVE той же действующей сметы; terminal решение/новая версия отзывает устаревшие действия.
- Создание, назначение, перенос, подтверждение визита, отправка/решение сметы, report submission, payment event, cancellation, linking/preference/revoke используют идемпотентность. Кнопки содержат короткий opaque action ID: серверный mapping связывает endpoint, request, entity/version, действие, expiry, permission epoch. В payload нет цены, адреса, телефона или bearer-доступа к заявке.
- Лимиты входа/форм/слотов/upload/token refresh, размеры body/периоды выборок задаются до релиза. IP rate-limiting данные не сохраняются бессрочно и не попадают в бизнес-аналитику.

Сеть оборвалась после commit — повтор с прежним idempotency key.

### Submit DTO (структура без вымышленных бизнес-значений)

- `appliance`: `categoryId` required; `brandId`, `modelId`/`modelText`, `approximateAge` optional.
- `fault`: выбранные `faultIds`, `otherDescription`, `description`, `errorCode`; требования обязательности текста/числа симптомов Q16. Связь fault↔category проверяет сервер.
- `address`: `street`, `building`; optional `districtId` того же F city, `apartment`, `entrance`, `floor`, `intercom`, `accessNotes`. Город/версия берутся сервером из trusted F и возвращаются read-only; raw `cityId/cityVersionId/city` не выбирают город. District/mapping — advisory; сервер фиксирует immutable address snapshot с city/area versions, display strings/timezone и coverage assessment.
- `preferredVisit`: `date`, `windowStart/windowEnd` с timezone или `manualPreference`; `availabilityCalculationId` informational, не reservation. Пустые окна не блокируют запрос ручного согласования.
- `urgency`: NORMAL/EXPRESS; `contact`: name, normalized phone input, ровно один выбранный messenger provider из public offers либо отдельный PHONE callback путь. `channelSelection:{optionVersionId,catalogVersionId,purpose}` обязателен для no-call intake; сервер проверяет один выбор по current A–D. No-call действует для TG/VK/MAX. Selection сохраняет immutable request preference до binding, но ещё не выдаёт grant/opt-in/platform permission. Fallback добавляется позднее явно, не массивом обязательных способов формы. Срочность не гарантирует прибытие.
- `attachments`: только READY file IDs этой F session; в лимитах опубликованной upload policy.
- `consent`: document version IDs, explicit accepted bool для требуемого основания; маркетинг отдельно и необязателен. Если актуальная версия изменилась — показать новый текст, не принимать молчаливое обновление. `phonePermission` отдельно и только при явном выборе.

Окончательный server result не содержит произвольной суммы и не считается подтверждением времени. Для phone repair заявок маршрут/стартовый статус отдельно согласовать; базовые клиентские пути — короткий callback и подробный no-call. Для TG сохраняется WAITING_TELEGRAM_LINK и точный исходный сценарий №3; для VK/MAX предлагается дополнительный WAITING_CHANNEL_LINK. Проверки общей очереди используют `is_waiting_link`, не переписывают TG-код. Новые enum/rollout утверждаются вместе с [state machine](DATABASE.md#7-state-machine-заявки).

**Предложение порядка согласия/файлов Q02:** шаг 2 выбирает локальные File objects, но не загружает их. В финальном шаге клиент подтверждает документ → `/public/form-session/consents` фиксирует evidence → upload/scan файлов → submit связывает consent и files с заявкой → безопасный binding канала. До consent полный адрес не отправляется в coverage check; район допустим для предварительной оценки. В R2 можно отдельно утвердить раннее узкое согласие purpose=ADDRESS_COVERAGE до ввода полного адреса на сервере: та же consent API фиксирует отдельную версию/evidence+cleanup, а финальное согласие на заявку остаётся самостоятельным. Ранняя загрузка/серверный draft с ПД требуют своего основания и retention. Ручной district-only вариант разрешён исходным ТЗ и не объявляется его нарушением; раннее address consent — проектное улучшение Q02, не уже принятое обязательство. Ошибка upload/coverage сохраняет форму/evidence без ложного успеха заявки.

### 3.1. Городской контекст и инварианты

Одна компания, не multi-tenant система. Каноническая схема — [DATABASE §3.8](DATABASE.md#38-география-одной-компании-основа-будущих-городов-r32), архитектурная ответственность — [ARCH §2.1](ARCHITECTURE.md#21-география-одной-компании-и-исторический-городской-контекст). V1 SINGLE_CITY требует ровно один configured ACTIVE/primary город как readiness rule, без постоянного max1 DB constraint и без публичного выбора города. `GET /public/site` разрешает server-trusted context; F фиксирует `intake_city_id/version`. Ноль/несколько active при SINGLE_CITY → CONFIGURATION_INCOMPLETE, а не первый найденный город. Параметры/headers/body с произвольным city ID не обходят server context; в staff API city определяется доступной scope и проверяется против объекта на каждой команде.

Callback и repair request всегда создаются с NOT NULL cityId/intakeCityVersionId. Если city из F выключен/закрыт для новых intake до первого submit — CITY_CONTEXT_STALE, не silent reassignment на новый primary; новый выбор формы требует нового trusted context. Replay committed submit возвращает прежний snapshot/result после auth. `request.cityId` lifetime immutable; адрес можно исправить внутри того же города versioned командой с coverage/replan/reconfirm guards. Ошибка города требует явной staff cancel/correct policy и **новой linked request** с reason/audit и повторной проверкой contact grants/consent по policy; PATCH city запрещён. Existing address snapshot содержит city/area version IDs плюс скопированные city/district/area display strings/timezone/assessment; переименование/архивация справочника не изменяет старые request/plan/accepted quote DTO.

Appointment и каждая plan version принадлежат request city через composite FK; план хранит visitTimezone/cityVersion/address/zone/policy snapshots и UTC instants. City/zone/district refs и coverage join проверяются same-city. Optional administrative district и FULL/PARTIAL M:N mapping к **версии service area** — подсказки для ручной адресной оценки, не proof IN_ZONE, GIS/геокодирование/полигоны не добавляются. При overlap фиксируется одна actual service zone с evidence.

Assign/reschedule требуют текущих technician city membership **и** zone grant на нужный период, specialty, shift/readiness и глобальной capacity. Lock key = technician ID, не `(technician,city)`; UTC reservations/schedules всех городов, global presence и GLOBAL/CITY exceptions учитываются вместе. Смена/отзыв membership использует тот же lock и не удаляет существующие визиты: conflict/attention+явный manager replan. Межгородские travel blocks/права/UI нужны перед активацией второго города позднее.

Stable catalog items и semantic rules общие, monetary versions и public estimates — cityId NOT NULL; exclusion period scoped `(city,item/rule)`, без global/city fallback. `quote.cityId=request.cityId`; calculation context использует current plan timezone snapshot (до плана — explicit intake context). Другой city price/rule version отвергается; accepted monetary snapshot immutable. Уведомления отображают plan timezone либо intake snapshot, jobs due_at UTC; callback intervals имеют только CITY scope и timezone intake city, без company fallback. Analytics/report projections возвращают selected city/timezone/basis/asOf, общие multi-city periods определяются отдельным поздним контрактом.

Company settings — legal identity/security/retention/channel policies/primary city ref; local contacts/hours/timezone только в service_city_versions. Существующие content blocks/revisions имеют COMPANY/CITY scope и provenance, без duplicate city_content. Общие TG/VK/MAX bots и A–E каталог остаются company-wide, city action выводится из request mapping. Географические административные endpoints описаны в §12: P03 structure, P04 prices, P05 intake, P09 scheduling; P01 только documentation/application ports+synthetic FK proof без domain geography tables. G01–G07 остаются вложенными assertions в существующих X/N/DoD, сохраняя исходные25 и общие69 IDs.

### Идентичность, версии и подтверждение визита

Дополнительный физический визит после завершённого/остановленного не создаётся reschedule старого started plan: `POST /requests/{id}/appointments` принимает validated predecessorAppointmentId и purpose PARTS_RETURN/PAUSED_RETURN/CONTINUATION, исполняя соответствующий PlanPartsReturn/PlanPausedReturn/WF command. Для reconciliation без новых физических работ используется `POST /work-reports/{id}/resubmit-reconciled` (T/M с I,V), с обязательным отсутствием активного visit/safe-stop guard из DATABASE §7. Это не generic setStatus.

`appointments.id` — стабильный идентификатор визита; `currentPlanVersionId` указывает на immutable `appointment_versions`. План содержит sequence, requestId/cityId, cityVersionId/visitTimezone, addressSnapshotId/serviceAreaVersionId, technicianId, arrivalWindow, plannedStart/end, buffers и scheduling policy snapshot. Composite FK гарантируют city плана/адреса = request city; runtime checks подтверждают current membership+zone grant, а capacity/tech lock глобальны. Фактические depart/arrive/start/finish events не редактируют прошлый план. Каждой версии соответствует не более одной `appointment_reservation`; после finish/cancel/supersede она released с историей. План, confirmations и reservation всегда проверяются на принадлежность одному request.

До выезда обычный перенос времени/мастера сохраняет stable id и создаёт новую версию. Назначение другого мастера/адреса/окна повторно проверяет coverage, смену, исключения, готовность и capacity с общими locks всех schedule mutations. Успешный перенос сбрасывает прежние technician acknowledgement и customer confirmation, выпускает новые actions; прежние actions отвечают `APPOINTMENT_VERSION_STALE` и не меняют состояние. Старый outbox тоже проходит current-version recheck перед доставкой. После начала фактического выезда/выполнения новая поездка оформляется новым appointment с predecessor link; прежние actuals/расходы/отчёты остаются у первоначального визита. Поздние изменения проходят review, а не обычный drag-and-drop.

Подтверждение клиента — самостоятельный versioned факт, не request status и не technician acknowledgement. `depart` требует current technician acknowledgement + current customer confirmation либо документированное phone confirmation с действующим явным разрешением звонка. При изменении плана обе стороны подтверждают новую версию. Customer confirmation не означает согласие на оплату любых работ, estimate approval не означает подтверждение времени.

Отмена **будущего первичного визита** клиентом освобождает reservation и по предлагаемому переходу ASSIGNED/TECHNICIAN_ACCEPTED возвращает заявку в WAITING_ASSIGNMENT. Отмена будущего return visit при WAITING_PARTS/PAUSED оставляет эту стадию и создаёт attention. Ни один случай не переводит весь заказ в CANCELLED и не обнуляет согласованные расходы/долг. После выезда `CancelAppointment` создаёт STOP_REQUESTED/pending review с manager alert и обязательным technician acknowledgement безопасной остановки; response содержит `outcome:PENDING_REVIEW`, `operationId` и safe next action. Нельзя ответить «отменено», пока работа/поездка продолжается. Финализация оценивает фактически выполненное, согласованные расходы и платёжные события; отдельная отмена заказа — команда §6. Поздний перенос после безопасного STOP_ACK завершает исходный визит и переводит заявку в proposed PAUSED; новый linked return appointment и обе confirmations не меняют request stage до отдельной Resume command. WAITING_PARTS используется только для запчастей. При STOP_REQUESTED разрешены read/reconcile/STOP_ACK; новые платные actions запрещены. Конкретные transitions/status names (включая PAUSED) — предложение Q19, утверждаются вместе с [матрицей state machine](DATABASE.md#7-state-machine-заявки).

Availability GET/search не создаёт гарантированную бронь. Два менеджера не должны получить два успешных конфликтующих назначения. Публичные окна не раскрывают roster сотрудников. Drag-and-drop CRM вызывает тот же reschedule command с guards; не локальный optimistic-only перенос. Разделение этапов: P09A — публичная availability в этапе 1, P09B — dispatch в этапе 2; это зависимые части одного scheduling core.

Платная работа выбирается из активного утверждённого каталога для составления сметы; отчёт ссылается на согласованные snapshot-строки, даже если текущая цена уже изменилась. Проверка `report.quoteId = line.quoteId`, совпадения request и согласованной версии обязательна; ссылки на строку другой заявки или смешение двух денежных ревизий в одном отчёте отвергаются. Если нужны исторические работы по предыдущему accepted agreement, они сохраняются отдельными связанными revisions с явным основанием, без перепривязки к новой цене. Отчёт сам не меняет amountDue. Платные строки требуют quoteId и approved строки; явно утверждённый бесплатный/NO_REPAIR результат может не иметь денежных строк/quote лишь с `noChargeBasis` и reviewer evidence, а не фиктивной нулевой ценой. Неизвестная цена не считается due=0. Stable `requestWorkItemId` связывает тот же объём между quote revisions; cumulative qty считается по lineage и только effective report revisions, не суммой всех исторических corrections. Submit атомарно FINISH визит/actual end и releases остаток reservation. Возврат на физическую доработку после FINISHED требует PAUSED→нового confirmed/acked/on-site visit; document-only correction сохраняет TECHNICIAN_COMPLETED. Monetary rework→PAUSED→PublishPausedQuote/новая approval→ResubmitReconciledReport→TECHNICIAN_COMPLETED без фиктивного ремонта только при отсутствии активного return visit: SCHEDULED сначала cancel/release, started/en-route сначала safe-stop/STOP_ACK под теми же scheduling locks. Physical rework требует Resume, не короткую reconciliation-ветку. Смешение ID строк без lineage не доказывает отсутствие двойного выполнения.

Смета — полная накопительная детализация с уже выполненными согласованными работами, не delta invoice; новая accepted сумма заменяет прежнюю, а не складывается с ней. Quote header содержит request cityId/cityVersionId/visitTimezone, immutable price/rule source versions того же city, currency и breakdown, согласованный с БД: travel + diagnostics + works (включая явно отражённые materials) + parts + timeSurcharge + expressSurcharge + approvedSurcharges − approvedDiscounts = totalMinor; компоненты неотрицательны, каждая строка попадает в один компонент. Возвращаются также base/adjustments, применимые налоговые обозначения, rounding/calculation policy snapshots, calculationHash, immutable revision и expiry. Состав/порядок расчёта утверждаются Q06; диапазоны публичной формы не превращаются в fixed price. Замороженные monetary поля/линии/политика не редактируются; изменение создаёт ревизию. Истечение — только SENT, по которому нет принятого решения: conditional transition SENT→EXPIRED проверяет ту же версию под блокировкой. APPROVE под тем же request/quote lock проверяет `DB time < expiresAt`, если срок задан; отставший expiry worker не открывает окно позднего согласия. Истёкшая кнопка не согласовывает смету.

Предыдущее принятое соглашение сохраняет денежную силу и amountDue до принятия замены. Отправка новой ревизии блокирует **новые** платные работы, но не стирает выполненные работы, отчёт, существующий долг или receipts. Истечение/отказ новой pending revision не отменяет уже APPROVED agreement; нельзя массово поставить EXPIRED всем сметам с прошедшим expiresAt. APPROVE новой актуальной revision атомарно меняет accepted agreement и баланс по утверждённому правилу; старые callbacks отвергаются. Старая SENT revision может быть SUPERSEDED при выпуске новой, а история accepted решения сохраняется отдельно.

APPROVE не запускает мастера автоматически: `start-repair` отдельно проверяет approval и состояние. QUESTION создаёт диалог/alert и оставляет ожидание; DECLINE не означает автоматический CANCELLED и не обнуляет согласованные диагностику/выезд. Конкретный путь завершения отказа/платного diagnostic-only результата — [матрица state machine](DATABASE.md#7-state-machine-заявки), Q04/Q09. Изменение каталога не пересчитывает согласованную смету.

Указание мастером «получено» не является банковским доказательством. Поле подписывается «сумма оплат, отмеченных в системе». Переплата сохраняется и выделяется, amountDue не подгоняется под cash received. Отмена визита/заказа, новая смета и истечение pending revision не удаляют платежи и задолженность.

### 11.2. Binding: provider claim и подтверждение исходной F

Реальный protocol применяется только при фактических B–C, D с актуальным owner-decision context и нужной части E. Для MAX AS-MAX-01 принят для архитектуры и разработки core/admin/adapter/binding/contract tests без регистрации/token; реальные grant/nonce/send ждут connection/technical/live readiness и E, без нового legal evidence gate. Production/live POST channel-links для неготового scope возвращает CHANNEL_NOT_READY. Тестовые fixtures не доступны публично и не могут изменить evidence на VERIFIED. Общий интерфейс, ручной код или иной transport не создают исключение из правил. Уже созданная заявка проверяет сохранённый option/preference snapshot: поздний A-off только для новых заявок не прерывает её bind при valid B–D.

1. После consent+submit исходная F создаёт link `{provider}`. Сервер фиксирует random token hash, provider+connection+request+F scope, TTL, attempt limits, pairing challenge; raw token выдаётся один раз в deep link без ПД. Провайдер/connection нельзя заменить параметром ссылки. Старые unused tokens отзываются атомарно.
2. Клиент самостоятельно открывает бота/сообщество и выполняет предусмотренное платформой действие. Только проверенный webhook связывает token с provider account/private endpoint и записывает **CLAIM**. В ответ provider получает лишь безопасное подтверждение claim/инструкцию вернуться в исходный браузер, без номера с деталями, адреса, сметы, истории или grant. Другой получатель пересланной ссылки не становится владельцем заявки.
3. Исходная F читает link state с ограниченным identity label и pairing challenge, явно подтверждает конкретного кандидата через POST `.../{id}/confirm` с CSRF+If-Match заявки. Endpoint проверяет тот же F, актуальный claim/candidate, challenge, TTL, current request/grant state и consume once; сменившийся candidate требует нового подтверждения. Provider callback не может подтвердить F за клиента.
4. Только успешное F confirm создаёт verified customer/account evidence и request-scoped grant; M:N связь с customers проверяется, не выполняется auto-merge общей истории. Повтор не выдаёт новый доступ. Перепривязка/отзыв — отдельные команды с evidence; совпавший телефон не доказательство identity.
5. Успешные F confirm+grant, technical platform permission и application opt-in переводят WAITING_TELEGRAM_LINK (TG) / proposed WAITING_CHANNEL_LINK (VK/MAX) → MANAGER_REVIEW по утверждённой матрице; predicate `is_waiting_link` общий. До завершения всех проверок — отдельная служебная очередь, не готовность к dispatch. До platform allow запрещённый канал не используется для напоминаний; F видит next action. Если исходный браузер потерян, автоматического восстановления по bearer link нет: controlled manual recovery с проверкой/evidence и аудитом, policy Q03/Q12.
6. Дополнительный endpoint уже обрабатываемой заявки проходит тот же dual proof, но не откатывает request stage в waiting_link: только первоначальная привязка меняет этот status. Для terminal заявки — отдельно разрешённый recovery/read scope по retention; наличие customer link не выдаёт все заказы.
7. Staff invitation — отдельные token namespace/handlers и Telegram authentication proof intended employee. Клиентский token или grant не создаёт сотрудника, staff invitation не привязывает клиентскую заявку.

Таким образом, на этапе 0 предложена обязательная двухсторонняя проверка browser request ownership + verified provider claim; вариант bearer-link-only не является допустимой реализацией R2. Это проектное решение до пользовательского утверждения, а не уже работающая защита.

### 11.4. Webhook, dedupe и ACK

| Провайдер | Transport acceptance/dedupe | Отдельный UX answer и предел подтверждения |
|---|---|---|
| Telegram | Проверить configured connection/secret header до inbox; key `(connectionId,update_id)`, сохранение+dedupe атомарно, provider 2xx после durable commit | `answerCallbackQuery` снимает ожидание; не означает domain commit или успешную оплату/подтверждение |
| VK Callback | confirmation возвращает server-specific code; обычное событие — expected secret+group_id+API version, key `(connectionId,group_id,outer event_id)` после проверки фактической версии. После durable acceptance HTTP 200 + `ok` | `messages.sendMessageEventAnswer` использует **object.event_id** нажатия, user_id+peer_id; этот event token действителен минуту. Не заменяет HTTP `ok` и не является outer event ID |
| MAX | Provider-specific discriminator/identity/dedupe key по утверждённой официальной версии. Не предполагать Telegram `update_id` или универсальный unique event ID; при отсутствии гарантированного ключа документировать составной key для типа и domain idempotency | Provider-specific callback answer, срок/метод/поддержка только после проверки официального protocol; API schema не доказывает доступ текущего бизнеса |

Без durable inbox при недоступной БД возвращается retryable provider failure, не ложный success. Worker выполняет домен+outbox атомарно и сохраняет outcome; UI callback отвечает максимально быстро допустимым provider protocol безопасным «получено/обрабатывается», если результат ещё не известен. Короткий срок UX answer не заставляет выполнить бизнес-команду до её guards; окончательный результат доставляется отдельно.

Дубли и запоздалые события ожидаемы, общего порядка провайдеров нет. Порядок не выводится из времени HTTP доставки. Ресурсный lock/optimistic versions и ожидаемые entity revisions защищают от гонок cancel/reschedule/confirm/approve. Нельзя обещать end-to-end exactly-once уведомления: outbound retry имеет отдельные transport guarantees. Raw update, peer ID, текст, action tokens/initData и секреты не выводятся в application logs; retained inbox payload минимизируется/шифруется и удаляется по policy.

Для VK: официально описаны `X-Retry-Counter` и повтор после 10 секунд, 3 минут, 10 минут, 30 минут, 1 часа; `Retry-After` с 410/429/503 и интервалом <3 часов, реальное время может быть больше. Несколько ошибок подряд временно останавливают уведомления. Это не гарантия отсутствия потерь/порядка/бесконечных retry. Внешний event_id по VKCOM callback_base — unique, повтор следует игнорировать; schema — technical evidence, фактический envelope/версия проверяются capture-тестом. `message_event.object.event_id` — другой краткоживущий идентификатор.

Для исходящего VK `messages.send` сохраняется один ненулевой int32 `random_id` на один outbox item при retry; 0 отключает uniqueness check. Методная документация в официальном поисковом индексе ограничивает дедупликацию заданным диалогом за последний час и максимум 100 последними сообщениями; полный fetch метода не удался. Поэтому собственная command/outbox идемпотентность обязательна, а random_id не обещает бессрочный exactly-once. Для других провайдеров их способ transport idempotency проверяется отдельно.

### 11.7. Управление способами подтверждения

CRM раздел: **«Настройки → Клиентские каналы и способы подтверждения»**. A не override B–E. Для MAX текущий D context учитывает принятый AS-MAX-01 и позднюю actual config compatibility без повторного юридического запроса; AS не создаёт B/C-live/E.

`AdminOptionDTO` дополнительно различает intent `offerEnabled` и вычисленное `effectiveOfferable`: UI не рисует зелёный «работает» только по intent. Нет endpoint `PATCH {ready:true}`. Future MAX profile можно настроить заранее без B, сохранить draft `enabled` intent, но publish enabled получит CHANNEL_NOT_READY, а не фиктивную регистрацию. A-off+publication применяется к новым intake; существующие grants/binds/deliveries не отзываются этим переключателем.

**Публичный контракт** `GET /public/customer-channels?purpose=REQUEST_CONFIRMATION`:

- Ответ `{data:{catalogVersionId,evaluatedAt,purpose,items:[{optionVersionId,provider,label,displayOrder,supportedActions}]}}`; только A∧B∧C∧D. Не возвращать disabled/unready providers с availability=false/причинами; причины доступны CRM. Public IDs каталога/версии option — config references, не connection/credential IDs. `supportedActions` — закрытый публичный enum CONFIRM_VISIT/REQUEST_RESCHEDULE/CANCEL_VISIT, не raw capabilities/permission names/evidence/protocol/credential metadata; публикация unknown field rejected и contract test whitelist.
- `purpose` — allowlisted bundle, нельзя запросить более слабую capability и затем использовать её для подтверждения. Нет E до клиента; список сообщает возможность выбора, не permission писать этому человеку. Public не выдаёт токены привязки.
- `Cache-Control:no-store` (либо строго ревалидируемый ответ без stale serving; baseline R3.2 — no-store). Submit повторно проверяет current catalog/A–D, не доверяет сохранённому GET. `items:[]` — честное отсутствие доступного messenger пути, показать callback только как отдельный разрешённый клиентом режим, не автоматическое переключение. Намеренное admin A-off всех способов в production — открытое Q24, не уже принятое callback-only business правило; до него no-call release не считается принятым, даже если empty UI технически безопасна.
- При new `POST /public/repair-requests` выбирается ровно один `channelSelection`; current catalog mismatch→409 CHANNEL_OPTIONS_CHANGED с инструкцией обновить список, A-off→CHANNEL_OFFER_DISABLED, B–D fail→CHANNEL_NOT_READY. Нет создания лишней заявки, silent substitute или выдачи клиентского consent. Версия выбора сохраняется в request preference, binding дополняет её grant новой revision.
- Идемпотентный replay ранее committed submit возвращает прежний результат после Auth, несмотря на последующий A-off. Уже сохранённая waiting_link заявка продолжает свой selected option snapshot при B–D; общий A-off не меняет E. Подтверждение binding/отправка проверяют actual connection/technical/live readiness, D с owner-decision context и нужную E; AS-MAX-01 не подменяет фактические B/C-live/E.
- Изменение канала существующей заявки — явный client/evidence command+new preference version; не обычная общая publication. Общий admin toggle не вызывает grant revoke/reroute/смену primary старых заявок. Connection security suspend может блокировать send старым, но сохраняет историю и создаёт attention.

Live staging acceptance — отдельный контролируемый ops/test path без public offer/A, после реальных B+C-tech+D+необходимой фазы E тестового участника и отдельного operational разрешения; C-live не предварительное условие. Не требует уже существующего live PASS, иначе возник бы цикл; результат PASS создаётся лишь фактическим успешным тестом и не public options PATCH. Никакого endpoint для произвольного `liveAccepted:true`; production не использует этот staging-only путь.

Audit обязателен на draft edits/publish/A-off/suspend: actor, reason, UTC, old/new config IDs/flags, affected scope; payload credentials/PII исключён. Concurrent publishes→412/409, один atomic current catalog. Предусмотрены N01–N12 [приёмки](ROADMAP.md#7-сценарии-административного-управления-n01n12), включая попытку bypass B–E, race GET→submit, unchanged old requests/consent и истечение readiness.

## 13. Контрактные тесты и готовность API

На этапе реализации OpenAPI содержит securitySchemes, обязательность I/V headers, DTO request/response каждой роли, enum статусов, validation bounds, safe errors и версию схемы. Единый Vitest5.1.1 runner для backend/frontend/common, Supertest HTTP и Playwright browsers следуют [ARCH §3](ARCHITECTURE.md#3-предлагаемый-стек) и exact inventory [Preflight B](PREFLIGHT_P01.md#b-стек-и-версии--полный-exact-baseline-r32); Oxc legacy decorators/partial metadata требуют Nest integration/build proof и независимого `tsc --noEmit`, совместимость ещё не доказана. Typed client генерируется из schema; CRM/Mini App/public UI не копируют произвольные интерфейсы вручную. CI проверяет compatibility и breaking changes. Добавочные provider поля/routes сначала появляются в схеме; legacy aliases вызывают те же commands и guards, deprecated status/enum mapping утверждается отдельно. Нельзя незаметно менять семантику уже развёрнутого клиента под тем же `/api/v1`.

Обязательны негативные проверки каждой protected группы: unauthenticated; другая роль; чужой request/file/quote/account/endpoint UUID; inactive user; stale session/version/permission epoch; невозможный state; лишнее price/status/provider identity поле. Для I — same body, changed body, parallel repeat, timeout после commit и повтор после отзыва доступа. Для PII — T history/public projection redaction, no-store и отсутствие request bodies в proxy/app telemetry.

Обязательная release/evidence matrix включает **все69** сценариев (25 исходных+20 M+12 X+12 N) [дорожной карты](ROADMAP.md). Ниже технические assertions внутри этих сценариев, не замена/перенумерация IDs:

- G01–G07 — вложенные geography assertions существующих X02/X05/X06/X08 и N/DoD, без новых top-level IDs: callback/request/visit same-city NOT NULL; rename/rezone сохраняет snapshots; cross-city price rejected/accepted quote stable; city+zone membership guards; plan timezone/global tech UTC conflict; v1 без city selector; второй synthetic city с иной timezone/районами/ценами существующими командами без ALTER фундаментальной схемы. P01 проверяет только synthetic FK/snapshot proof, не создаёт domain tables.
- Одинаковая команда с тем же результатом/ошибкой через TG/VK/MAX и REST staff; никакой цены/перехода внутри adapter.
- Forwarded link даёт только CLAIM без ПД/grant; wrong/missing/expired F, CSRF, changed candidate/challenge, reused token и несовпадающий provider/connection не подтверждают binding; ETag заявки возвращается F read. Общий телефон/provider account не раскрывает заказы другого customer; manual recovery/staff invitation используют отдельные evidence/auth paths.
- Platform allow/block, application opt-in, legal consent, preference и request grant изменяются независимо; revoked epoch блокирует старые actions/outbox, PHONE fallback/phone decision/call-record запрещены без explicit phone permission. Timeout не запускает автоматический звонок/параллельную рассылку.
- Wrong provider secret/group/connection/schema, duplicate/reordered events, недоступная БД и внешний провайдер после commit; VK outer event_id и button object.event_id не смешиваются; callback UX answer отдельно от durable domain result. MAX key не подменяется Telegram update_id.
- Два менеджера назначают конфликтующее время; reschedule/address/schedule-exception идут под общими locks. Fail новой брони сохраняет старую; successful new version сбрасывает обе confirmations; старая кнопка/retry/outbox не подтверждает новый план. После started новый визит связан predecessor и не стирает actuals.
- Future customer cancellation освобождает бронь без automatic order CANCELLED; после выезда DTO остаётся pending STOP до review/technician acknowledgement. Долг и выполненная работа сохраняются; клиентский reschedule preference не создаёт бронь сам.
- Состязание quote approve/expiry/new-version; SENT→EXPIRED не затрагивает уже accepted agreement; новая pending revision не обнуляет amountDue, но блокирует новые платные работы. Cross-request/cross-revision report line и overlimit adjustment без конкретного approval отвергаются.
- RECEIPT/reversal/refund immutable, проверяются original receipt/request/currency/остаток и повтор; generic CORRECTION отвергается. Dashboard counters/filter links согласованы по asOf/definitionsVersion; technician summary не раскрывает старую PII.

Операции, зависящие от открытых вопросов соответствующего модуля, остаются проектом; принятое AS-MAX-01/owner §20 не открывает заново MAX legal discussion. Registration/credentials/technical/live/E gates действуют только при реальном подключении и не блокируют architecture/P01/core/adapter/другие модули. P07 core отделён от адаптеров; P09A availability предшествует P08A engineering формы, P08B — отдельный live/release scope с >=1 опубликованным готовым messenger, MAX зависимость условна только при его публикации; P09B dispatch — в ориентировочной группе этап2; P11A quote API может разрабатываться параллельно P10/P11B UI только после стабильного контракта/необходимых доменных prerequisites. Реализация начинается после явного разрешения зависимого подэтапа; окончательные схемы endpoints утверждаются вместе с ER/state machine и юридическими основаниями.
