# P03-02 — кто управляет географией мастерской

**Решение владельца от 21.11.2026:** утверждён вариант 1 — делегированное управление только в назначенных городах. Владелец отдельно принял P03-01 (`3677960`) и разрешил перейти к P03-02. После проверки владелец отдельно принял реализацию P03-02 и выбрал остановку без перехода к P03-03. Это не развёртывание и не выдача прав реальным сотрудникам. Источники: [контракт операций](API.md#121-административная-география-и-scope-p03-не-p01), [проект матрицы](DECISIONS.md#13-текущая-модель-capability-и-операций-r2), [реализованный RBAC P02](RBAC.md).

## Утверждённая матрица

| Операция | Администратор | Менеджер | Мастер |
|---|---|---|---|
| Создать город; включить/выключить город, сменить основной город компании | Только с отдельным глобальным правом на соответствующую операцию: создание — `geography.manage`, активация/смена основного — `geography.publish` | Нет | Нет |
| Читать локальные настройки, районы, зоны и версии | `geography.read`, GLOBAL или в разрешённом городе | Только при явно выданном `geography.read` в назначенном городе | Не административное чтение; только краткая сводка собственных допусков |
| Подготовить новую версию настроек **города**; опубликовать версию города/покрытия **зоны** | Подготовка — `geography.manage`; переключение текущей версии — отдельно `geography.publish` | Нет | Нет |
| Вести районы, создавать зоны, готовить версии покрытия FULL/PARTIAL | `geography.manage` | Можно явно делегировать `geography.manage` только в назначенных городах, без права публикации | Нет |
| Читать и менять территориальные допуски мастера | `staff.geography.read` / `staff.geography.manage`, независимые права | Можно явно делегировать эти операции только для мастеров и только в назначенных городах | Только свои действующие допуски, без истории других сотрудников и без записи |
| Выдать полномочие роли или изменить территорию управления менеджера | Только системный ADMIN через защищённую операцию RBAC; нельзя расширять собственную область | Нет, даже с `staff.geography.manage` | Нет |

**Исключение, отдельно утверждённое владельцем:** пять географических прав включаются автоматически только у первого зарегистрированного администратора. Источник — единственная запись первичной настройки (`staff_bootstrap_marker`), а не сортировка сотрудников или имя роли. На новой установке выдача привязывается к его исходному назначению SYSTEM ADMIN; при обновлении — только к тому же активному и подтверждённому первоначальному назначению. Нет подходящего получателя — нет автоматической выдачи или подстановки другого ADMIN. Повторный вход, обновление, отзыв и повторное назначение роли не должны заново выдавать снятое право. Для остальных администраторов, менеджеров и CUSTOM нет автоматических grants. Пять исходных прав не записываются на общую роль ADMIN. На каждое обращение сервер заново проверяет сессию, операцию, роль, допустимый город и реальный объект. Для работы менеджера с редактором необходимы явные `geography.read` + `geography.manage`, для управления допусками — `staff.geography.read` + `staff.geography.manage`. Право на запись не заменяет независимое право на чтение. Для краткой сводки мастер проходит проверку SELF; она не даёт списка чужих сотрудников, истории или права записи.

Роль разрешает **операцию**. Административное назначение сотрудника ограничивает **территорию управления**. Допуск мастера к работам — отдельная запись с датами и городом/зоной, не источник административной власти. Ни менеджер, ни мастер не могут назначать себе или другим сотрудникам административные города. Изменение территории/полномочий не должно переживать отзыв в ранее открытой сессии. Общие права новой роли и канал входа сами по себе не заменяют эти проверки.

## Как пользоваться API на синтетическом стенде

Все пути ниже относительно `/api/v1`. В существующем редакторе CRM `/crm/access` администратор может явно выдать права роли. Городские назначения и редактирование зон в этом подэтапе выполняются через API; экран географических настроек — следующий объём работ.

| Операция | Путь и данные | Какую версию передать |
|---|---|---|
| Создать черновой город; добавить и опубликовать локальные настройки | `POST /settings/service-cities` с `{code}`; затем `POST /settings/service-cities/{cityId}/versions` с `displayName`, `timezone`, `publicContact`, `officeHours` и необязательным `addressDisplay`; затем `POST …/versions/{versionId}/publish` | Создание города без `If-Match`, для остальных — версия города. Публикация настроек не активирует город |
| Активация/смена primary | `POST …/{cityId}/activate`; при замене активного города нужны `replaceActiveCityId` и `replaceActiveCityVersion`. Для приостановки primary — `POST …/{cityId}/deactivate` с `{suspendIntake:true}` | Версия целевого города; при явной замене также версия прежнего. Никакого подбора города «по умолчанию» |
| Районы, зоны и черновики | `GET/POST …/{cityId}/administrative-districts` и `…/{cityId}/service-areas`; `GET/POST …/service-areas/{areaId}/versions`, `PATCH …/versions/{versionId}`. `GET/PUT …/versions/{versionId}/district-coverage`; PUT заменяет набор `districts: [{districtId, relation, description?}]` | Для создания дочернего объекта — версия родителя. Для редактирования черновика и покрытия — версия черновика |
| Опубликовать покрытие | `POST …/service-areas/{areaId}/versions/{versionId}/publish`, тело `{expectedAreaVersion}` из GET зоны | `If-Match` черновика **и** `expectedAreaVersion` зоны. Два разных черновика с одним старым указателем не могут оба стать текущими |
| Назначить менеджеру территорию; выдать мастеру допуск | `GET/POST …/{cityId}/administrators/{staffId}/assignments`; `GET/POST …/{cityId}/technicians/{staffId}/city-memberships` и `…/service-area-grants`. Выдача: `{validFrom,validTo?}`, для зоны ещё `areaId`. Отзыв: `POST …/{grantId}/revoke` с `{}` | Версия **сотрудника**, указанного в пути, а не текущего администратора. Выдача административного города — тело `{}`. Отзыв допуска в город одновременно отзывает его зоны, не стирая историю |
| Свои допуски; отзыв исключения первого администратора | `GET /telegram/technicians/self/territory` (bearer текущего мастера, без произвольного `staffId`); `POST /settings/geography/bootstrap/{staffId}/{permissionCode}/revoke` (CRM ADMIN с правами управления ролью и соответствующим GLOBAL-правом) | SELF — без версии; отзыв исходного права — версия целевого сотрудника |

Для записи через CRM необходимы действующая сессия, точный Origin, JSON, `X-CSRF-Token` и уникальный `Idempotency-Key` (UUID). Формат версии — `If-Match: "geo-vN"`. Ответ на запись содержит только `{id,version}`, не карточку объекта. Повтор с тем же актором, операцией, целью, телом и версией возвращает прежнюю квитанцию (`200`), без повторной выдачи, аудита или события. Изменённый запрос с тем же ключом — `409`; нет обязательной версии — `428`, устаревшая — `412`. Отозванные полномочия по-прежнему проверяются до возврата квитанции.

Совместимые пути `/catalog/service-areas` и `/technicians/{staffId}/{city-memberships,service-area-grants}` требуют явный `?cityId=<UUID>` и вызывают те же команды. Для списков справочников — `limit` (по умолчанию 50, максимум 200), у районов/зон можно исключить архивные строки. Публичного выбора города и приёма заявок нет. Контакты, текст покрытия и токены в audit/outbox не попадают.

## Критерии проверки

1. **Данные.** Зоны и их неизменяемые версии, необязательные районы, M:N FULL/PARTIAL с составными FK своего города. Ни FULL, ни PARTIAL не доказывают конкретный адрес. На синтетических городах А и Б нельзя подставить чужой район, версию зоны или город. Изменение покрытия не переписывает прошлую версию.
2. **Права и сроки.** Списки отфильтрованы на сервере; чужой ID не даёт доступ к записи, её истории, счётчикам или результату команды. Допуск в зону требует действующего допуска в тот же город на весь заявленный период. Отзыв под общей блокировкой мастера сохраняет историю. Нет допуска на основании должности, наличия сессии или переданного `cityId`.
3. **Команды.** Origin/CSRF для CRM; `Idempotency-Key` для записей, `If-Match` для изменения существующего агрегата, раздельные manage/publish. Повтор перепроверяет доступ, конкурентный отзыв и запись сериализуются, аудит фиксируется в той же транзакции. Обновление primary/ACTIVE в `SINGLE_CITY` не оставляет две действующие конфигурации. Публикация географической версии не открывает публичный intake.
4. **Регрессия.** Fresh/upgrade с `010`, replay, schema drift, ограничения и права на реальном тестовом PostgreSQL; HTTP- и конкурентные тесты для разрешённых и запрещённых действий, прежний P02 RBAC и P03-01 остаются работоспособны. Эта проверка не заменяет будущие тесты цен, заявок и назначений визитов.

**Локальные результаты перед приёмкой:** lint исходников, typecheck и production-сборки API, Web и Mini App прошли. Полный Vitest с включёнными PostgreSQL-тестами — 545/545 (41 файл). Проверены 12 миграций на PostgreSQL 18.7, 79 ограничений CHECK, обновление с данными, повторное применение и отсутствие расхождений Prisma с БД. Playwright — 48/48 на Chromium, Firefox и WebKit в desktop/mobile; браузерные ответы API были синтетическими, а полномочия и конкурентность отдельно проверены на настоящем Nest API и PostgreSQL.

**Вне P03-02:** реальные города и сотрудники, запуск второго города, production и публичный выбор города; цены, адресные заявки и расписание. Миграции P03-02 в рабочую БД не применялись.
