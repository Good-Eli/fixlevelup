## 1. Как читать статусы

- **Зафиксировано ТЗ/пользователем** — сохраняем без пересмотра разработчиком.
- **Предлагается** — инженерное решение, требуется подтверждение; наличие в документации не делает его принятым.
- **Открыто** — нужен бизнес-ответ/юридическое решение/измерение. Не подставлять молчаливый default.
- **Блокирует** — указано, что именно нельзя начинать: весь этап, конкретный модуль или production. Отсутствие реального телефона не мешает создать Auth после разрешения, но запрещает публиковать сайт с придуманным номером.

## 5. Открытые вопросы: без чего нельзя начинать соответствующую реализацию

Группы: **G0** — перед стартом этапа 1/утверждением базовых контрактов; **Gm** — до зависимого модуля; **Gp** — до публикации/эксплуатации. Значения не заполнены за владельца. R3.2: не переспрашиваются подтверждённые facts/MAX assumption/3 равноправных канала/админка/направление городов одной компании; Q21 OWNER_DECIDED с отложенным подключением, Q23 частично release details, Q25 только реальные geo values. Другие модульные Q/технические части ADR остаются открытыми; ниже явно перечислены принятые факты/допущения и невыполненные внешние условия. Три равноправных канала/управление A для новых заявок приняты F12–F14; это не общее утверждение всех ADR или разрешение кода. Операционные ответственные по незакрытым вопросам ещё не назначены. При закрытии каждой строки фиксировать: ответственного, статус OPEN/ACCEPTED/REJECTED/DEFERRED, выбранный вариант, дату, ссылку на подтверждение пользователя и разрешённый scope. DEFERRED не снимает gate зависимого модуля.

### 12.1. Доступ к Docker Engine из сессии

Первичная проверка этапа 0 записала «доступ отклонён к `dockerDesktopLinuxEngine`» и риск «Docker CLI есть, Engine не доступен». Перепроверка 19.11.2026 показала, что это артефакт песочницы DSH, а не состояние Docker: Docker Desktop `4.61.0` запущен, группа `docker-users` содержит `vsiof`, каналы `\\.\pipe\docker_engine` и `\\.\pipe\dockerDesktopLinuxEngine` существуют, а вне confined-режима `docker version`/`docker info` отвечают (Engine `29.2.1`, `linux/amd64`) и видны 6 работающих контейнеров.

Причина прежней записи: DSH в confined-режимах не разрешает открывать именованные каналы, поэтому клиент Docker получает `permission denied while trying to connect to the docker API` при живом демоне. Это ожидаемая граница песочницы, а не дефект окружения; повторять ту же команду «другим способом» внутри песочницы бессмысленно.

Рабочее правило: проверки Engine/`docker ps`/интеграционные запуски контейнеров выполняются вне confined-режима, с подтверждением пользователя на конкретную команду. Клиентские команды (`docker compose version`, `docker buildx version`) работают и внутри песочницы. Не включать unauthenticated TCP API Docker (`tcp://localhost:2375`) и не менять ACL канала ради обхода ограничения.

### 12.2. Git author identity

Наблюдение 19.11.2026: `user.name` и `user.email` настроены **локально** в репозитории, effective identity доступна; конкретный личный email удалён из документации и не повторяется в evidence/logs. Global Git не изменялся; конфигурация Git этой корректировкой не меняется. Техническая разрешимость GIT_AUTHOR_IDENT/GIT_COMMITTER_IDENT **не равна согласию публиковать личный email**. Публичные author/committer address, remote/visibility и первый commit остаются OPEN Q01. Без отдельного approval коммит не создавать даже локально с личным адресом (он может попасть в будущую публичную историю). Предлагается точный no-reply, предоставленный хостингом выбранному аккаунту, либо согласованный служебный адрес. Не выдумывать no-reply ID и не рассчитывать, что Mailmap/настройка профиля скроет уже записанный email. Перед первым разрешённым commit проверить обе effective identities/переменные GIT_AUTHOR_EMAIL/GIT_COMMITTER_EMAIL приватно, без печати адреса; проверить Git index/рабочие docs на личные данные. Текущая работа не создаёт commit, push или изменения `.git/config`. См. [Preflight P01 §E](PREFLIGHT_P01.md#e-безопасные-git-author-и-committer).

Fingerprint может склеить неразличимые lifecycle дубли: такие события только idempotent permission/lifecycle projection, не денежная команда. Edited messages не повторяют CREATE с тем же mid. Transport uncertainty не даёт повторный бизнес-эффект благодаря customer_actions+entity versions.
- События permissions могут приходить вне порядка: DENIED устанавливает новый local epoch; поздний старый ALLOWED не восстанавливает opt-in без доказанного нового user action. При неизвестном порядке/отсутствии server sequence — UNKNOWN/attention и recheck platform permission/явный новый opt-in, fail closed для sensitive sends. Нет единого sorted timestamp всех мессенджеров.

## 16. Каталог сообщений и правила резервного канала

Versioned template = text/action schema+allowlist per provider/audience/locale+review evidence. Allowlist — поля из server projection, не arbitrary request serialization. Из-за отсутствующих business texts здесь **типовой контракт полей**, не готовые обещания/контакты/цены. Deny по умолчанию: полный адрес/телефон/ФИО клиента, свободный диагноз/внутренние комментарии/фото/секреты/ссылки-токены за пределами строго разрешённого action handler. Для quote детализация code/title/qty/price из snapshot необходима ТЗ; legal review Q20 может сузить через защищённое представление без потери доступного клиенту расчёта.

Fallback алгоритм R2: (1) intent фиксирует цель/semantic version; (2) primary grant+platform allow+app service opt-in+legal basis+connection access+template approval проверяются перед каждой отправкой; (3) transient retry по backoff/provider rate limits до policy limit; (4) hard block/исчерпание→CRM attention; перейти только к заранее перечисленному fallback этой request preference с соответствующим scope и consent; (5) перед fallback повторно проверить current plan/quote/permissions, старые сообщения obsolete; (6) provider accepted не read; одновременно пришедшие ответы разных каналов дедуплицирует domain action. Недоставка не меняет заявке выбранный режим и не включает PHONE. Exact retry TTL/лимиты/тихие часы/когда fallback на uncertainty — Q18; uncertain outcome может дать duplicate external messages, UI/домен не дублирует бронирование.

Revocation не равна cancellation заказа: STOP/deny прекращает уведомления/действия конкретного endpoint; user может выбрать иной endpoint с proof, либо явно разрешить звонок. Если нет разрешённых путей — CRM issue и информация в существующей F-сессии, а не звонок по сохранённому номеру. Grant revoke, opt-in revoke, platform block — отдельные события/epoch; восстановление одного не восстанавливает всё автоматически.

## 21. P02-01 — модель доступа и контракт каналов

### Утверждено владельцем 20.11.2026

- Администратор и менеджер имеют веб-кабинет; менеджеру необходима также возможность оперативно распределять поступившие заявки между мастерами с телефона. Полноценная работа, статистика, аналитика, настройки и прочие функции менеджера остаются в веб-кабинете. Мастер работает через Telegram Mini App; создание мастера не создаёт автоматически веб-логин или пароль. Клиент взаимодействует через Telegram, VK или MAX; все три — целевой функционал.
- После аутентификации применяется единый серверный контроль principal, роли, capabilities, scope и актуального состояния; канал входа сам по себе не добавляет прав. Staff-права отделены от клиентских прав на конкретную заявку. Default deny и запрет самоэскалации обязательны.
- Staff Telegram Mini App и клиентский Telegram-бот — разные сценарии, даже если у одного человека совпадает Telegram subject. Клиентский grant не создаёт staff-доступ, staff link не создаёт customer grant.
- P02-01 разрешён для документации; код, миграции, зависимости и реальные подключения не входят в этот scope. Следующие подэтапы требуют отдельного разрешения. Отсутствие platform accounts/tokens не блокирует проектирование и offline-разработку; реальные подключения и live-приёмка проверяются отдельно.

### Минимальный проектный контракт: identity и authorization

Аутентификация проверяет credential конкретного способа доступа и создаёт доверенный серверу principal; клиентские параметры, display name, телефон и имя канала сами его не задают. Авторизация — отдельная общая серверная проверка: тип и идентификатор principal, текущие роль/активность, capability или применимый request grant, scope/ownership и состояние ресурса/времени. Для клиента вместо staff role/capability применяется тип client и request-scoped grant с разрешёнными действиями; общий механизм различает типы principal, не выдаёт клиенту staff-роль. Публичная F-сессия — отдельный ограниченный контекст формы, не полноценный staff/customer principal. Проверка повторяется для replay и перед транзакционным write/отложенным действием; старые сессии, кнопки и данные UI не закрепляют право навсегда. Защищённый write и конкурентный revoke/изменение прав сериализуются в БД общим lock либо version-CAS с конфликтом записи на общем authorization state в той же транзакции: если revoke зафиксирован первым, write отклоняется; если write зафиксирован первым, его результат сохраняется, последующие действия запрещены. Конкретный протокол выбирается при реализации и проверяется конкурентным тестом revoke/write. Для внешней отправки абсолютный отзыв уже начатого сетевого вызова не гарантируется. Неизвестное право или scope запрещено; нельзя выдавать себе или делегировать отсутствующие полномочия. GLOBAL/CITY — типизированный контракт; фактические CITY grants/FK только после P03 ([DATABASE §3.8](DATABASE.md#38-география-одной-компании-основа-будущих-городов-r32)).

Web-credential относится к менеджеру/администратору; мастер идентифицируется проверенным Telegram Mini App initData и уже существующей активной staff-связью. Для будущей реализации предлагаются случайные opaque session secrets: хэш секрета хранится на сервере, проверяются срок, отзыв и актуальное состояние/версия доступа; защищённая web cookie — HttpOnly/Secure/SameSite с CSRF/Origin-защитой, Mini App session — в памяти, не в long-lived localStorage. Пароли — Argon2id; логин с общей ошибкой и ограничением попыток, logout/блокировка отзывают сессию, смена пароля отзывает остальные. Rotation и ограничения replay проверяются атомарно. Это проектные security-критерии, не реализованные механизмы; bootstrap, параметры хэширования, TTL/renew/recovery и proof привязки требуют согласования для следующих подэтапов. Телефон и совпадение внешнего subject не объединяют клиентов и сотрудников и не расширяют доступ к заказам.

### Мобильное распределение менеджером: предложение P02-01

Утверждена потребность менеджера оперативно распределять заявки с телефона, не отдельный технический способ реализации. **Рекомендуемый, пока не утверждённый вариант:** обычный служебный Telegram-бот с inline-кнопками — основное оперативное представление; адаптивная страница конкретной заявки в существующем веб-кабинете — дополнительное. Бот уведомляет о новой заявке, показывает краткую разрешённую информацию, предлагает назначение и список подходящих мастеров, затем подтверждение и фактический результат/конфликт. Мобильная страница вызывает ту же операцию под обычной web-сессией. Отдельный мобильный кабинет, статистика, отдельное приложение и менеджерский Mini App не проектируются; достаточность обычного бота необходимо проверить, а не считать доказанной.

**Staff identity и привязка (предложение):** менеджер сохраняет web credential и может привязать Telegram subject к той же активной staff-учётной записи. Вариант proof: в авторизованной web-сессии менеджер инициирует короткоживущий одноразовый challenge; бот получает проверенный private sender как candidate; исходная web-сессия показывает минимальную проверяемую метку кандидата и требует отдельного подтверждения с CSRF-защитой. Challenge связан с manager/session/connection, ограничен по сроку и попыткам, хранится как hash, consume/revoke атомарны. Один введённый Telegram ID, пересланное приглашение, Start или callback не доказывают контроль обеих сторон и не выдают связь. Rebind/recovery и отзыв требуют отдельного безопасного подтверждения и аудита; старые actions инвалидируются. Точные TTL, UX против социального обмана, политика смены привязки и доказательство intended employee согласуются до реализации. Staff бот — отдельный доверенный контекст от клиентского Telegram; мастерский Mini App тоже не является менеджерским интерфейсом. Физическое разделение или безопасная изоляция bot connections — вопрос реализации и security review, не автоматическое право по Telegram ID.

**Единая операция назначения:** staff bot и mobile web вызывают существующие общие Dispatch candidate query и команду создания назначения ([API §7](API.md#7-расписание-и-диспетчеризация)); не создаётся вторая бизнес-логика. Сервер каждый раз проверяет active manager, `dispatch.manage`, GLOBAL/CITY scope/доступ к заявке, current state и version, активность и пригодность мастера, текущие city/zone/skills/shift/readiness и capacity. Список кандидатов — снимок, не бронь; при подтверждении проверка повторяется под общими locks назначения/смен/отзыва и транзакционными guards. Идемпотентность и версия запроса различают повтор уже совершённой команды и устаревшее/конфликтующее новое действие; после отзыва прав результат повтора не раскрывается. Два конкурирующих назначения не получают два несовместимых успеха. Команда атомарно фиксирует план/резервацию, историю, business audit и outbox; результат после commit, а callback ACK сам по себе не успех. Старая кнопка не назначает повторно или на изменённый план; пользователю возвращается безопасный актуальный конфликт/необходимость обновить выбор. Режим выбора окна и другие обязательные поля не обходятся ради краткой кнопки.

**Уведомления (предложение):** связь со служебным ботом активируется только после подтверждённого связывания и разрешённого запуска/регистрации менеджером; получатели — активные менеджеры с `dispatch.manage` и scope заявки, а не все сотрудники. Отправка допускает только минимум: например безопасный reference/номер и тип события без телефона, адреса, файлов и иных лишних ПД; окончательный allowlist согласуется. Ссылка ведёт на внутренний маршрут конкретной заявки без секрета или ПД и не является credential: на мобильном сайте обязательна web-аутентификация и повторная авторизация. В бот-кнопках только короткие opaque references, связанные с recipient, операцией, объектом/версией и сроком; новый запрос повторно проверяет права, ни ссылка, ни callback payload не является самостоятельным правом.

Outbox хранит один semantic notification intent на событие/получателя/цель; transport dedupe отдельно от бизнес-идемпотентности и не гарантирует exactly-once внешнего сообщения. Перед отправкой повторно проверяются активность, scope, link и актуальность состояния; устаревшие действия инвалидируются сервером, при возможности сообщение обновляется, но доступность редактирования не условие безопасности. Блокировка бота, постоянный отказ, retry exhaustion или неопределённый результат фиксируются без потери заявки и видимы в CRM/операционном alert; bounded retries/backoff для временных ошибок, uncertain outcome не объявляется недоставкой и не запускает бесконтрольный повтор/другой канал. Конкретная escalation/оповещение без доступного получателя требует решения; автоматического назначения нет.

### Минимальный проектный контракт: клиентские каналы

- **Вход и нормализация:** каждый отдельный adapter проверяет transport/connection и подлинность доступным платформе способом, валидирует вход и нормализует его в общий типизированный event: источник/connection, идентификатор или допустимый ключ события, проверенный sender/private endpoint, тип и минимальные данные действия. Недостоверные/неполные сведения не становятся principal или grant. Адаптер отвечает в соответствии с протоколом платформы; технический ACK/ответ на кнопку не доказывает бизнес-успех.
- **Общая обработка:** durable приём и transport dedupe предшествуют асинхронной обработке там, где применимо. Core повторно проверяет действующий grant, разрешённое действие, scope, состояние и версии и вызывает общие application commands. Adapter переводит форматы/ошибки платформы, но не определяет правила заявок, записи или цен. Конкретные схемы и особенности API уточняются в P07-TG/VK/MAX, без нового общего платформенно-зависимого домена.
- **Кнопки и callbacks:** opaque action reference разрешается сервером в конкретные endpoint, заявку, действие, актуальную версию и срок; данные кнопки сами не предоставляют доступ. Подтверждение записи — отдельная доменная команда, не ACK транспорта и не факт отправки сообщения. Пока P09B не реализован, проверяется контракт на synthetic командах, а не реальная запись.
- **Привязка:** проверенный platform sender подтверждает лишь контроль endpoint, а не владение заявкой. Проект ADR04/Q17 — проверяемый claim и отдельное подтверждение исходной F-сессией; пересланный bearer link сам по себе не создаёт grant. Выдавать grant только после принятого proof и проверки scope; детали dual proof, recovery/rebind и merge требуют согласования Q03/Q17. Контакты и совпадающий телефон не дают автоматического merge.
- **Повторы и доставка:** transport dedupe, одноразовость действия и idempotency доменной команды — разные уровни. Повтор после отзыва снова проверяет доступ; конкурентные действия разных каналов не должны повторно менять бизнес-состояние. Отправка после фиксации доменного результата через outbox с повторной проверкой текущих прав/разрешений; ограниченные retries/backoff для временных ошибок, постоянный отказ/исчерпание — наблюдаемая ошибка и разбор. Неопределённый результат внешней отправки не равен недоставке: возможны дубли сообщений, exactly-once доставка не обещается, автоматический звонок или неразрешённый fallback запрещены. Подробнее — [API §11](API.md#11-клиентские-tgvkmax-привязка-и-доставка) и [архитектура §10](ARCHITECTURE.md#10-клиентские-каналы-уведомления-и-общение).

### Проверки и секреты

| Уровень | Что доказывает | Чего не доказывает |
|---|---|---|
| Unit и общие contract tests | Политики, нормализацию и одинаковый контракт команд, включая deny/replay/version и ошибки на synthetic данных | Совместимость с реально работающей платформой |
| Mock/stub platform API | Offline-модель входа/исхода, retries и платформенные ответы по зафиксированным fixtures | Реальный webhook, credentials, доставку или фактические лимиты |
| Интеграция с реальным API | Отдельно разрешённые операции с настоящим тестовым connection и актуальным API | Полный бизнес-путь без E2E и всех его зависимостей |
| Live/staging E2E | Реальную привязку, действия и сообщения в разрешённой staging-среде конкретного провайдера; полный booking — после P09B | Готовность других каналов или production без отдельных gates |

Fixtures и stub не должны попадать в production как подмена adapter. Токены и иные секреты передаются через переменные окружения или защищённое хранилище, разделяются по средам, не хранятся в исходниках/Git и не пишутся в логи; raw initData, содержимое подписанных ссылок и ПД также не логируются. Missing/invalid secret закрывает соответствующий реальный connection, но не блокирует offline fixtures или другие каналы. Реальные подключения, отправки и тестовые участники требуют отдельного разрешения и доступов; synthetic успех не становится live PASS.

### Открыто до соответствующей реализации

- **Q03/Q17:** доказательства и полномочия для привязки, смены endpoint, потери исходной F-сессии, recovery/rebind и ручного merge; доступ к подтверждённым ранее заявкам. Предлагаемый dual proof не объявляется утверждённым.
- **Q12:** точное окно адреса/телефона/файлов мастера, содержимое истории, немедленный отзыв файлов, сроки и ограничения staff/F/link сессий и повторного обмена initData. Никакие TTL не назначены этим документом.
- Матрица role × capability × scope/limits (§13), порядок делегирования без самоэскалации, безопасный bootstrap и восстановление credentials; конкретное доказательство intended employee для staff Telegram link.
- Для клиентских каналов — Q02/Q18/Q20 и доменные решения Q04/Q19 по мере соответствующих модулей; детали transport/API актуализируются при реализации адаптеров. AS-MAX-01 остаётся принятым допущением разработки, а не фактом реального подключения или новым договорным запросом.
